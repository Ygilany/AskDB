**With a tenant policy and any scope but `global`, the tenant check refuses a Postgres planner-statistics relation, under every dialect.** The per-table checks look only at tables the policy names, so a `SELECT` could read values sampled from every tenant's rows through `pg_stats` (`most_common_vals`, `histogram_bounds`), beside a query that carried its tenant predicates, and `ask()` returned it with `tenantGuardrail: { passed: true }`, even under `enforcement: strict`; the read-only check allows the read too. Now naming `pg_stats`, `pg_stats_ext`, `pg_stats_ext_exprs`, `pg_statistic` and `pg_statistic_ext_data`, qualified with `pg_catalog` or not, is a tenant finding with the new rule code `UNCHECKABLE_RELATION` (`tableId: ""`): `strict` throws `TenantGuardrailError`, and `warn` returns the warning. `validateTenantGuardrails()` reports it too. A listed name counts in any code position, as a listed function's does, so a column or an alias named like one is refused; text in strings and comments isn't. Code that handles every `TenantGuardrailRuleCode` needs a case for it. No other system relation is refused, and row-level security stays the boundary (ADR 0012).
