**With a tenant policy and any scope but `global`, the tenant check refuses a statement that doesn't start with `SELECT` or `WITH`, under every dialect** (#698). A custom `AskDialect` skips the read-only check by design (ADR 0010), and the tenant check read a `DO` body as a dollar-quoted string, so `ask()` returned a `DO` block, `CALL`, `EXPLAIN` or `SHOW` from a custom dialect with `tenantGuardrail: { passed: true }`, even under `enforcement: strict`. A `DO` block could then read every tenant's rows. Now every statement must start with `SELECT` or `WITH` past any comments and opening parentheses, read with the shared lexer. A statement ends at each `;`, and on SQL Server also at a statement verb such as `EXEC` or `DECLARE`, which T-SQL runs with no `;` before it. A custom dialect is read every engine's way, with both string settings for Postgres and MySQL, and MySQL's versioned `/*!NNNNN … */` comments read both as code and as comments. Any other statement is a tenant finding with the new rule code `NOT_SELECT_OR_WITH` (`tableId: ""`): `strict` throws `TenantGuardrailError`, and `warn` returns the warning. `validateTenantGuardrails()` and `bindPreparedQuery()` report it too. Built-in dialects already rejected these statements in the read-only check, which still throws first. Code that handles every `TenantGuardrailRuleCode` needs a case for `NOT_SELECT_OR_WITH`.
