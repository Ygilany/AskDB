**Omitting sensitive identifiers now also withholds text that names them (#374, ADR 0022).** With `omitSensitiveIdentifiersFromNlToSqlPrompt: true`, the NL→SQL prompt used to drop a sensitive column's own line but keep every description, alias, enum value and common query language block that named it, so a `customers` description of "Stores each customer's email and phone" still told the model about `email` and `phone`. Both prompt builders now withhold that text, by the schema contract's mention rule and ADR 0017's schema-wide names: `formatSchemaV2ForNlToSql` drops a table's description and each matching alias, a column's whole annotation (aliases, enum values, description) when any part names one, and the common query language block. `synthesizeRetrievedDdl` does the same for the schema text it renders, and drops the text of every retrieved chunk that names a sensitive column, checked as the prompt renders it, or carries `sensitive: true`, so an index built with `includeSensitiveDescribable: true`, an index built before beta.44, or a custom retriever can't put it back; the chunk still picks its tables. With omission off nothing changes, since the prompt lists sensitive names tagged `(sensitive)` anyway.

`@askdb/core` exports `sensitiveMentionNames(schema)`, the list of names the rule checks (a column marked sensitive itself by its bare name, a column sensitive only through its table as `{ table, column }`), which `@askdb/rag`'s chunker now imports instead of keeping its own copy; its chunks don't change. `NlToSqlSchemaFormatStats` gains a required `mentionDroppedCount` (always `0` with omission off and for a v1 schema), `synthesizeRetrievedDdl` returns one too, and the `askdb.prompt.sensitive_redacted` and `askdb.pipeline.retrieval_used` log events carry it.

`createMentionMatcher` now groups qualified names by table and checks each text first against a small pattern of the bare names and each table followed by its separator, running the full pattern only on a hit. Checking texts against every column of many sensitive tables then costs about as much as checking against one column per table (about 50 ms instead of 1.8 s for 90,000 texts against 900 names, on Node 22 as well as 26); its matches don't change.

**Upgrade notes:** code that builds an `NlToSqlSchemaFormatStats` object by hand (a test double, say) must now set `mentionDroppedCount`; `0` keeps the old meaning.
