**With a tenant policy and any scope but `global`, the tenant check refuses a call whose reads it can't see, under every dialect** (#702). The per-table checks blank string literals, so a `SELECT` could reach every tenant's rows through a function that runs a query or reads a table named in a string, and `ask()` returned it with `tenantGuardrail: { passed: true }`, even under `enforcement: strict`: `query_to_xml('SELECT * FROM orders', …)` from a custom `AskDialect`, which skips the read-only check, and `table_to_xml('orders', …)` or `crosstab('… FROM orders …')` under the built-in Postgres dialect, whose read-only check allows them. Now such a call is a tenant finding with the new rule code `UNCHECKABLE_FUNCTION` (`tableId: ""`): `strict` throws `TenantGuardrailError`, and `warn` returns the warning. `validateTenantGuardrails()` and `bindPreparedQuery()` report it too. The list is fixed in the tenant check: `query_to_xml`, `query_to_xmlschema`, `query_to_xml_and_xmlschema`, `cursor_to_xml`, `ts_stat`, `ts_rewrite`, `crosstab`, `crosstab2`, `crosstab3`, `crosstab4`, `table_to_xml`, `table_to_xml_and_xmlschema`, `schema_to_xml`, `schema_to_xml_and_xmlschema`, `database_to_xml`, `database_to_xml_and_xmlschema`, `connectby`, `dblink_build_sql_insert`, `dblink_build_sql_update`, `xpath_table`, `dblink`, `dblink_exec`, `dblink_connect`, `dblink_connect_u`, `dblink_open`, `dblink_send_query`, `dblink_fetch`, `dblink_get_result`, `OPENQUERY`, `OPENROWSET`, `OPENDATASOURCE` and `set_config`, called bare, quoted or qualified, in any case, with comments allowed before the `(`. Code that handles every `TenantGuardrailRuleCode` needs a case for `UNCHECKABLE_FUNCTION`.
