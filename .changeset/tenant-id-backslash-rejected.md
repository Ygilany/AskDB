**Breaking: AskDB inlines a tenant ID only when it is printable ASCII without a backslash**, on every dialect (#360, #371, ADR 0024). `ask()` and `resolveTenantSql()` in `tenantSqlMode: "sql-only"`, and `bindPreparedQuery()` (whose `sql` always inlines tenant IDs), throw `TenantScopeError` with reason `UNESCAPABLE_TENANT_ID` for any other ID instead of returning SQL. Before, the ID was escaped for the dialect, or only had its quotes doubled for a custom `AskDialect`, and the literal could end early on the server. On Postgres with `standard_conforming_strings = off`, the ID `x\' OR 1=1 --` made a scoped query return every row. Under a MySQL or MariaDB connection charset of `sjis`, `cp932` or `ujis`, `2¥' OR 1=1 --` did the same, because `¥` is sent as a backslash. Printable-ASCII IDs without a backslash are unchanged. A control character in a tenant ID now throws this `TenantScopeError` rather than `QueryParameterError`. **What a host must change:** with tenant IDs outside printable ASCII (for example `café` or `東京`), call `ask()` in `tenantSqlMode: "sql-params"` (the default), which passes any ID as a driver parameter. `bindPreparedQuery()` can't rebind such an ID yet (#664).
