# ADR 0011 — Connection labels are built from parsed parts, never by masking

## Status

Accepted (2026-09-29).

## Context

AskDB shows a label for a configured database connection: Studio serves one as `sourceLabel` from `GET /api/introspect/status`, and the connector registry builds it from what each engine's adapter parses. The connection string behind the label usually carries a password, so the label must never contain one.

Studio first built the label with `new URL()` and printed `protocol//host/path`. For the SQL Server Prisma/JDBC form (`sqlserver://host;database=db;user=sa;password=S3cret`) the non-special scheme parses with an opaque host, so the whole `;password=…` tail was shown. #189 replaced it with denylist masking: find each secret (URL userinfo, `password=`-like keys, SQLite `key=` params) and replace it with `****`, keeping the rest of the string. Three independent review rounds each found a new way past the masking:

1. **Round 1.** A password containing an unencoded `/`, `?` or `#` ended the URL authority before the `@`, so no userinfo was found and the input came back unchanged (`postgres://app:pa/ss@db:5432/app`, `mysql://root:pa/ss@db:3306/shop`, `mssql://sa:S3/cret@host:1433/db`). In the Prisma form, a password containing `@` turned the port's `:` into the start of "userinfo", which masked the port and left the rest of the password visible (`sqlserver://host:1433;…;password=p@ssw0rd` → `sqlserver://host:****@ssw0rd`).
2. **Round 2.** Leading whitespace hid a URL from scheme detection (` postgres://u:secret@h/db` came back unchanged). An unescaped separator in an unquoted password (`Password=ab;cd;Database=x`) masked only `ab`. SQLite `file:` URIs carried `key=` / `hexkey=` encryption keys in the query string, which nothing masked.
3. **Round 3.** A quoted or braced value followed by more text leaked the tail (`?password='ab'cd` → `?password=****cd`, same for `Password={ab}cd;`). JDBC and near-miss URL forms were not recognised as URLs, so they came back unchanged (`jdbc:postgresql://u:secret@h/db`, a quoted URL, `postgres:/u:secret@h/db`, `sqlserver://sa:se;cret@h`). A percent-encoded SQLite key name (`file:app.db?%6Bey=secret`) did not match the key denylist.

Every fix added another rule to recognise one more way a secret can be spelled, and every round found a spelling the rules missed. The failure is structural: masking copies everything it does not recognise as a secret, so any unrecognised spelling leaks.

Option A (below) then ran into a second structural problem. The first version of A parsed each engine's formats with AskDB's own label parser, and three delta reviews each found a spelling that parser split differently from the driver, so part of a password was read as the database or server: an unquoted `;;` (`Password=p;;Database=leak` → `sqlserver://h/leak`), a value starting with `;` (`Password=;Database=leak`), and Unicode whitespace before that `;` (`Password=\u00a0;Database=leak`). `@tediousjs/connection-string`, the parser `mssql` uses, reads all three as part of the password. A second implementation of a grammar diverges from the first at its edges, and the edges are where passwords live.

## Options considered

### Option A — Build the label only from parts that parsed cleanly (chosen)

Each engine parses its own connection-string formats into a small set of parts known to be safe to show: host, port and database, or a file path for SQLite. A shared builder turns those parts into a label and checks each part against an allowlist (hostname characters, digits for the port, identifier characters for the database, no `? # ; = @` or control characters in a file path). If the input does not parse cleanly, or any part fails its allowlist, the label is `configured <engine> connection`. No substring of the input outside those parsed parts is ever copied.

A new spelling of a secret can no longer leak: the label never contains text the parser did not deliberately extract and the allowlist did not accept. The cost is that some legitimate strings (a libpq `key=value` DSN, a SQL Server named instance, a Prisma string with `user=name@server`) get the fallback label instead of a host and database.

### Option B — Denylist masking (rejected)

Find the secret and replace it with `****`, as #189 did. Rejected because of the three rounds above: masking fails open. Each new spelling (an unencoded reserved character, whitespace, a quote followed by text, a JDBC prefix, percent-encoding) leaks until someone finds it and adds a rule. The concrete bypasses are listed in the context section; each is now a row in the label tests.

### Option C — Engine-only label, no host or database (rejected)

Always show `configured <engine> connection`. This can never leak and needs no parsing. Rejected because the label exists to tell the user which database Studio is about to introspect; "configured postgres connection" can't distinguish staging from production. Option A gives the same guarantee for every input that doesn't parse cleanly, and still shows the host and database for the ordinary strings that do. The extra risk A takes is limited to what the parser extracts, and the allowlist bounds even that.

### Where the allowlist is applied: parts at the registry, or a label string from the adapter

Option A still leaves a choice of contract between the engine and the host.

- **A1, adapters return parts and the registry formats (chosen).** The adapter's optional `connectionLabelParts(connection)` hook returns `ConnectionLabelParts` or `undefined`; `registry.connectionLabel()` always calls `formatConnectionLabel` on them. There is no path by which an adapter's own text reaches the label, so the allowlist applies to every adapter, first-party or third-party.
- **A2, adapters return a label string (rejected).** A `connectionLabel(input): string` export per engine, or a string-typed adapter hook, makes the allowlist optional: an adapter that forgets `formatConnectionLabel` can return the raw URL (`oracle://scott:S3cret@db:1521/orcl`) or a masked string (`oracle://scott:pa/ss@db:1521/orcl`, the round-1 bypass). This was the design on #189 before the delta review; the review on #199 probed both leaks through a third-party adapter. It also forced Studio to switch on the engine to find each engine's function, which ADR 0007 rules out.

## Decision

Option A, with the A1 contract.

- **Parsing is engine knowledge.** Each engine package owns the parser for its formats: `@askdb/postgres` and `@askdb/mysql` (URLs), `@askdb/sqlserver` (`mssql://` URLs, the Prisma/JDBC `sqlserver://host:port;key=value` form, and ADO.NET `key=value;` strings), `@askdb/sqlite` (plain paths and `file:` URIs, reading only the path). The parser is internal to the engine package and is wired to hosts only through the adapter's `connectionLabelParts` hook; engines export no label function. Postgres export bundles and Prisma schema paths are returned as `{ file }` parts.
- **Parts come from the driver's own parser; never a reimplementation.** An engine takes host, port and database from the same parser its driver uses, so the label names exactly what the connection will use and can't split a string differently from it:
  - `@askdb/postgres` uses `pg-connection-string`, the parser `pg` uses (a `?host=` override included).
  - `@askdb/sqlserver` uses `resolveConnectionInput()` (AskDB's own code for `mssql://` and Prisma's `sqlserver://` form), and for ADO.NET strings `@tediousjs/connection-string` with `MSSQL_SCHEMA`, as `mssql` does. The step `mssql` applies after it (splitting `data source` into server, instance and port) is mirrored, and a differential test checks it against `mssql`'s `ConnectionPool.parseConnectionString`.
  - `@askdb/mysql` uses WHATWG `new URL()` with the mapping `mysql2`'s `ConnectionConfig.parseUrl` applies. `mysql2` itself is not a dependency (it is about 630 KB with seven dependencies, and an optional peer); a differential test checks the result against `mysql2`'s `parseUrl`.
  - `pg-connection-string` (16 KB) and `@tediousjs/connection-string` (34 KB) have no dependencies of their own and are exact-version dependencies of the engine package, because label code runs even when the driver isn't installed. Their versions match the ones `pg` and `mssql` resolve in the lockfile; a driver upgrade that bumps them should bump these too.
  - Prisma's `sqlserver://host:port;key=value` form is the one grammar AskDB parses itself, because it is AskDB's connection code (`parsePrismaSqlServerUrl`), not a driver's: `mssql` never sees that string. Adopters' working strings must not break, so the parser is the earlier one plus Prisma's `{…}` escaping: a string without `{` connects with exactly the same values as before (a test runs the pre-#189 parser as a fixture over a corpus), a `{` opens a span read verbatim up to the first `}` as in Prisma's own parser (`prisma/connection-string`, `src/jdbc.rs`), and Prisma's credential aliases (`username`, `uid`, `pwd`) are read only when the canonical key is absent. `initial catalog` is still ignored, because reading it would change where a working string connects. The one class this can't keep is a value holding a literal `{`: the old parser read braces as plain characters (`password={abc}` was `{abc}`), Prisma's grammar reads them as an escape (`abc`), and an unclosed `{` now throws. Which reading to keep is an open choice for the maintainer (Prisma users sharing one URL need the escape; AskDB-only strings may rely on the literal reading); the test records both readings for each brace row. The label is stricter than the connection: a `sqlserver://` string with `{`, a quote, a segment that isn't `key=value`, or an empty segment before another one can be read more than one way (the parsers before and after Prisma escaping disagree, or an unbraced `;` sat inside a value), so `isPrismaSqlServerUrlAmbiguous` sends it to the fallback label even though it still connects. The earlier label took its parts from the split-on-`;` reading, which put the tail of a braced password into the label (`password={S3c;database=ret;}` → `/ret`).
  - If a parser throws or returns anything unexpected (a non-string field, no host where one is needed), the parts are `undefined`. On top of the driver's reading, two properties of the raw string still make it fall back, because they mean the driver's host or path came out of a password: an `@` or `#` after the host of a URL (a password containing `/`, `?` or `#` is split there), and any `@` in the `sqlserver://` form, which has no userinfo.
- **The builder is shared.** `formatConnectionLabel(engine, parts)` lives in the shared engine kit, `@askdb/introspect/kit` (it started in `@askdb/connectors`, which re-exports it for compatibility); the registry imports it from there. `parseConnectionUrl(input, schemes)` sits next to it for third-party engines whose driver has no parser to reuse; the built-in engines don't use it.
- **The registry builds every label.** `registry.connectionLabel(provider, connection)` is `formatConnectionLabel(provider, adapter.connectionLabelParts?.(connection))`. An unregistered provider, an adapter without the hook, or a hook that returns `undefined` gets `configured <provider> connection`. So every label, built-in or third-party, has passed the allowlist.
- **The allowlist stays as the second line of defense.** Whatever a parser returns, `formatConnectionLabel` still checks each part's characters and its shape: a value that isn't a plain object, or a part that isn't a string, gets the fallback. The registry also catches a throwing `connectionLabelParts` hook and uses the fallback, so an error message that quotes the connection string never becomes the label.
- **No user name.** Labels show host, port and database only. The pre-#189 Studio label (`protocol//host/path`) did not show the user either, and no documented output depends on it.
- **Apps don't parse connection strings or switch on the engine.** Studio (and any other host) asks the registry for the label (ADR 0007); it never inspects the raw string itself.
- **Through connection resolution ([ADR 0008](0008-engine-packages-and-connector-registry.md)).** Once the registry resolves connections, an adapter's `resolveConnection` returns only the connection or an error, and `registry.resolveConnection()` adds `sourceLabel = registry.connectionLabel(provider, connection)`. `defineLiveConnectorProvider` takes the engine's parser as `connectionLabelParts`. Postgres export bundles and Prisma schema paths are `{ file }` parts; with no schema path, Prisma's label is `configured prisma connection`. Studio serves `sourceLabel` as-is and needs no second pass, because every label has already passed the allowlist. An adapter's `error` is still free text and must not echo the connection string.

## Consequences

- Labels look like `postgres://db:5432/app`, `sqlserver://db:1433/app`, `./data/app.db`, or `configured <engine> connection`. The scheme is the engine id, not the input's scheme (`postgresql://` and `mssql://` inputs show `postgres://` and `sqlserver://`).
- Some valid strings get the fallback label: libpq keyword/value DSNs, Postgres multi-host URLs, socket-directory hosts, SQL Server named instances (`host\instance`) and named pipes, `sqlserver://` strings containing `@` (such as `user=admin@server`), any URL whose query contains `@`, and parts the allowlist rejects (a database named `app;`). Supporting one of them means a wider allowlist or a new part, not a new parser.
- The label shows what the driver reads, even where that differs from what the user meant: a repeated ADO.NET key shows its last value, `Password=ab;cd;Database=app` shows no database (the driver reads `cd;Database` as a key), and in Prisma's form any `{…}` value gets the fallback label (the connection reads `password={S3c;database=ret;}` as that password and the database set outside it).
- Each engine's label test has a differential section: for every corpus row that shows a part, the part equals what `pg` (`new pg.Client({ connectionString })`), `mysql2` (`ConnectionConfig.parseUrl`) or `mssql` (`ConnectionPool.parseConnectionString`, or `resolveConnectionInput()`) resolves from the same string.
- Every leak input from the three review rounds, and the ADO.NET spellings from the delta reviews (`;;`, a leading `;`, Unicode whitespace before it), is a row in the engine label tests (`packages/<engine>/src/label.test.ts`, which go through the adapter and the registry). The Studio route test for `GET /api/introspect/status` holds every leak class from each round, including every round-3 input and each ADO.NET spelling class from the delta reviews; `@askdb/config` trims config values, so leading-whitespace inputs reach the route already trimmed. The registry's own test covers an adapter that hands back unsafe parts (a raw or masked URL as the host or file).
- A future contributor must not:
  - reintroduce masking or any denylist of secret key names for labels, including as a "fallback" for inputs the parser doesn't handle (the fallback is `configured <engine> connection`);
  - copy any substring of the input into a label other than a part the parser extracted and `formatConnectionLabel` accepted (no "keep the rest of the string", no query parameters, no user name);
  - add a way for an adapter or engine to supply label text directly (a string-returning hook or export), which makes the allowlist optional again;
  - loosen a part's allowlist (the character classes in `formatConnectionLabel`) without amending this ADR;
  - reimplement a driver's connection-string grammar for a built-in engine. Reuse the driver's parser; if it can't be used (size, Node-only globals), mirror it, say why in the code, and add a differential test against the real parser;
  - parse connection strings in an app. A new format goes into the owning engine package's parser.
