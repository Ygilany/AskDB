# ADR 0012 — AskDB's SQL checks are defense in depth; the database is the security and tenant boundary

## Context

AskDB returns SQL and never executes it (`AGENTS.md`, "Conventions"). Before `ask()` returns, it runs three checks on the model's SQL:

- **Read-only checks** (`validateSelectSql`, `packages/core/src/sql/validate.ts`): the first keyword is `SELECT` or `WITH`, there's one statement, there are no comments, no denylisted keyword appears unquoted, and no denylisted function is called. They run on tokens from a dialect-aware lexer (`packages/core/src/sql/lexer.ts`), not on a parse tree.
- **Tenant check** (`validateTenantGuardrails`, `packages/core/src/sql/tenant-guardrail.ts`): when this decision was proposed, each tenant-scoped table named in the SQL only had to come with its tenant column, join-path columns or `:tenant_*_ids` placeholder somewhere in the statement's code. Since #341 (fixing #315) it runs on the model's SQL before tenant rendering and requires a tenant predicate that filters: the tenant column compared with the placeholder, ANDed into a `WHERE`, inner-join `ON` or `HAVING` clause (since 1.0.0-beta.53, `HAVING` only on a `GROUP BY` key), on scoped and covered root tables. It is still a scan over tokens, not a parse.
- **Sensitive check** (`validateSensitiveReferences`, `packages/core/src/sql/sensitive-guardrail.ts`): sensitive columns and tables named in the SQL or reached through a wildcard are reported.

The recorded design promised more than that:

- `docs/specs/multi-tenancy.md`: "**Strict mode fails closed** — when the guardrail validator cannot prove a query is tenant-safe, it rejects. Prompting alone is not sufficient; SQL validation is the second line of defense." Its feature list described "AST-based Postgres SQL checks" with cross-table scope compatibility.
- `docs/contracts/tenant-policy.md`: "Parser-based validation (primary)" with `node-sql-parser`, and a heuristic fallback that rejects whatever it cannot prove.
- `docs/mission.md`: "non-negotiable tenant scoping in generated and executed queries".

None of the parser work exists. The checks that did ship passed SQL the design said would be rejected: `WHERE tenant_id = … OR 1=1`, and a tenant column that is only selected (#315, since fixed by #341). When this was decided, the tenant check didn't tie a predicate to a particular table reference anywhere in one statement, including its CTEs, derived tables and subqueries (only set-operation branches were checked on their own), so an unfiltered reference passed beside a filtered one: `WITH t AS (SELECT id FROM orders WHERE agency_id = :tenant_agency_ids) SELECT * FROM orders` passed (#399, closed in 1.0.0-beta.53; `docs/contracts/tenant-policy.md`, "Each read, in its own `SELECT`"). The other checks still miss wildcards over tables written in some `FROM` forms (#306–#309), a second `SELECT` in a SQL Server batch, and SQL lexed under a different string setting from the server's, such as MySQL `NO_BACKSLASH_ESCAPES` (#340). The independent review behind PR #184 found the docs site, `SECURITY.md` and the contracts describing the design rather than the code.

AskDB also can't see what decides whether a query is safe once it runs: the executing role and its grants, row-level security, which views and functions have side effects, `search_path`, and the server's lexical settings. The host owns all of these (`docs/mission.md`, "Target audience").

So the question is what AskDB's checks are for, and where the boundary sits.

## Options considered

### A. Make AskDB's checks the security boundary

Build what the original design described: a parser per engine, name resolution, and a proof that every tenant-scoped row source is filtered to the caller's scope (or deterministic predicate rewriting, #235, plus a verification step). Every bypass would then be a vulnerability.

- **For:** it matches the original spec and would let AskDB promise tenant isolation to hosts that don't configure the database.
- **Against:** a boundary has to read SQL exactly as the server does. That means one grammar per engine and version, the server's modes (#340 shows even lexing depends on `sql_mode`), extensions, and user-defined functions and views AskDB never sees. Proving tenant scoping for arbitrary `SELECT`s (CTEs, subqueries, `LATERAL`, set operations, views that join across tenants) is research-grade work. Even then, AskDB would be vouching for SQL whose execution it doesn't control. Rejected for now. The door stays open: see "When to revisit".

### B. Checks are a best-effort lint; the database is the boundary (chosen)

Keep the checks, describe them as heuristic defense in depth that catches common model mistakes, and make the database the security and tenant boundary: a least-privilege, read-only role; row-level security or an equivalent per-tenant mechanism; timeouts and row limits. AskDB fails closed only where it owns the mechanism end to end.

- **For:** it matches the code and what AskDB can know. The checks stay useful: they give fast feedback on the mistakes models actually make (a write statement, a stacked statement, a forgotten tenant filter, a sensitive column), and `strict` mode stops those before the host runs anything.
- **Against:** hosts must configure the database. Hosts that relied on the old wording lose a guarantee they never had.

### C. Drop the SQL checks

Return the model's SQL unchecked and document the database as the only control.

- **For:** the most honest option, and less code to maintain.
- **Against:** it throws away cheap, useful catches, and leaves hosts without mature database controls with nothing at all. Studio's Playground **Execute** also uses `validateSelectSql` as one of its guards (ADR 0009, `apps/studio/src/execute-registry.ts`). Rejected.

## Decision

Option B.

1. **The checks are a lint, not a boundary.** Docs (the docs site, `SECURITY.md`, the package READMEs and descriptions, and `docs/`) call them checks or guardrails and the output "checked SQL". They never call them a security boundary, and never say they guarantee tenant isolation or read-only execution. `SECURITY.md` ("What AskDB guarantees") lists only the mechanical properties the checks do enforce, and says when they hold (a dialect that matches the server's string settings).
2. **The database is the boundary.** The docs lead with the execution-side controls: a least-privilege read-only role, database-level tenant enforcement (Postgres row-level security keyed on a per-request setting, per-tenant views or roles), statement timeouts and row limits (`concepts/safety-boundaries.mdx`, "Run generated SQL safely"; `guides/run-safely-in-prod.mdx`).
3. **AskDB fails closed where it owns the mechanism.** When a tenant policy exists, `ask()` throws without a valid `tenantScope`. It expands a `subtree` scope through the host's resolver or throws. It binds tenant IDs with driver markers (`sql-params`, the default since ADR 0024) or as literals with their quotes doubled (`sql-only`), and throws on a placeholder it can't bind. The read-only checks have always run on the model's SQL, and since #341 the tenant check does too. Neither re-runs on the rendered SQL (only the sensitive-reference report does, and it doesn't check structure), so rendering must never change the statement's structure (the rendering contract ADR 0010 Decision 0 also relies on). The literal form meets that because AskDB inlines a tenant ID only when it is printable ASCII without a backslash, on every dialect, and rejects any other (#371, #360; ADR 0024). Such a literal, with its quotes doubled, reads the same whatever the server's string settings and connection charset are. A custom `AskDialect` must choose its mode with a tenant scope, because AskDB can't know its driver's markers; `ask()` refuses a `DialectSpec` whose `id` isn't built in (#717). In `strict` mode it throws when the tenant lint finds a problem. These are AskDB's guarantees; a passing lint isn't.
4. **Bypass reports are hardening fixes.** SQL that gets past a check is in scope and gets fixed, but at hardening severity. A report is more severe when it defeats something AskDB does own (scope validation, ID binding), or when it causes data loss or a cross-tenant leak in an integration that followed the guidance above (`SECURITY.md`, "Scope"). A report that depends only on a dialect whose string settings don't match the server is triaged as configuration, tracked in #340, unless it defeats ID binding for values AskDB accepts: that is an ID-binding defect (#371).
5. **Tightening the lint doesn't move the boundary.** Better checks are welcome: the tenant check on pre-render forms with predicate rules (#315, done in #341), one decision point for all checks (ADR 0010, #310), deterministic predicate rewriting (#235), a sql_mode-aware MySQL dialect (#340). None of them, on its own, makes the checks a boundary. Relaxing the "not a security boundary" language requires superseding this ADR and updating `docs/contracts/tenant-policy.md` ("Not implemented") in the same PR.

## Consequences

- **Hosts own isolation.** Multi-tenant hosts must enforce tenancy in the database. The multi-tenancy spec lists RLS (or equivalent) as the recommended primary tenant boundary, and the docs site's safety, production and multi-tenancy pages say so.
- **`strict` means something narrower.** It means "throw when the lint finds a problem", not "reject what can't be proven safe". The field name and values don't change (`docs/contracts/tenant-policy.md`).
- **Known gaps are documented, not hidden.** `SECURITY.md` and the docs site list them: the tenant check's limits after #341 (hierarchy roots aren't checked as roots, joined scoped tables aren't checked for a shared scope, and an unqualified `ON` predicate can count for a read its join doesn't see where a name is spelled like a join word; #399, a predicate that covered reads outside its own `SELECT`, and #400, a join on the wrong columns, closed in 1.0.0-beta.53), the `FROM` forms the sensitive check misses (#306–#309), server string settings (#340), SQL Server second statements that start with `FETCH`, `END`, `GET` or `MOVE CONVERSATION` (#327), and Postgres catalog visibility.
- **Mission wording changes.** `docs/mission.md` separates what AskDB guarantees (scope required, prompt instructions, ID binding, the lint rejecting or flagging SQL without a tenant predicate that filters) from what the database enforces. `docs/roadmap.md` follows it: Phase 10 (completed) no longer records tenant-predicate injection or fail-closed validation as delivered, and Phase 13 no longer calls tenant scoping non-negotiable.
- **Later ADRs build on this.** ADR 0010's Consequences ("Not a stronger guarantee") assumes this stance, and this record is its source.
- **Security triage has a stated policy.** Reporters and maintainers can tell a hardening fix from a vulnerability by the rule in Decision 4.

## When to revisit

- A parser-backed analysis that reads SQL the way each supported server does, including its modes, becomes practical (Option A).
- Deterministic tenant predicate rewriting (#235) lands with a verification step strong enough to state as a guarantee for some class of queries.
- AskDB starts executing SQL on a supported path beyond Studio's local Playground, which would put the execution boundary inside AskDB (today a non-goal: `docs/mission.md`).

## Amendments

**2026-11-05 — SQL Server statement boundaries (#327, PR #622):** T-SQL needs no `;` between statements, so the read-only checks passed `SELECT 1 SELECT 2`, and Studio's Execute ran it in a batch. The checks now find a second statement on SQL Server: a top-level `SELECT` that continues nothing, a `(SELECT …` right after a complete value, a label, and control-flow verbs on the denylist. That check reads tokens, so it is only as good as the lexer's agreement with SQL Server about where a token ends. Three review rounds each found a new disagreement: `0x`, `1E` and money literals, Unicode whitespace inside a name, U+FEFF, `$ .5` and `\` as money, and `@` inside a name. The maintainer chose between three options:

- **Copy more of SQL Server's tokenizer.** Each round fixed the cases found and the next round found more. Rejected: it does not converge, and SQL Server's tokenizer is not specified anywhere AskDB can check against.
- **Fix the cases found and rely on a runtime guard.** Studio's single-result-set guard (#373) would catch a second statement in Execute, but nothing would catch one in SQL that `ask()` returns to a host. Rejected as the only defense; #373 stays as a second layer.
- **Accept only plain code on SQL Server (chosen).** Outside strings and quoted names, SQL Server code must be printable ASCII (no `\`) or Unicode letters, marks and digits, with no bare money sign, no number written against a word and no `?` written against a name or number. A `:` written directly against anything but `(`, a comma or an operator counts as a label, whatever the name looks like. Names continue through `@`, `$` and `#`, as SQL Server's identifier rules say. Anything else throws `SQL_MULTI_STATEMENT`. Model-written SQL has none of these (all 160 recorded consumer-lab replies pass), and the rule turns an open-ended list of tokenizer cases into a short list of allowed text.

This keeps the Decision: the checks are still defense in depth, and the database role is still the boundary. A second statement that starts with `FETCH`, or with `END`, `GET` or `MOVE CONVERSATION`, still passes; those words also appear in ordinary queries or as column names.

**2026-11-05 — Tenant IDs leave the SQL text (#231, #360, #371; [ADR 0024](0024-tenant-ids-leave-the-sql-text.md)):** `tenantSqlMode` defaults to `sql-params`, so tenant IDs are driver parameters unless a host asks for `sql-only`. Wherever AskDB still inlines a tenant ID (`sql-only`, in `ask()` or a rebind), it refuses one that isn't printable ASCII or that contains a backslash, on every dialect, so the literal keeps the statement's structure whatever the server's string settings and connection charset. A custom `AskDialect`, or a `DialectSpec` whose `id` isn't built in, must set `tenantSqlMode` with a tenant scope (`TENANT_SQL_MODE_REQUIRED`). Decision 3 says so, and no longer depends on the dialect matching the server for tenant IDs.

**2026-11-05 — Locking reads (#319, PR #649):** the read-only checks passed SQL Server's `WITH (UPDLOCK)`, Postgres `FOR SHARE` and MySQL `LOCK IN SHARE MODE`, and rejected `FOR UPDATE` only because `update` is on the keyword denylist. Run inside a host's transaction, each held locks that other writers waited on. The maintainer chose between two options:

- **Leave locking reads to the host.** Document that the checks don't block them, and tell hosts to use a read-only transaction and a lock timeout. Rejected: SQL Server has no read-only transaction, and a read-only role still takes update locks there.
- **Reject every locking read on every engine (chosen).** The checks throw `SQL_LOCKING_READ` for `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` and `LOCK IN SHARE MODE` at any depth, and on SQL Server for the lock hints `UPDLOCK`, `XLOCK`, `HOLDLOCK`, `PAGLOCK`, `TABLOCK`, `TABLOCKX`, `ROWLOCK`, `SERIALIZABLE` and `REPEATABLEREAD`, as unquoted words anywhere or quoted alone in parentheses after a table name. `NOLOCK` and `READUNCOMMITTED` stay allowed.

SQL Server also reads a quoted hint as the hint when it stands alone in parentheses right after a table name, at any depth and with trailing spaces (`FROM t ([UPDLOCK])`, `t (("UPDLOCK "))`). SQL Server 2022 refused quoted hints in other positions: inside `WITH`, in a list, and after an alias or a function call. Three rules for quoted names were weighed:

- **Pass every quoted name.** Rejected: `FROM t ([UPDLOCK])` takes the lock.
- **Reject every quoted name spelled like a hint.** Rejected: a column named `rowlock` could then never be used, although the prompt lists it quoted (`[rowlock]`) so the model can.
- **Reject a quoted hint name only alone in parentheses right after a name (chosen).** The check reads tokens, so it can't tell a table from a function: `COUNT([rowlock])` is rejected too. A qualified column (`COUNT(t.[rowlock])`) isn't alone in its parentheses, so it passes, and the docs tell users to write it that way.

SQL Server also compares hint names loosely: it ignores some characters (U+FEFF, U+200D, `Ș`) and reads others as ASCII letters (`ʟ` as L, `ɪ` as I). So `WITH (UPDʟOCK)`, `WITH (SERɪALɪZABLE)` and `t ([UPDLOCK` + U+FEFF `])` hold the lock, under a read-only login too. Three options were weighed for these spellings:

- **Match spellings loosely.** Treat each non-ASCII character as up to two ASCII letters, and keep non-ASCII names bare. Rejected: each collation ignores different characters, so, like copying SQL Server's tokenizer for #327, it does not converge.
- **Ship the spelling check and file the rest.** Rejected: on SQL Server the database role can't stop the lock, and the docs would claim that every locking read is rejected.
- **Printable ASCII for unquoted words and lone quoted names (chosen).** On SQL Server, every unquoted word anywhere in the statement, and a quoted name alone in parentheses right after a name, must be printable ASCII; only then is it matched by its spelling. Any other quoted name may use any characters. This narrows the #327 amendment's plain-code rule, which let Unicode letters through in unquoted code.

The escape hatch is quoting: `[Größe]` passes, and so does `COUNT(t.[Größe])` where the name would otherwise stand alone in parentheses. The prompt lists every name that isn't plain ASCII quoted on SQL Server (`promptIdentifierQuoter`, `packages/core/src/sql/prompt-identifiers.ts`), and on an id that is no built-in engine, whose SQL the checks also read the SQL Server way. On both, the prompt also tells the model to quote a non-ASCII alias and to qualify a quoted column that is alone in parentheses (`nonAsciiNameRule`). So model-written SQL passes when the model follows that instruction, except a quoted non-ASCII name that is the only item in a column list (`WITH [集計] ([合計]) AS …`, `AS d ([合計])`) or in a one-value `PIVOT … IN ([東京])` list, which can't be qualified and is still rejected (a column list's name goes inside the query instead); `ask()` doesn't retry, so a schema or a question in a language other than English depends on it. None of the consumer lab's 160 recorded replies has a non-ASCII character outside a string. An id that quotes with a backtick can't use these names yet (#672). The rule fails closed: allowing more spellings later is additive, while tightening one after 1.0 would break hosts.

The hint rules apply per engine. The T-SQL hints are T-SQL syntax, so they are checked on the SQL Server lexer (and for ids that are no built-in engine); the five `FOR …` and `LOCK IN SHARE MODE` forms are checked on every lexer.

This keeps the Decision. The check matches words, not the locks a statement takes: the connection's isolation level still decides what a plain `SELECT` locks (SQL Server `REPEATABLE READ` and `SERIALIZABLE`, MySQL and MariaDB `SERIALIZABLE`), so hosts still set a lock timeout.

**2026-11-06 — Unicode-escaped identifiers (#692, #704):** on Postgres, `U&"set\005fconfig"('app.agency_id', '2', true)` calls `set_config`, but the checks compared the escaped text `set\005fconfig` with the denylist and passed it. Every name on the Postgres and CockroachDB function denylist could be called this way, including with a `UESCAPE` clause, a lower-case `u`, a schema-qualified name or the six-digit `\+XXXXXX` escape (all run on Postgres 17.11). So could a scoped table: `SELECT id FROM U&"\006Frders"` reads `orders`, and the tenant check, which matches names as written, reported nothing, while the query returned both tenants' rows on Postgres 17 (#704). A sensitive column could be hidden the same way. Run against a row-level-security policy keyed on a session setting, `set_config` lets one statement change its own tenant unless the host has revoked it. Two options were weighed:

- **Decode `U&"…"` names before matching.** The later checks would see the real name, and a model could still write a `U&` name. Rejected: the decoder would have to match Postgres's escape rules exactly (`\XXXX`, `\+XXXXXX`, `\\`, the `UESCAPE` character and its limits, UTF-8 only). CockroachDB's support for the syntax is undocumented, so any difference would be a new way around the checks.
- **Reject every `U&"…"` identifier on the Postgres lexer (chosen).** The checks throw `SQL_UNICODE_ESCAPED_IDENTIFIER` for `U&` (either case) written right before a `"…"` name with nothing between, the form Postgres's scanner reads as one identifier. This covers postgres, cockroachdb, and an id that is no built-in engine. `U& "x"` with a space is the `&` operator and passes, and so does a `U&'…'` string, which names nothing. The tenant check refuses the same names, in any position, as `UNICODE_ESCAPED_IDENTIFIER` (`tableId: ""`), whenever the SQL may be read as Postgres, so a custom `AskDialect`, which skips the read-only check, is covered; the policy's `enforcement` decides it. Both checks share one detector (`findUnicodeEscapedIdentifier` in `packages/core/src/sql/lexer.ts`). It also reads the `U` that the lexer glues to a `:` into a `:U` placeholder token, as in the array slice `[1:U&"…"]`, and the function denylist likewise reads a `:name` token followed by `(`, as in `[1:set_config(…)]`: Postgres reads that `:` as the slice separator, and both ran `set_config` on Postgres 17.11 (found in the #705 review). AskDB never asks the model for a `U&` name, since a name that isn't plain ASCII can be written in plain double quotes (`"注文数"`), so no prompt instruction leads the model into the rejection.

This keeps the Decision: revoking `set_config` in the database (`guides/enforce-tenancy-in-the-database.mdx`) is still the boundary, and indirect calls through a view or a user function remain the host's to block.

**2026-11-06 — String continuation after `E'…'` (#703):** Postgres joins two string constants separated by whitespace that contains a newline, and an `E'…'` constant keeps its escape mode into the next one. The lexer read the second constant in plain mode, so where `\'` ends one reading's string, the other's goes on. `SELECT E'a'`, a newline, then `'\'' AS x, o.* FROM orders o --'` reads as three closed strings to AskDB, and as the constant `a'` followed by an unscoped read of `orders` and a comment to Postgres. It passed both the read-only check and the tenant check under the built-in `postgres` dialect. Two options were weighed:

- **Model the continuation.** The lexer would follow Postgres's rule, keeping the escape mode across whitespace and `--` comments with a newline, and the tenant check's own scanner would need the same rule until it is rebuilt on the shared lexer (#342). Rejected: two copies of a scanner rule, and any difference between them and Postgres is a new way past the checks.
- **Refuse it at the boundary (chosen).** On the Postgres lexer (postgres, cockroachdb, an id that is no built-in engine, or no dialect), an `E'…'` string followed by a gap that contains a newline and then a bare `'…'` is refused: `SQL_STRING_CONTINUATION` in the read-only check, which runs it before every other check, and `STRING_CONTINUATION` (`tableId: ""`) in the tenant check, decided by `enforcement`. Both use one detector (`findEscapeStringContinuation` in `packages/core/src/sql/lexer.ts`), and both readings still agree up to that boundary. A comment of any kind in the gap, `/* … */` included, doesn't change the outcome, so the check doesn't depend on reading Postgres's rule exactly. On Postgres, a plain, `U&`, `B` or `X` string continued the same way reads with the same boundaries in both, and passes. CockroachDB differs: it reads a lowercase `b'…'` byte string with backslash escapes, plain or continued, which the checks didn't model. That gap predated #703; the #730 amendment below refuses the form. The lexer also reads `:E'…'` (a `JSON_OBJECT` key's or an array slice's `:`) as `:` and an escape string; it used to read a `:E` placeholder there, which hid the string from the check (found in the #709 review).

A third option came up in the #709 review and is not decided here: **allow only plain forms on the Postgres lexer**, refusing every construct whose boundaries depend on a mode the checks might not share with the server (`E'…'` strings, `U&` names, and so on), as the #327 amendment did with an allowlist of plain code for SQL Server. That would end the per-shape list that #692, #703 and #704 started, but it would also refuse legitimate `E'…'` escapes such as `E'\n'`, so it needs its own decision.

This keeps the Decision: the database role and row-level security are still the boundary.

**2026-11-06 — The sensitive check fails closed on the same forms (#707):** under a custom `AskDialect`, which skips the read-only check, or a direct `validateSensitiveReferences` call, the sensitive check matched `U&"p\0061ssword"` and a column after a continued `E'…'` string as written, and passed them. `SensitiveGuardrailResult` is public, so how to report them was part of the decision:

- **Decode the name and match it.** Rejected for the reason the #692 amendment gives: the decoder would have to match Postgres's escape rules exactly, and any difference would be a new way past the check. It also does nothing for the continued string.
- **Report each form as a new `SensitiveReference` kind.** Rejected: `references` lists the sensitive tables and columns the SQL names, and the check can't tell which column either form reads, so the entry would name nothing.
- **Report each form as a scope issue (chosen).** The check raises `UNICODE_ESCAPED_IDENTIFIER` and `STRING_CONTINUATION` in `unresolvedScope`, so `passed` is `false`, `strict` mode throws `SensitiveReferenceError`, and `warn` reports it, as for `UNTERMINATED_TOKEN`. The tenant check and the sensitive check find both forms through one function, `findPostgresOnlyForms` in `packages/core/src/sql/lexer.ts`, under the same Postgres readings, so all three checks refuse the same two forms.

**2026-11-06 — CockroachDB byte strings (#730):** CockroachDB reads a lowercase `b'…'` byte string with backslash escapes, and keeps them across a continuation (`case 'b'` and `scanString` in its `pkg/sql/scanner/scan.go`). The lexer reads `b'…'` under the Postgres profile without them, as Postgres reads a bit string. So under the `cockroachdb` dialect, `SELECT b'\'' AS x, o.* FROM orders o --'` was one string to the checks and an unscoped read of `orders` to CockroachDB: it passed the read-only check, the tenant check and `ask()` in `strict` mode, with or without a continuation. After a slice's `:` (`[1:b'…']`), which the lexer read as a `:b` placeholder, it passed the read-only check; the tenant check's own scanner caught that form as a missing tenant predicate. Not run on a live CockroachDB: there was no CockroachDB fixture. Two options were weighed:

- **Model the escapes.** A CockroachDB lexer profile would read `b'…'` with backslash escapes, and the tenant check's own scanner (#342) would need the same rule. Rejected for the reason the #703 amendment gives: two copies of a scanner rule, and any difference from the server is a new way past the checks.
- **Refuse it at the boundary (chosen).** On the Postgres lexer, a `b'…'` string (lower-case `b`) that holds a backslash or is continued on a later line is refused, by one detector (`findEscapedByteString` in `packages/core/src/sql/lexer.ts`): `SQL_ESCAPED_BYTE_STRING` in the read-only check, right after `SQL_STRING_CONTINUATION`, `ESCAPED_BYTE_STRING` (`tableId: ""`) in the tenant check, and the scope issue `ESCAPED_BYTE_STRING` in the sensitive check, both through `findPostgresOnlyForms`. Without a backslash or a continuation, both readings end the string at the same quote, and it passes. `B'…'` is a bit string on both engines and passes. The lexer also reads `:b'…'` as `:` and a byte string, as it does `:E'…'`.

**Decided (2026-11-06, with the coordinator): the refusal also runs under `postgres`,** beyond the #730 decision's "under `cockroachdb`". A host may point the `postgres` dialect at CockroachDB, which is wire-compatible. Postgres reads `b'…'` as a bit string, where a backslash is an error, so the cost there is one rare spelling. And refusing is the fail-closed direction, the easy one to undo before 1.0. What's lost: a byte string with escapes on CockroachDB, which a hex string cast to bytes (`'\x00'::bytea`, read the same on both engines) can write instead, and a lowercase bit string continued on a later line on Postgres. The **allow only plain forms** option from the #709 review would cover this form too; it is still open as #721.

**2026-11-06 — A `DialectSpec` keeps a built-in `id` (#717; [ADR 0029](0029-core-owns-built-in-dialect-specs.md)):** `ask()` checked a `DialectSpec` under an `id` that isn't built in under every engine's lexer at once, which rejected valid names (#672) and couldn't read the SQL the way its real engine does. `ask()` now refuses such a spec with `UnknownDialectError`, before the tenant check, retrieval and the model call, so Decision 3's "must choose its mode" applies to a custom `AskDialect` only. A direct `validateSelectSql()`, `validateTenantGuardrails()` or `generateSelectSql()` call still reads such a spec's SQL every engine's way, which fails closed.

**2026-11-06 — Sequence writers (#825):** on MariaDB, `NEXTVAL(s)`, `SETVAL(s, n)` and `NEXT VALUE FOR s` advance or set a sequence from a `SELECT`, and a sequence table is "created as a normal table without rollback", so the change outlives the host's transaction. The `mysql` and `mariadb` dialects passed all three, while the Postgres dialects already listed `nextval` and `setval` as blocked functions. SQL Server advances a sequence with `NEXT VALUE FOR` too.

- **`NEXTVAL` and `SETVAL` (chosen: the MySQL-family `blockedFunctions`).** A data change in the spec that `MARIADB_DIALECT` spreads, matched like every blocked function (`name(`, quoted or qualified). MySQL has no sequences, so no read is lost.
- **`NEXT VALUE FOR` (chosen: one word-sequence check on every lexer, `SQL_FORBIDDEN_FUNCTION`).** It's three words, not a `name(` call, so a function list can't hold it. Keying it to the MySQL and SQL Server lexers was the other option, but Postgres and SQLite don't parse it, so refusing it everywhere costs no read and keeps one rule. It reuses the code for the function it spells; no `SqlValidationRuleCode` member was added.
- **Left allowed:** `PREVIOUS VALUE FOR` and `LASTVAL()`, which return the value the session last drew without changing the sequence.
- **Not covered:** MariaDB's `seq.nextval`, which its docs list under `sql_mode=ORACLE` only. Lexically it's a qualified column named `nextval`, and the checks read MariaDB's default mode, as they read each engine's default string settings.

**2026-11-07 — Four readings that differed from the engine ([GHSA-8pwj-6hfv-5pm4](https://github.com/Ygilany/AskDB/security/advisories/GHSA-8pwj-6hfv-5pm4); #827):** work on #815, which compares the checks' readings across dialects before rebuilding the tenant check on the shared lexer, found four places where the tenant check read SQL differently from the engine, each confirmed on the engines involved (Postgres 17, MySQL 8.4, MariaDB 11.4, SQL Server 2022, SQLite and CockroachDB 26.3). Its scanner opened a dollar-quoted string at any `$$`, inside a name too and under every dialect, though only Postgres and CockroachDB have such strings and every engine reads `x$$y` as one name. It skipped an unquoted name on its own keyword list when it looked for the query blocks that need a table's predicate, though MySQL takes `user`, and Postgres takes `lock`, `qualify` and `by`, as plain table names. It read a MySQL-family `DialectSpec` with `backslashEscapes` unset as escapes off, where the server and the shared lexer read it as on. And it ended a `--` comment only at a line feed, while Postgres and SQL Server also end one at a carriage return; the shared lexer had the opposite difference on MySQL, MariaDB and SQLite, which reached the sensitive check. Each could pass a statement whose tables or predicates the engine read differently, so the maintainer published them as one advisory, fixed in `@askdb/core` 1.0.0-beta.50.

- **Read each the way the engine does (chosen).** Dollar-quoted strings only under the Postgres reading, and never right after a name character; an unset `backslashEscapes` on a MySQL-family spec reads as on; a line comment ends where each engine ends it, through `lineCommentEndsAtLfOnly` on the MySQL and SQLite lexer profiles; and every spelling of a table's name counts when the check looks for the blocks that need its predicate.
- **A `postgres` dialect is read both ways for comment ends,** as the #730 decision reads `b'…'` under it: a host may point `postgres` at CockroachDB, which ends a comment only at a line feed. Reading both is the fail-closed direction.
- **Only `ORDER BY` and `GROUP BY` stay keywords there.** `ORDER` and `GROUP` are reserved on every engine, and the `BY` after them is the keyword. Every other word on the old list is a plain name somewhere. The cost is fail-closed: a scoped table named `limit` or `offset` makes that keyword in a query count as the table, so the query needs its predicate.
- **One loosening, to match the engine.** Under `sqlserver`, a predicate after a comment that a carriage return ends is code, as SQL Server reads it, so it now counts.
- **Kept the tenant check's scanner** rather than rebuild it on the shared lexer, which #815 does, so the fix stayed small enough to ship through the advisory's private fork. A test per engine package runs each shape on the multi-engine fixture and asserts the engine's reading as well as the check's.

**2026-11-07 — A tenant-check cross-tenant leak is a vulnerability (Q33):** GHSA-8pwj-6hfv-5pm4 and GHSA-rmjw-pffc-5hjr were tenant-check misses: the check passed a scoped query that, on the real engine, read every tenant's rows. Decision 4 already lists a cross-tenant leak among the more-severe cases, but its "in an integration that followed the guidance above" clause reads as excluding them, since that guidance is database-side tenant enforcement, under which no leak reaches data. The maintainer settled the triage: **a tenant-check miss that would let a tenant-scoped query read another tenant's rows is a vulnerability and gets a security advisory,** whatever the host's database enforcement, because keeping the model's SQL within the caller's tenant scope is the tenant check's one job. A read-only or sensitive-column check that misses stays a hardening fix (its failure doesn't cross a tenant boundary). This refines Decision 4's severity rule; it does not move the boundary — the database (row-level security, a read-only role) is still the sound boundary, and the tenant check is still a heuristic lint, not a parser. `SECURITY.md`'s "Scope" section states the same rule.

**2026-11-07 — Non-ASCII dollar tags ([GHSA-rmjw-pffc-5hjr](https://github.com/Ygilany/AskDB/security/advisories/GHSA-rmjw-pffc-5hjr)):** the independent review of the GHSA-8pwj documentation found a residual of its first case. The tenant check's scanner matched a dollar tag with ASCII letters only, while Postgres, CockroachDB and the shared lexer's `DOLLAR_TAG` accept non-ASCII letters, so it read `$é$ … $é$` as code where the engine reads a string. Confirmed on Postgres 17 and CockroachDB 26.3. The scanner's tag pattern now matches the shared lexer's, the same choice as the GHSA-8pwj amendment (read it the way the engine does), and the per-engine live test covers it. Under the Q33 rule it got its own advisory, fixed in `@askdb/core` 1.0.0-beta.51.

**2026-11-07 — A `$N` parameter written against a word (#665):** on the Postgres lexer, a `$N` parameter takes in a word written right after its digits, so `$1INTO` and `$1FOR` were one `parameter` token and the read-only check never saw `INTO` (`SELECT … INTO` creates a table) or `FOR` (a locking read). Postgres 17 rejects both as trailing junk after a parameter, on the fixture; Postgres 14 and earlier, and CockroachDB, weren't checked. Two options were weighed:

- **Refuse the shape on the Postgres readings (chosen):** `validateSelectSql` refuses a parameter token that matches `$` digits then a non-digit, under `postgres`, `cockroachdb` and an id that is no built-in engine, after `SQL_NOT_SELECT_OR_WITH` and before the keyword and locking checks. It matches how #327 handles a number written against a word on SQL Server: refuse rather than guess how a server splits it. What's lost: a template that writes a word right after a parameter, which a space fixes.
- **Accept it and rely on the server (rejected):** Postgres 15 and later reject the SQL, but a server that ends the parameter at its last digit would run the keyword, and the checks can't tell which server they're reading for.

The refusal reuses `SQL_FORBIDDEN_KEYWORD`, since the risk is a keyword the check can't see. A rule code of its own would add a member to the public `ValidationErrorCode` union, which is the maintainer's call, so that question is open. MySQL reads `$1abc` as one identifier and SQLite as one named parameter, so their readings are unchanged.

**2026-11-07 — Each read needs its own predicate (#399):** the tenant check looked for a table's predicate per query block, the whole statement or one set-operation branch. So a predicate inside a CTE or derived table covered an unfiltered outer read of the same table (`WITH mine AS (SELECT id FROM orders WHERE agency_id = :tenant_agency_ids) SELECT * FROM orders` read every tenant's orders), and a predicate on one reference covered another, including a mispaired subquery under `multi_root`. The maintainer chose to fix it before 1.0.0-rc.1 as a targeted fix on the tenant check's token reading, rather than wait for the shared analysis (ADR 0010's stage (c)). Each CTE body, derived table, subquery and set-operation branch is its own `SELECT`; a predicate filters the reads of its own `SELECT` (and, through `col IN (…)`, the query around it); a qualified predicate counts only for the read it names (its alias, or its table's name when what follows the table ends it with no alias; a read followed by anything else has no name), names compare as the engine compares them, and a qualifier that names no read the check sees counts for nothing. A read inside a derived table or CTE also counts when every reference to the source is filtered on the column and the source passes it through unrenamed and computes nothing across its rows; anything this can't follow fails closed. How a read is named went through two designs. First, any word after a table was its alias unless it was on a list of words that end a source; rejected, because each engine puts its own clause words there (`TABLESAMPLE`, `NOT INDEXED`, `PARTITION`, `FOR SYSTEM_TIME`) and every review found another. The maintainer chose an allowlist: a read is named only as `table` or `table [AS] alias` followed by what ends the source, and any other form leaves it nameless. A `SELECT` that reads a table more than once must tell its reads apart: each read canonical, at the `SELECT`'s own level, with a distinct plain alias and a predicate qualified with it, or the check refuses. The cost is some correct queries refused, such as a root table joined for a label from a CTE, derived table or scalar subquery whose own `SELECT` doesn't filter it. Which columns a join equates is #400. Under the Q33 rule it gets an advisory once the fixed version ships.

**2026-11-07 — A join counts only on the declared columns (#400):** for a table scoped through a join path, the tenant check only looked for each join column's name somewhere in the statement and a filter on the path's root, so `appointments a JOIN sub_agencies s ON a.client_id = s.id WHERE s.id IN (:tenant_sub_agency_ids)` passed and matched client IDs against sub-agency IDs. A root filtered through another table's column had the same gap: `agencies a, orders o WHERE o.agency_id = :tenant_agency_ids` passed with no join at all. The maintainer chose to fix it before 1.0.0-rc.1, on the #399 scopes rather than with the shared analysis (ADR 0010's stage (c)): stage (c) isn't scheduled before rc.1, and a cross-tenant leak couldn't wait for it (the maintainer's 2026-11-07 decision, recorded on #399 and #400). Within one `SELECT`, a read is in scope when a column the policy says holds an allowed root's IDs is bound to that root's placeholder, directly, through `col = col` conjuncts, or through `col IN (SELECT col …)` over a column bound in the subquery. It is also in scope when a foreign key the policy declares (a join-path step, a hierarchy or root-parent key, or a scope column to its root's ID) links it, on exactly those columns, to a read that is in scope. In a `SELECT` with an outer join, no `ON` filters, seeds, links or hops, since the outer join keeps rows an `ON` never matched: there only `WHERE` and `HAVING` count. The review rounds first narrowed this per join (an outer `ON` linking only across its join), and each round found another way round it, so the maintainer chose the whole-`SELECT` rule; the cost is that a join path written as `LEFT JOIN` with `WHERE` filtering the joined side is refused, where `JOIN` passes. An unqualified column in an `ON` names only that join's operands. A hop is followed only to a table read written after `FROM`, `JOIN` or a `FROM`-list comma, never to a source that borrows a table's name. What it can't follow fails closed: a join through a derived table or CTE, or across a correlated subquery. `col IN (…)` no longer carries a predicate out of its subquery on its own; it links the two `SELECT`s only as a join. Two correct shapes now pass that didn't: a scoped table's tenant column joined to a filtered root's ID, and `col IN (SELECT id FROM <root> WHERE id = :p)`. Under the Q33 rule it gets an advisory once the fixed version ships.

**2026-11-07 — Readings that differed from the engine ([GHSA-9w7p-c3w8-4839](https://github.com/Ygilany/AskDB/security/advisories/GHSA-9w7p-c3w8-4839)):** the independent reviews of #399 found six places where the tenant check read SQL differently from the engine: a SQLite string name in a source's parentheses, a `HAVING` name MySQL resolves to a select-list alias, the `AND` of a `BETWEEN`, `order` or `group` after a spaced dot, a `HAVING` predicate on a column that isn't grouped, and an `OR` after an alias spelled like a clause word. A review of #400 found a seventh: a column name the engine reads as another column counted as the policy's (on Postgres, an unquoted `agencyid` beside a camelCase `"agencyId"`, or a quoted `"OWNER_TYPE"` for a discriminator, also passed through a derived table; on SQL Server under a case-sensitive collation, `agencyid` beside `agencyId`; on SQLite, `égency_id` beside `Égency_id` in a filter). Under the Q33 rule they get one advisory, fixed in 1.0.0-beta.53. Four of the fixes chose between designs:

- **`HAVING` (chosen: count it only on a plain `GROUP BY` key, written the same way, and never on an unqualified name a select-list item is aliased to when read the MySQL way).** Rejected: dropping `HAVING` as a filter clause, which refuses every grouped query filtered there; and modelling each engine's name resolution in `HAVING`, which differs between MySQL's documented order and what it ran on the fixture. What's lost: a `ROLLUP`, `CUBE` or `GROUPING SETS` key, and a key spelled another way, are refused.
- **The `OR` scan (chosen: it ends only at `WHERE`, `HAVING`, `GROUP BY`, `ORDER BY`, a set operation or `JOIN`, never beside a `.`, and at `STRAIGHT_JOIN` only read the MySQL way).** Rejected: a per-engine list of reserved words, which each review would have to extend. What's lost: an `OR` after `QUALIFY` counts as beside the predicate, which no built-in engine has.
- **Column names (chosen: compare a written column with the schema's spelling under a rule per reading: read the Postgres way, a quoted name exactly and an unquoted one with its ASCII letters lower-cased; the SQL Server way, as written, since a database's collation may be case-sensitive and the check can't see it; the MySQL and SQLite ways, with ASCII letters lower-cased).** Rejected: any case everywhere, which counts a column the engine reads as another; exact everywhere, which refuses `AGENCY_ID` on MySQL, where it is always the same column; and a collation input for SQL Server, which needs a new dialect option (a follow-up). What's lost: on a case-insensitive SQL Server database, and under a custom id or none, a tenant column written in another case than the schema is refused; and a policy that spells a column in another case than the schema refuses its unquoted name, though under `strict` the policy must use the schema's spelling anyway.
- **SQLite's string alias after parentheses (chosen: read it as the alias only where the SQL may be read as SQLite).** Under a custom id or none, the other readings see no alias there, so a read filtered only through it is refused, as `orders 'x'` already was.

**2026-11-08 — Names that engines sharing a reading read apart ([GHSA-rx3m-m5jr-pwch](https://github.com/Ygilany/AskDB/security/advisories/GHSA-rx3m-m5jr-pwch)):** the review of GHSA-9w7p-c3w8-4839's fix found three names the check folded differently from an engine: CockroachDB lower-cases every letter of an unquoted name where Postgres folds only ASCII ones, though both are read the Postgres way; Unicode lower-casing merges letters MariaDB keeps apart (U+212A KELVIN SIGN and `k`); and a `HAVING` predicate's `GROUP BY` key was compared with Unicode lower-casing where SQLite folds only ASCII letters. Its private review then found the same class in aliases and qualifiers, in `İ` (U+0130) and the Kelvin sign in table names, in names CockroachDB normalizes to NFC, and a table gate that never saw a table whose name starts or ends with a non-ASCII letter. One function now reads a written name for every engine that shares the reading, and the column, alias, qualifier and CTE-name comparisons use it: a name those engines read apart names nothing (chosen: refuse it, since the check can't tell which engine runs). A name with a letter some engine folds into ASCII (U+0130, U+0131, U+017F, U+212A), or not in NFC as written, is refused unless the schema spells it exactly. Rejected: refusing every non-ASCII name the schema doesn't spell, as SQL Server's reading does, which would refuse every alias a model writes for a question in another language. What's lost: read the Postgres way, an unquoted alias, qualifier or column with an upper-case non-ASCII letter names nothing; read the MySQL way, a non-ASCII letter in another case than the schema doesn't match; and a model's alias holding `ı` (common in Turkish) is refused. Table names are matched in any case with Unicode word edges, and each letter lower-cased on its own, as CockroachDB does, so the gate finds more reads, never fewer.

**2026-11-08 — Names CockroachDB lower-cases into others ([GHSA-p2v7-pv8j-c264](https://github.com/Ygilany/AskDB/security/advisories/GHSA-p2v7-pv8j-c264)):** the review of GHSA-rx3m-m5jr-pwch's fix found three more places where the check lower-cased or normalized a name differently from CockroachDB: a name in NFC only before lower-casing (`J` + U+030C lower-cases to `ǰ`), which reached the table gate, and a word-final capital sigma in the column-list rule and in a derived table's items, which compared names with JavaScript's `toLowerCase` (`ς`) where CockroachDB writes `σ`.
