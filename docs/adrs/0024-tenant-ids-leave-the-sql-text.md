# ADR 0024 — Tenant IDs leave the SQL text by default, and an inlined tenant ID is printable ASCII without a backslash

## Status

Accepted (2026-11-05). The maintainer chose the default (#231, "Decision (2026-11-05)" in its body, option A). The rest was settled on 2026-11-05 when #231, #360 and #371 were planned together; [#371's Step 3 comment](https://github.com/Ygilany/AskDB/issues/371#issuecomment-6666455938) records the business-value decision. Review of the implementation found two more cases: a custom `AskDialect` on SQL Server, and a `¥` under a Japanese connection charset. Decisions 2 and 3 below answer them, under the release's rule that safety wins over convenience. Implemented with `DEFAULT_TENANT_SQL_MODE` and `escapeTenantId` in `packages/core/src/sql/tenant-placeholders.ts`, and the `TENANT_SQL_MODE_REQUIRED` check in `packages/core/src/ask.ts`. Contract: [`tenant-policy.md`](../contracts/tenant-policy.md), "Output modes" and "Enforcement rules". It amends [ADR 0012](0012-sql-checks-are-defense-in-depth.md) (Decision 3) and [ADR 0010](0010-sql-guardrail-decision-point.md) (Decision 0's rendering contract, and, since #664, how a rebind renders tenant IDs in `sql`). Amended 2026-11-05 ([#664](https://github.com/Ygilany/AskDB/issues/664)): a rebind takes `tenantSqlMode` with the same default, so Decision 4 and the rebind consequence changed. Amended 2026-11-06 ([#731](https://github.com/Ygilany/AskDB/issues/731)): `tenantSqlMode` governs `sql` only. `unboundSql` always binds the tenant IDs, in `ask()` as in a rebind (Decision 6).

## Context

ADR 0012 Decision 3 says AskDB owns tenant-ID binding. The checks run on the model's SQL before AskDB renders the tenant IDs (#341), and none of them runs again on the rendered SQL. So rendering must never change the statement's structure.

`ask()` rendered tenant IDs in one of two modes, and `sql-only` was the default:

- **`sql-only`** inlined each ID as a literal, escaped for the dialect: quotes doubled, and backslashes doubled when the dialect's `backslashEscapes` was on. With no dialect at all (a custom `AskDialect`), it only doubled quotes (#360).
- **`sql-params`** replaced each placeholder with the dialect's driver marker and returned the IDs as `tenantParams`. A custom `AskDialect` got Postgres-style `$N` markers.

The literal form keeps the structure only when the server reads the literal's bytes the way the dialect does. AskDB can't see the server's settings, and the CLI, the HTTP API and Studio can't set `backslashEscapes` at all (#340). Three cases break it:

- **String settings.** The independent review of #184 showed it on Postgres 17 with `standard_conforming_strings = off`: the tenant ID `x\' OR 1=1 --` rendered as `'x\'' OR 1=1 --'`, and the scoped query returned every row. A custom `AskDialect` aimed at MySQL had the same break-out under MySQL's default settings (#360).
- **Connection charset.** The review of #643 showed that a tenant ID with no backslash can still break out. `2¥' OR 1=1 -- ` rendered as `'2¥'' OR 1=1 -- '`. A MySQL or MariaDB connection whose charset is `sjis`, `cp932` or `ujis` sends `¥` as byte 0x5C, which the server reads as a backslash, so the query returned every agency's rows.
- **Marker style.** The same review showed that `$1` is not a parameter marker on SQL Server. T-SQL reads it as the money constant 1. With a custom `AskDialect` and the new default, `agency_id = $1` ran and returned agency 1's rows, whatever the scope.

## Decision

1. **The default `tenantSqlMode` is `sql-params`**, exported as `DEFAULT_TENANT_SQL_MODE`. Tenant IDs leave the SQL text: a host runs `sql` with `tenantParams`, or `unboundSql` with `params`.
2. **AskDB picks markers only for an engine it knows.** A built-in dialect id, or a `DialectSpec` under one (such as `{ ...POSTGRES_DIALECT, backslashEscapes: true }`), keeps the `sql-params` default with that engine's markers. AskDB can't know which markers any other dialect's driver takes, so `ask()` with a custom `AskDialect` or a `DialectSpec` whose `id` isn't built in, a tenant policy and no `tenantSqlMode` throws `TenantScopeError` (`TENANT_SQL_MODE_REQUIRED`) before any retrieval or model call. The host chooses `"sql-params"` (`$N` markers) or `"sql-only"`. The rule allows known engines rather than listing the shapes that need a mode: a list missed first a custom `AskDialect`, then a `DialectSpec` under another `id`, and each got `$N` by default. Only own keys of `BUILT_IN_DIALECTS` count as built-in ids, so a name such as `"constructor"` doesn't. A `tenantSqlMode` that is neither of the two throws the same reason on every dialect, in `ask()` and `resolveTenantSql()`, rather than be read as one of them. Amended 2026-11-06 (#717, [ADR 0029](0029-core-owns-built-in-dialect-specs.md)): `ask()` now refuses a `DialectSpec` whose `id` isn't built in, with `UnknownDialectError`, before this check, so only a custom `AskDialect` reaches `TENANT_SQL_MODE_REQUIRED`.
3. **Wherever AskDB inlines a tenant ID, the ID must be printable ASCII (U+0020 to U+007E) without a backslash.** Any other ID throws `TenantScopeError` (`UNESCAPABLE_TENANT_ID`), on every dialect and with no dialect. The quotes are doubled and nothing else is escaped. Such a literal reads the same whether or not the server treats backslash as an escape, and goes out as the same bytes in every ASCII-compatible connection charset. So an inlined tenant ID keeps the statement's structure whatever the server's settings are.
4. **Rebind follows the same default.** `bindPreparedQuery()` and `askdb.bind()` take `tenantSqlMode`, default `"sql-params"`: the rebound `sql` keeps the business values inlined and holds tenant markers, run with the new `BoundQuery.tenantParams`. `"sql-only"` inlines the IDs and follows rule 3, so it throws `UNESCAPABLE_TENANT_ID` for such an ID. `unboundSql` + `params` don't change (#664). A template's dialect id is always a built-in one, so the rebind always knows its markers and Decision 2 never applies to it.
5. **Business values keep the dialect-match condition.** The values `bindPreparedQuery()` inlines into its `sql` are still escaped for the dialect, and the docs say that a value with a backslash can escape its literal when the dialect doesn't match the server (#340). The docs point hosts at `unboundSql` with `params` for values their users type.
6. **`tenantSqlMode` governs `sql` only** (amended 2026-11-06, #731). `unboundSql` always binds the tenant IDs as driver markers, with the IDs in `params`, in `ask()` and in a rebind. Before, `ask()` under `"sql-only"` inlined them into `unboundSql` while the rebind bound them, so one mode had two contracts. `"sql-only"` exists for a tool that takes one SQL string, which is `sql`. A caller that runs `unboundSql` already binds `params`, so inlining there gained nothing and put the IDs back in the SQL text. Rejected: inlining in the rebind too (it moves IDs into the text a caller binds anyway), and keeping both shapes (one mode, two contracts).

## Options considered

- **Keep `sql-only` as the default and only harden it** (option B on #231). Rejected. The default path would still put tenant IDs into SQL text that no check reads. For values that define a security boundary, binding should be the default and inlining the opt-in.
- **Give a custom `AskDialect` `$N` markers by default.** Rejected: on SQL Server the query runs and filters to the wrong tenant, even when the host passes `tenantParams`.
- **Keep `sql-only` as the default for a custom `AskDialect` only.** Rejected. Two defaults are two rules to document, and inlining by default is what this ADR moves away from.
- **Escape a backslash in a form that every server setting reads the same way.** On Postgres, an `E'…'` literal always reads backslash escapes. MySQL and MariaDB have no such form: a hex literal (`X'…'`) or `CHAR(…)` changes the value's type and collation. Rejected: it needs a literal form for each engine and still has no answer for MySQL.
- **Refuse only the characters known to map to 0x5C** (`¥` U+00A5, `₩` U+20A9). Rejected. Non-ASCII IDs would keep working, but safety would depend on knowing every connection charset's mapping. The allowlist doesn't.
- **Keep the backslash rule and document "UTF-8 connections only".** Rejected. It makes ADR 0012 Decision 3's guarantee conditional again.
- **Detect the server's string settings and charset.** Rejected here. Core does no database I/O, and a detected setting can't cover every connection a host opens. #340 tracks letting hosts configure the dialect.
- **Make `BoundQuery.sql` optional, and leave it out for an ID that can't be inlined.** Rejected in #664: the result's shape would depend on the data, so code tested with ASCII IDs would fail in production on an ID such as `agência`. An opt-in option that leaves `sql` out was rejected too: it keeps the refusal as the default.
- **Refuse backslashes in business values too** (#371, step 3). Rejected. It refuses legitimate values such as `C:\tmp` or `50\%`, and loses the safe `unboundSql` + `params` pair with them. The literals the model writes into `ask()`'s `sql` carry the same dialect-match condition (#340), so the docs keep that condition either way.

## Consequences

- **Breaking for hosts that pass `tenantScope` without `tenantSqlMode`.** With a built-in dialect, `result.sql` now holds driver markers. Running it without `tenantParams` fails at the driver (Postgres: "there is no parameter $1"; better-sqlite3: "Too few parameter values"; MySQL: a syntax error; SQL Server: "Must declare the scalar variable"). It never returns other tenants' rows. The fix: pass `tenantParams`, run `unboundSql` with `params`, or set `tenantSqlMode: "sql-only"`.
- **Breaking for hosts with a custom `AskDialect`, or a `DialectSpec` whose `id` isn't built in, and a tenant policy.** They must set `tenantSqlMode`. An explicit `"sql-params"` gives `$N` markers, which SQL Server reads as money constants, so a SQL Server host sets `"sql-only"` or rewrites the markers. `resolveTenantSql()` called without a dialect still renders `$N`, as documented. A later, additive change could let an `AskDialect` declare its marker style. Since #717 (2026-11-06), such a `DialectSpec` gets `UnknownDialectError` from `ask()` instead: it keeps a built-in `id`, or the engine implements `AskDialect`.
- **A tenant ID that isn't printable ASCII, or that contains a backslash, works only in `sql-params` mode**, in `ask()` and in a rebind. Both refuse it in `sql-only`. A tenant-scoped rebind's `sql` needs `tenantParams`; without them the driver errors, and never returns other tenants' rows. A control character in a tenant ID now throws `TenantScopeError` (`UNESCAPABLE_TENANT_ID`) rather than `QueryParameterError`.
- **Driver-side interpolation is outside this guarantee.** A driver that interpolates parameters into the SQL text on the client, such as mysql2's `query()` with params, re-escapes them itself; under `sjis`, `cp932` or `ujis` a `¥` still goes out as 0x5C. The docs tell hosts to use `execute()` (server-side prepared statements) or a `utf8mb4` connection.
- **`TenantSqlDialect.backslashEscapes` now steers only how tenant substitution lexes the SQL**, not how it escapes tenant IDs. The internal `escapeSqlLiteralLegacy` is deleted.
- **Hosts that report or forward the mode** (Studio today, the HTTP API in #343) import `DEFAULT_TENANT_SQL_MODE` rather than hard-code a string.
