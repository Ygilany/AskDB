Plan 033: originally written 2026-07-19 at commit `9f5e600`; **rewritten 2026-08-04 at commit `c81bb4e`** after a maintainer design review. The first version tried to make queries reusable *without* a model call — a prepared-query artifact, schema/policy/context fingerprints, tenant access-shape comparison, and a `client.bind()` rebind path. That premise was wrong: every AskDB request always invokes the model. The rewrite keeps the input unchanged (the question still goes to the model with its values inline) and changes only the *output* — the model returns the bound SQL exactly as today, plus the same statement in unbound form and a JSON manifest of the values it parameterized. `ask()` therefore returns today's `sql` verbatim alongside `unboundSql`, `params`, and per-parameter metadata a host can render a dynamic form from; if the extra blocks are missing or inconsistent they are dropped, so the feature can default to on without any caller being able to regress. `bindPreparedQuery()` survives as a pure local utility that substitutes escaped literals before execution, sharing one tokenizer, scanner, and escaper with the tenant placeholder path. That substitution model makes dialect-aware literal escaping security-critical, so the MySQL/MariaDB backslash weakness in `escapeSqlLiteral` moves **into** this plan's scope. Fingerprints, rebind policing, host-declared `{{token}}` syntax, and `@askdb/client` source changes stay out of scope.

Plans 044–052: generated on 2026-08-05 at commit `595182d` (immediately after PR #168, reusable query parameter binding, merged) via `improve plan`, from a review of the **multi-tenancy system** — the policy model, the enforcement path, and the Studio authoring experience. Every finding was verified against post-merge code before the plan was written.

The cycle has four groups. **Correctness in the tenant path** (046 marker/fail-closed/operator bugs, 047 the unimplemented `subtree` descendant expansion). **Honesty about what the system guarantees** (045 the guardrail's misleading self-description plus a cheap lexer-based hardening, 048 removal of the dead `tenantFilters` field, 049 documenting database-level enforcement). **Where enforcement should actually live** (050, a design spike — not a build plan). **Studio** (044 the untypechecked web UI and the crash it hid, 051 authoring, 052 comprehension).

Two findings are worth calling out because they are capability gaps rather than defects. `subtree` access — the access kind for hierarchical tenancy, and the motivating case for the whole hierarchy half of the policy model — never expands descendants; `policy.hierarchy` is collected, validated for cycles, serialized, and then read by no query-time code. And `TenantScope.tenantFilters` is declared, zod-validated, given a full Studio editor, and documented, while nothing in `packages/core` reads it.

PR #168 changed what is affordable here. Its `tokenizeSqlSpans` lexer (`packages/core/src/sql/bind.ts`) is the primitive the guardrail was missing, which makes 045's hardening cheap and 050's spike worth running. Its `markerStyleForDialect` also made 046 more urgent: business parameters now bind with dialect-correct markers while the tenant path still hardcodes Postgres `$N`, so a single statement on MySQL or SQL Server can now contain both `?` and `$1`.

- **034 was rewritten on 2026-08-05** and dropped from L to S. The original proposed dual-publishing a CommonJS build via two `tsc` passes. - **036's dependency note was corrected in the same pass.** It previously claimed extra value once 034 landed, on the theory that dual-publishing creates duplicate ESM/CJS module instances. Verified false: `require()` and `import()` of the same package return the *same* namespace object. 036 stands on its independent justification — removing the module-handle threading a lazy-loading consumer needs, and surviving two *versions* of the package in one tree.
- **036, 037, 038, 039, 040, 043 have no file overlap with each other** and can land in any order or in parallel. They are the low-risk group; if capacity is limited, these are the cheapest wins.

## Findings considered and rejected — 044–052 cycle

- **Making the tenant guardrail sound (clause-position awareness, `OR`/negation analysis, subquery scoping)**: not attempted as a plan. #168 shipped a *lexer*, not a parser — it answers "is this offset inside a string literal?", not "is this identifier in a `WHERE` clause?". 045 fixes only the false-positive class the lexer can fix and reclassifies the check as an advisory lint; whether to build real rewriting is 050's question. Do not re-audit the guardrail's remaining unsoundness as a bug — it is documented and pinned by tests in 045 Step 4 case 5.
- **Implementing `tenantFilters` instead of removing it**: rejected. No specification exists for what applying host-supplied filter conditions to model-generated SQL should mean, and the pattern (hand AskDB conditions and trust it to apply them faithfully) is the same prompt-and-hope model 045/049/050 are moving away from. A host that can pre-resolve conditions can apply them itself or express them as an RLS policy.
- **Adding a graph-layout dependency for the Studio hierarchy view**: rejected in 052. Tenant hierarchies are shallow; a nested list with CSS indentation is more accessible than an SVG graph and adds no dependency.
- **Generating RLS DDL from the tenant policy**: out of scope for 049 and remains a stated non-goal in `docs/specs/multi-tenancy.md`. 049 teaches the pattern and inverts the framing (RLS is the enforcement layer, AskDB's predicates are defense in depth) without automating policy generation.
