<p class="doc-eyebrow">The contract</p>

<p class="doc-lede">The schema artifact is the folder of files your team authors, reviews, and checks into version control. It's the model's only source of knowledge about your database, and it's yours to evolve like any other piece of source code.</p>

This page explains how the artifact is put together and why. The [Schema artifact format](/reference/schema-artifact-format/) lists every file and field.

## Two layers

The artifact keeps two kinds of knowledge apart, because they come from different places.

The **physical layer** is `schema.json`: the tables, columns, types, keys and relationships. It comes from the database. `askdb introspect` reads the database and writes it, and writes it again each time you run it. You rarely edit it by hand.

The **enrichment layer** is markdown: a file for each table you describe, plus optional business concepts and a tenant policy. It comes from people: what a table means, what your users call it, and how they phrase questions about it. Introspection never touches it.

The split lets each layer change at its own pace. Re-introspection can't erase what your team wrote. And a diff of `schema.json` shows what changed in the database, and nothing else.

## Stable IDs join the layers

The markdown doesn't repeat table or column names. It refers to them by ID, such as `table:public.orders` or `table:public.orders#status`.

AskDB builds each ID from the names in the database, so the same database always gives the same IDs. That is what lets your markdown keep matching after every re-introspection.

The cost is renames. A renamed table or column gets a new ID, and AskDB can't tell a rename from a removal plus an addition. The markdown that named the old ID stops applying, and the loader reports it as a warning instead of guessing. [Author your schema](/guides/author-your-schema/#re-introspecting) has the steps to follow after a rename.

## Sensitivity only escalates

A table or column can be marked sensitive in `schema.json` or in its markdown. The two places aren't equal. Markdown can mark something sensitive, but it can't un-mark it. Only `schema.json` can.

This is deliberate. Markdown is the layer many people edit, often in Studio, so a mistake there is likely. A `sensitive: false` in markdown can't expose a column that `schema.json` marks sensitive. Un-marking takes a change to `schema.json`, which is a small, visible diff for a reviewer, and re-introspection keeps it.

## What the model actually receives

The model never sees the directory you author. At generation time AskDB merges the physical layer and the enrichment into a single compact, model-facing text — a DDL-style description where each table is rendered as a block and your enrichment is folded in as inline comments (descriptions, aliases, and "common query language" attached to the table and columns they describe). Sensitive fields are tagged or withheld here according to your mode.

So the two layers you maintain separately on disk — `schema.json` for structure, markdown for meaning — are assembled into one annotated schema description the model reads. The prompt carries that repackaged text and the question, never your rows, your credentials, or your query results. When your schema has a tenant policy, the prompt also carries a tenant policy block and the `context` from your `tenantScope`, as advisory text. The block names tenant IDs only by placeholder, such as `:tenant_agency_ids`, never by value. See [Privacy model](/concepts/privacy-model/) for the full list of what reaches the model. When a schema is too large to send whole, the same rendering is applied to only the relevant slice retrieved for the question (see [RAG for large schemas](/guides/rag-for-large-schemas/)).

## Directory or bundle

You author the artifact as a folder, because a folder of small files diffs and reviews well. To ship it to a service, an agent or a build, `askdb bundle` packs the folder into one JSON file. It refuses a folder the loader refuses, and loading the bundle gives the same result as loading the folder.

The loader reads the artifact's file names exactly, and refuses one in the wrong case, such as `Tenant-Policy.md`, on every OS. On Linux, where file names are case-sensitive, it would otherwise skip that file without a word, and a skipped `tenant-policy.md` turns tenant enforcement off. On macOS and Windows the same folder would load. Refusing everywhere makes the mistake fail on a laptop before it can fail open in production.

A schema directory or bundle (`schema.json`, `tables/*.md`, `concepts.md`, `tenant-policy.md`, or an inline `schemaJson`) is input AskDB parses and puts into the model prompt, so whoever can write it can change what AskDB loads and what the model sees. Before `@askdb/core` 1.0.0-beta.48, a crafted front-matter block in a schema markdown file could also run code in the process that loaded it ([GHSA-qqx9-qpw2-wcqg](https://github.com/Ygilany/AskDB/security/advisories/GHSA-qqx9-qpw2-wcqg)); since beta.48, schema front-matter must be YAML. Load schema files only from sources you trust.

## Why a file, not a prompt template

The schema artifact is a deliberate choice. The alternative, a prompt template buried in application code, is opaque, hard to review, and tangled with the rest of your codebase.

A versionable file means:

- Your data team can review changes in a PR like any other code.
- You can see, line by line, what context the model receives.
- Enrichment evolves at its own pace, decoupled from app deploys.
- The same artifact powers the CLI, the library, and the HTTP API: one source of truth.
