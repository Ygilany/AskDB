<p class="doc-eyebrow">The contract</p>

<p class="doc-lede">The schema artifact is the single file (or directory) your team authors, reviews, and checks into version control. It's the context the model uses to generate SQL — and it's yours to evolve like any other piece of source code.</p>

## On disk

A schema artifact is a folder with one required file and a few optional companions:

```
my-app.schema/
  schema.json           # required — physical structure
  tables/
    users.md            # optional — per-table descriptions, aliases, concepts
    orders.md
  concepts.md           # optional — cross-table business concepts
  tenant-policy.md      # optional — multi-tenant scoping rules
  schema.lock.json      # optional — written by @askdb/rag indexing (embedder, store, chunk hashes)
```

Only `schema.json` is required. An artifact with no markdown is valid; you can add enrichment incrementally.

Table markdown files are matched to tables by the `id` in their front-matter, not by filename. When AskDB creates one for you it uses `<table>.md`. It uses `<schema>.<table>.md` instead if two tables share a name (for example `public.orders` and `archive.orders`), or if `tables/` already holds a file with the same name, such as `Orders.md`. Names that a case-insensitive file system stores as one file count as the same. That covers case, Unicode normalization and case folding, such as `ß` and `SS`. The rule doesn't depend on the operating system, so the same schema and `tables/` contents get the same default names on every OS. Very long names are shortened and end in a short hash.

AskDB looks up the names in this layout exactly. A name that matches one only when case is ignored, such as `Tenant-Policy.md`, `Tables/` or `tables/orders.MD`, makes [`loadSchema()`](/reference/core-api/#loadschemapath) throw `SchemaParseError` on every OS. On Linux, where file names are case-sensitive, AskDB would otherwise skip that file, and a skipped `tenant-policy.md` turns tenant enforcement off.

When you need one portable file (for distributing to a service, an agent, or a build artifact), bundle the directory:

```bash
npx askdb bundle my-app.schema --out my-app.schema.bundle.json
```

The bundle carries `schema.json`, every `tables/*.md`, `concepts.md`, and `tenant-policy.md`, so loading it gives the same result as loading the directory. `askdb bundle` refuses every directory that `loadSchema()` refuses: a name in the wrong case, or a file that exists but can't be read. It fails instead of leaving the file out.

## The physical layer

`schema.json` holds the structural facts: stable IDs, physical table and column names, types, nullability, primary keys, relationships, and sensitivity flags. Here it is for a Postgres database with `orders` and `users` tables, with `users.email` marked sensitive:

```json
{
  "version": 2,
  "schemaId": "my-app",
  "provider": "postgres",
  "tables": [
    {
      "id": "table:public.orders",
      "name": "orders",
      "schema": "public",
      "sensitive": false,
      "columns": [
        {
          "id": "table:public.orders#id",
          "name": "id",
          "type": "uuid",
          "nullable": false,
          "primaryKey": true,
          "sensitive": false
        },
        {
          "id": "table:public.orders#user_id",
          "name": "user_id",
          "type": "uuid",
          "nullable": false,
          "sensitive": false
        },
        {
          "id": "table:public.orders#status",
          "name": "status",
          "type": "text",
          "nullable": false,
          "sensitive": false
        }
      ],
      "relationships": [
        {
          "from": "table:public.orders#user_id",
          "to": "table:public.users#id"
        }
      ]
    },
    {
      "id": "table:public.users",
      "name": "users",
      "schema": "public",
      "sensitive": false,
      "columns": [
        {
          "id": "table:public.users#id",
          "name": "id",
          "type": "uuid",
          "nullable": false,
          "primaryKey": true,
          "sensitive": false
        },
        {
          "id": "table:public.users#email",
          "name": "email",
          "type": "text",
          "nullable": false,
          "sensitive": true
        }
      ]
    }
  ]
}
```

Each table records its database namespace in `schema`, and every table needs one. `provider` records the engine that introspection read. When your config doesn't set `dialect`, AskDB's config-driven entry points pick the SQL dialect from `provider` (see [Configuration](/reference/config/)).

`askdb introspect` writes `schema.json`, and you can also edit it by hand, for example to mark a column sensitive or to un-mark one. When you introspect again into the same directory, AskDB rebuilds `schema.json` from the database and keeps only the `sensitive` flags from the existing file, matched by table and column ID. Every other hand edit to `schema.json` is overwritten.

## The enrichment layer

Per-table markdown adds the meaning the model needs to generate good SQL: descriptions, aliases, common query language, example questions, and column-level notes.

```markdown
---
id: table:public.orders
name: orders
schemaId: my-app
aliases: [purchases, sales]
columns:
  - id: table:public.orders#status
    enum: [pending, paid, shipped, cancelled]
    description: Order lifecycle state.
---

# Table: orders

Customer purchase orders. One row per submitted order.

## Common query language

- "sales" usually means paid orders
- "active customers" excludes status = cancelled
```

This layer survives re-introspection. When your database changes, `askdb introspect` updates `schema.json` and leaves your markdown intact.

Front-matter can also mark a table or column sensitive. This is what Studio's Sensitivity tab writes: a table-level `sensitive: true`, or `sensitive: true` on a `columns` entry. Sensitivity is **escalate-only**. Front-matter can make a table or column sensitive on top of `schema.json`, but a front-matter `sensitive: false` never un-marks something `schema.json` marks sensitive. AskDB ignores it and reports a `sensitivity_downgrade_ignored` warning. A sensitive table makes all of its columns sensitive. To un-mark a column, edit `schema.json`. If a `columns` entry names a column from a different table, its `sensitive: true` still applies to that column, and AskDB reports a `misplaced_column_id` warning so you can move the entry to the right file. If a column is listed more than once, it is sensitive when any of its entries says `sensitive: true`. A repeat within one file is reported as a `duplicate_column_id` warning, and only the first entry's description, aliases, and enum are used. Each table gets exactly one markdown file: two files with the same front-matter `id` are an error.

## What the model actually receives

The model never sees the directory you author. At generation time AskDB merges the physical layer and the enrichment into a single compact, model-facing text — a DDL-style description where each table is rendered as a block and your enrichment is folded in as inline comments (descriptions, aliases, and "common query language" attached to the table and columns they describe). Sensitive fields are tagged or withheld here according to your mode.

So the two layers you maintain separately on disk — `schema.json` for structure, markdown for meaning — are assembled into one annotated schema description the model reads. That repackaged text, plus the question, is the entire prompt: never your rows, your credentials, or your query results. When a schema is too large to send whole, the same rendering is applied to only the relevant slice retrieved for the question (see [RAG for large schemas](/guides/rag-for-large-schemas/)).

## Stable IDs

Every table, column, and concept has a stable ID. The markdown files refer to tables and columns only by ID, never by name. Table and column IDs come from the names in the database, so introspecting an unchanged database again gives the same IDs.

| ID | Refers to |
| --- | --- |
| `table:public.users` | A table (always schema-qualified; engines without schemas use `public`) |
| `table:public.users#email` | A column |
| `concept:customer` | A cross-table business concept |

Renaming a table or column in the database changes its ID. AskDB treats a rename as a removal plus an addition, and doesn't map the old ID to the new one. Renaming a table changes the ID of every column in it too.

<Aside type="caution" title="A rename drops sensitivity marks">
After a rename, a `tables/*.md` entry that names the old ID stops applying: `loadSchema()` ignores it and reports an `orphaned_table_id` or `orphaned_column_id` warning. A `sensitive: true` on the old ID doesn't carry over either, from `schema.json` or from front-matter. Move your markdown entries and sensitivity marks to the new ID before you ship the schema.
</Aside>

## Why this matters

The schema artifact is a deliberate choice. The alternative — a prompt template buried in application code — is opaque, hard to review, and tangled with the rest of your codebase.

A versionable file means:

- Your data team can review changes in a PR like any other code.
- You can see, line by line, what context the model receives.
- Enrichment evolves at its own pace, decoupled from app deploys.
- The same artifact powers the CLI, the library, and the HTTP API — one source of truth.
