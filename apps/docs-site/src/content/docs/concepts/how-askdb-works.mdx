<p class="doc-eyebrow">The pipeline</p>

<p class="doc-lede">AskDB is a function that turns a question and a schema artifact into checked SQL. Everything else — execution, approval, audit — happens in your application, not in AskDB.</p>

## The five steps

When you call `ask()` (or the equivalent CLI / HTTP surface), AskDB runs these steps in order:

1. **Load the schema artifact.** The CLI, the HTTP API and `@askdb/client` load it from a directory, a bundle file or a `schema.json`. When you call `ask()` directly, you pass an artifact you loaded with `loadSchema()`.
2. **Retrieve relevant chunks (optional).** When you pass a retriever, AskDB pulls only the slice of the artifact that's relevant to the question, using `@askdb/rag`. If you also pass the artifact's chunk count and it's at or below `retrievalThresholdChunks` (30 by default), AskDB uses the whole artifact instead.
3. **Build the prompt.** The question, the schema text and the selected SQL dialect get assembled into the context the model sees, plus the tenant policy and the scope's advisory context when you use one. [Privacy model](/concepts/privacy-model/#what-the-model-sees) lists everything it holds.
4. **Generate.** AskDB calls the model you supplied — any provider compatible with the [Vercel AI SDK](/guides/bring-your-own-model/) — and the model returns SQL. AskDB does not host inference; your key, your billing.
5. **Check.** AskDB runs its SQL checks on the returned SQL. The read-only check makes sure it's one statement that only reads, and refuses it if not. When your artifact has a tenant policy, the tenant check makes sure each tenant-scoped table is filtered by tenant. When it marks tables or columns `sensitive`, the sensitive check reports SQL that reads one. Depending on their mode, those two refuse the SQL or return it with warnings. The checks catch common model mistakes but aren't a security boundary. [SQL checks](/reference/sql-checks/) gives each check's rules, and [Safety boundaries](/concepts/safety-boundaries/) explains what they miss.

`ask()` returns the checked SQL, the values to bind when the SQL has parameters, and what the checks found. [`AskPipelineResult`](/reference/core-api/ask/#result--askpipelineresult) lists every field. What happens next is your call.

## The runtime boundary

<img src={runtimeBoundaryUrl} alt="Flow from question and schema through ask() to checked SQL, with execution owned by your application" class="doc-diagram" />

AskDB stops at checked SQL. Your application — the code that imports `@askdb/core` or calls the HTTP API — owns everything past that:

- The database driver and connection pool.
- Read-only roles, and tenant isolation such as Postgres row-level security ([Enforce tenancy in the database](/guides/enforce-tenancy-in-the-database/)).
- Query timeouts, row limits, and result pagination. The SQL comes back without a row limit; [Cap the rows a query returns](/guides/cap-the-rows-a-query-returns/) shows how to cap it on each engine.
- Whether to show the SQL to the user, log it, queue it for review, or run it immediately.
- Audit logging and observability.

This split is intentional. AskDB is a code-generation step, not a runtime, so it slots into existing services and your existing security model: the database role you already trust to run queries is the one that bounds what generated SQL can do.

## Where the model lives

You bring the model. AskDB calls whatever provider you wire in — typically through the Vercel AI SDK — using your API key. Requests go straight from your environment to the provider. AskDB does not proxy, log, or cache them.

The same model never sees your database connection, your credentials, or the rows your application returns. See [Privacy model](/concepts/privacy-model/) for the precise list of what crosses the boundary.
