<p class="doc-eyebrow">Adapting to your stack</p>

<p class="doc-lede">Two knobs you tune per deployment: the <strong>dialect</strong> (which SQL flavor AskDB generates and checks) and the <strong>mode</strong> (what may enter the model's context beyond the schema artifact and the question).</p>

## Dialects

A dialect is a `DialectSpec` built into `@askdb/core`. Six ship with the core package: `postgres`, `cockroachdb`, `mysql`, `mariadb`, `sqlite` and `sqlserver`. Core owns them so that generating SQL needs no engine package and no database driver. A dialect tells the pipeline how to:

- Brief the model on the engine's SQL: a short paragraph in the prompt on functions, casts and matching (for example `ILIKE` and `::type` on Postgres, `TOP` on SQL Server).
- Quote table and column names in the prompt the way the engine does, including names that are reserved words.
- Bind parameters with the engine's driver markers (`$1` on Postgres, `?` on MySQL and SQLite, `@p1` on SQL Server).
- Check that the SQL is a read-only `SELECT` under the engine's rules: its extra forbidden keywords, blocked functions and string escaping.

Introspection is a separate job, and it's the one that needs an engine package and a driver: `@askdb/postgres`, `@askdb/mysql` (MySQL and MariaDB), `@askdb/sqlite` and `@askdb/sqlserver`. Each also re-exports its engine's dialect constant, but `ask()` needs only the dialect id. CockroachDB has a dialect and no engine package, and it's outside the 1.0 support claim: AskDB's end-to-end tests don't cover it.

The CLI, Studio and the HTTP API pick the dialect for the schema you configure: the `dialect` in `askdb.config.ts`, else the engine the schema artifact records, else `postgres`. For an engine AskDB ships no dialect for, they refuse rather than guess: see [`dialect`](/reference/config/#dialect). A server that reads strings differently from the engine's default needs a dialect built to match: see [Match your server's string settings](/guides/match-server-string-settings/). Switching engines is mostly a package swap, and [Switch engines](/guides/switch-engines/) has the checklist.

## Modes

A **mode** declares the trust boundary AskDB enforces for a run: what's allowed to enter model context beyond the schema artifact and the natural-language question. Today there are two values.

- **`schema_only`**, the default. AskDB grounds generation in the schema artifact and returns SQL only. The model never sees rows, credentials or query results. This is the right mode for almost every production deployment.
- **`bounded_results`.** Today it produces the exact same SQL as `schema_only`, and every AskDB surface still returns SQL only. The value is reserved for a later step, in which a host could summarize bounded tabular results back through the model. Until that ships, choosing it changes nothing you can observe. The contracts that step must honor are in [`docs/contracts/modes-v1.md` on GitHub](https://github.com/Ygilany/AskDB/blob/main/docs/contracts/modes-v1.md).

The operator owns the mode, not the caller. The config's `modes.askdbMode` is the loosest mode any run gets, on the CLI, `@askdb/client` and the HTTP API. A run can ask for a stricter mode, but not a looser one: asking for `bounded_results` under a `schema_only` config runs `schema_only`, with no error. `modes.omitSensitiveFromPrompt` works the same way: a run can turn omission on, never off. [`modes`](/reference/config/#modes-and-host) in the configuration reference has the keys, and [`askdb ask`](/reference/cli/#askdb-ask) the `--mode` flag.

## Sensitive fields

Marking a table or column `sensitive` in the schema artifact works alongside the mode. By default the prompt lists a sensitive column with a tag, so the model handles it with care. With `modes.omitSensitiveFromPrompt`, the prompt leaves it out. The [privacy model](/concepts/privacy-model/#sensitive-columns) explains what each setting withholds, and [Keep sensitive columns out of prompts](/guides/keep-sensitive-columns-out-of-prompts/) sets it up.

## Picking a mode

For most teams:

- Start with `schema_only`. It's the safest default.
- Mark sensitive columns in your schema artifact early. Decide per deployment whether to include them tagged or omit them.
- Don't reach for `bounded_results` until you have a concrete need — most analytics use cases don't.
