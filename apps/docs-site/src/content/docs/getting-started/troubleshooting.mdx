## Schema and config

### `No askdb.config.* or .config/askdb.* found in …`

`askdb ask` and `askdb introspect` print this when the current directory has no config. `bootstrapAskDbEnv()` throws a similar error (`… found under <cwd>`) when you embed the libraries.

AskDB looks for `askdb.config.<ext>` (then `.config/askdb.<ext>`) in the **current working directory only** — in a monorepo it won't find a config in a parent directory. Supported extensions, in precedence order: `ts`, `mts`, `cts`, `js`, `mjs`, `cjs`.

If the project has no config yet, create one with `npx askdb init`. If it has one, run the CLI from the directory that holds the config.

```bash
cd apps/api && npx askdb ask --question "..."
```

When embedding the libraries, the equivalent knob is the `cwd` option: `bootstrapAskDbEnv({ cwd: "/path/to/project" })`.

### `AskDB config at <path>: the config has no ai block`

The config file loaded, but it has no `ai` block. Every config needs one, even when you only run `askdb introspect`: add the provider and its connection, as [The `ai` block](/reference/config/#the-ai-block) shows. A config without an `introspection` block fails the same way, and the message names that block.

Other `AskDB config at <path>: …` errors say what can't load, such as an unknown `rag.store`, a file with no default export, or top-level `await`, which the synchronous load can't run. Fix it in the file the message names.

### `Set ASKDB_DEBUG=1 to print the stack trace.`

The CLI hit an unexpected error, most often a config file that exists but fails to load: a syntax error, a missing import, or dependencies that aren't installed yet. The line above the hint is the error message, and it usually names the file and line.

Rerun with `ASKDB_DEBUG=1` to see the stack trace:

```bash
ASKDB_DEBUG=1 npx askdb ask --question "..."
```

`askdb studio` doesn't stop on a config that fails to load: it prints `askdb-studio: warning: <path> could not be loaded, so Studio is ignoring it: …` and starts without it. Fix the file and restart Studio; the setup wizard never overwrites it.

### `SchemaParseError: Cannot read schema at …`

The path passed to `--schema` (CLI) or `loadSchema()` (library) doesn't exist or isn't a valid schema artifact. Valid inputs are:

- A schema directory (e.g. `my-app.schema/`)
- A bundled JSON file (e.g. `my-app.schema.json`)
- A `schema.json` file inside a directory (the name matches in any case, so `Schema.json` works too)

Run `ls my-app.schema/` to confirm the directory was created by `askdb introspect`. If it's empty, the introspection step didn't complete successfully.

### `SchemaParseError: Refusing to load … as a standalone physical layer`

You passed a JSON file that isn't named `schema.json`, such as `prod-schema.json`, and its directory also holds `tenant-policy.md`, `tables/`, or `concepts.md`, in any case (`Tenant-Policy.md` counts). Loading the file alone would ignore those files, so `ask()` would run without your tenant policy and without the `sensitive: true` marks in `tables/*.md`. AskDB refuses instead.

Pass the directory to `--schema` or `loadSchema()`, or rename the file to `schema.json`. To load only the physical layer, pass the file's content to `loadSchemaFromJson()`.

### `SchemaParseError: Schema directory … has a file name in the wrong case`

A file in the schema directory has the right name in the wrong case, such as `Tenant-Policy.md`, `Concepts.md`, `Tables/` or `tables/orders.MD`. AskDB reads these names exactly. On Linux, where file names are case-sensitive, it would skip the file: a skipped `tenant-policy.md` means `ask()` runs with no tenant policy, and a skipped table file drops its `sensitive: true` marks. macOS and Windows would load the same directory, so AskDB refuses it on every OS, and you find out before you deploy.

Rename each file the error names, for example `git mv Tenant-Policy.md tenant-policy.md`. If the error says `keep one of Tenant-Policy.md, tenant-policy.md`, the directory holds both spellings, which only a case-sensitive filesystem allows. Merge them into the correctly named file and delete the other; a rename would overwrite it. `askdb bundle` refuses the directory the same way.

### `Refusing to write … outside the schema directory: "…" is a symbolic link`

A file AskDB writes in the schema directory is a symbolic link: `schema.json` (from `askdb introspect --out` or Studio's **Resync schema**), a `tables/*.md` file or `tables/` itself, `concepts.md`, `tenant-policy.md`, or Studio's `playground-history.json`. Writing through it would change the file it points at, which can be outside the schema directory, so AskDB refuses. A repository can carry symbolic links, so this can come from a checkout.

Replace the link with a regular file that holds the content you want, then run the command or save again. The schema directory itself can be a symbolic link. A linked `.gitignore` doesn't stop Studio: it skips adding `playground-history.json` there and still saves the history, so add that line yourself.

### `SchemaParseError: Missing required field …`

The schema artifact is from an older format. Re-run introspection to regenerate it:

```bash
npx askdb introspect --url "$DATABASE_URL" --out my-app.schema --schema-id my-app
```

## SQL generation

### `SqlValidationError: SQL_NOT_SELECT_OR_WITH`

AskDB only returns `SELECT` or `WITH … SELECT` statements. The model generated a non-SELECT statement (e.g. `INSERT`, `UPDATE`, `DROP`). This is a guardrail, not a bug.

If you're seeing this on legitimate read questions, the model may be misreading the schema. Check that your table and column descriptions in the schema artifact don't imply write operations.

### `SqlValidationError: SQL_MULTI_STATEMENT`

The model returned more than one SQL statement. AskDB refuses multi-statement output. On SQL Server this includes a second statement written without a `;`, such as `SELECT 1 SELECT 2`, because T-SQL doesn't need one between statements. On SQL Server it also fires on code AskDB can't split into tokens the way SQL Server does, such as a non-breaking space or a bare `$` outside a string; the message names the character. Use plain spaces, and keep other text inside string literals or `[bracketed]` names (see [Safety boundaries](/concepts/safety-boundaries/#what-askdb-checks)). Rephrase the question to ask for a single result, or break it into two separate `ask()` calls.

### `SqlValidationError: SQL_COMMENT` / `SQL_FORBIDDEN_KEYWORD` / `SQL_FORBIDDEN_FUNCTION`

The generated SQL contains a SQL comment (including `#` on MySQL), a forbidden keyword (`INTO`, `DELETE`, `EXEC`, `WAITFOR`, etc.), or a call to a blocked side-effecting function (`pg_sleep`, `set_config`, `LOAD_FILE`, `SLEEP`, etc.). Keywords are matched as whole, unquoted tokens, so a column like `deleted_at` or `"delete"` is fine, but an unquoted column or alias named like a keyword (say, `update`) also trips them. These are heuristic, defense-in-depth guardrails. If one fires on a legitimate query, file an issue with the question and schema excerpt.

### `SqlValidationError: SQL_LOCKING_READ`

The generated SQL is a locking read: `FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`, or a SQL Server table hint that takes or holds locks, such as `WITH (UPDLOCK)` or `WITH (HOLDLOCK)`. AskDB returns plain reads only, because a locking read can hold locks that other sessions wait on until your transaction ends. If the question asks to lock or reserve rows, rephrase it as a plain read, and write any locking statement your application needs in your own code. `NOLOCK` and `READUNCOMMITTED` hints pass. On SQL Server the error also fires on a column named like a lock hint, such as `rowlock`, and on an unquoted name that isn't plain ASCII, such as `Größe`, because SQL Server compares hint names loosely: write the name quoted (`[rowlock]`, `[Größe]`), and qualified when it's the only thing inside parentheses (`COUNT(t.[Größe])`). A one-name column list can't be qualified (`WITH [集計] ([合計]) AS …`): name the column inside the query instead (`SELECT 1 AS [合計]`). See [Safety boundaries](/concepts/safety-boundaries/#what-askdb-checks) for every form.

### `SqlValidationError: SQL_UNICODE_ESCAPED_IDENTIFIER`

On Postgres or CockroachDB, the generated SQL uses a Unicode-escaped identifier such as `U&"set\005fconfig"`. Its escapes can spell a blocked function or a sensitive column that the other checks match by name, so AskDB rejects every `U&"…"` name rather than decoding it. AskDB never asks the model for this form. A name that isn't plain ASCII works in plain double quotes (`"注文数"`). `U& "x"` with a space (the `&` operator) and `U&'…'` strings pass. See [Safety boundaries](/concepts/safety-boundaries/#what-askdb-checks).

### `SqlValidationError: SQL_STRING_CONTINUATION`

On Postgres, CockroachDB, or a dialect id that is no built-in engine, the generated SQL continues an `E'…'` string on a later line: `E'a'`, a newline (and possibly a comment), then `'b'`. Postgres joins the two and reads the second with backslash escapes, while AskDB's checks read it as a plain string, so they can disagree about where it ends and miss code after it. AskDB refuses the pair rather than guess. Join the parts with `||`, or write one literal. A plain `'…'` string continued on the next line passes. See [Safety boundaries](/concepts/safety-boundaries/#what-askdb-checks).

### `SqlValidationError: SQL_ESCAPED_BYTE_STRING`

On Postgres, CockroachDB, or a dialect id that is no built-in engine, the generated SQL has a `b'…'` byte string (lower-case `b`) that holds a backslash, such as `b'\x00'`, or continues on a later line. CockroachDB reads it with backslash escapes, while AskDB's checks don't, so they can disagree about where the string ends and miss code after it. AskDB refuses the string rather than guess. Write the bytes as a hex string cast to `bytea` (`'\x00'::bytea`), which Postgres and CockroachDB both read as bytes. A `b'…'` string with no backslash, and a `B'…'` bit string, pass. See [Safety boundaries](/concepts/safety-boundaries/#what-askdb-checks).

### `SqlValidationError: SQL_UNTERMINATED`

A string literal, quoted identifier, dollar-quoted string, or block comment in the generated SQL never closes, so the validator cannot tell where the statement ends and rejects it. On MySQL or MariaDB, check that the dialect's `backslashEscapes` setting matches the server (`NO_BACKSLASH_ESCAPES`). A mismatch matters beyond false rejections: it also lets SQL through that the server reads differently. See [Match your server's string settings](/concepts/safety-boundaries/#match-your-servers-string-settings).

### Generated SQL references a column or table that doesn't exist

This is the most common failure mode. The model hallucinated an identifier that isn't in your schema. AskDB doesn't check generated identifiers against the schema, so your database reports these when you run the query.

**Fix:** Enrich the relevant tables in your schema artifact with plain-English descriptions. The more context the model has, the less it invents:

```bash
npx askdb studio   # open the enrichment UI
# or
npx askdb enrich   # headless AI-assisted enrichment
```

If the column exists in the database but the model keeps getting it wrong, check that `askdb introspect` has been re-run since the column was added, and that its description in the schema artifact isn't ambiguous.

### The SQL is syntactically valid but logically wrong

SQL validation is heuristic — AskDB confirms the statement kind and blocks write keywords, locking reads and side-effecting functions, but it doesn't check identifiers and can't verify that the query answers your question semantically. The quality of answers depends almost entirely on how well the schema artifact describes your data.

Checklist:
1. Does the relevant table have a description? (`description:` field in the table's `.md` file)
2. Do column names match how users phrase questions? Add aliases in the schema artifact.
3. Is this a complex aggregation or join? Add an example question + expected SQL to the table file.
4. Try a more capable model — `gpt-4o` vs `gpt-4o-mini` makes a meaningful difference on complex schemas.

## Model and API keys

### `Error: API key not found` / `AuthenticationError`

The model provider didn't receive a key. For the CLI, set the environment variable before running:

```bash
OPENAI_API_KEY=sk-... npx askdb ask --question "..."
```

For the library, verify the key is passed when constructing the provider:

```ts
const openai = createOpenAI({ apiKey: process.env.OPENAI_API_KEY });
```

See [Bring your own model](/guides/bring-your-own-model/) for per-provider configuration.

### `Error: Model not found` / 404 from provider

The model name passed to the provider doesn't exist or isn't available on your account tier. The default CLI model is `gpt-4o-mini` (OpenAI). Override it with `OPENAI_MODEL` in your `askdb.config.ts` or pass a different model instance to `ask()`.

## Studio and drivers

### Studio shows "driver not installed" or an Install button

Studio's **Execute Query** feature (running SQL against a live database) requires an optional peer driver package. Install the one matching your engine:

```bash
npm install pg          # Postgres
npm install mysql2      # MySQL
npm install better-sqlite3  # SQLite
npm install mssql       # SQL Server
```

After installing, refresh Studio. The driver readiness indicator near the Execute button should clear.

<Aside type="note">
Generating SQL in Studio does **not** require a driver. Only the Execute Query action does.
</Aside>

### Studio doesn't connect to my database

Studio execute is off by default. Check that `studio.execute.enabled: true` is set in `askdb.config.ts`, that `studio.execute.databaseUrl` (or `studio.execute.file` for SQLite) is set, and that the database is reachable from your machine. Restart Studio after editing the config. Studio resolves the execute connection in this order:

1. `studio.execute.databaseUrl` / `studio.execute.file`
2. The introspection connection for the same engine, only when `studio.execute.useIntrospectionConnection: true`

The provider comes from `studio.execute.provider`, or the active `introspection.provider` when it's a live engine.

See [Configuration — Studio execute](/reference/config/#studio-execute-configuration) for the full resolution order.

## SQL Server

### `self-signed certificate` / TLS error on connection

SQL Server enables TLS by default. Local and dev instances typically use a self-signed certificate, which Node.js rejects:

```
Error: self-signed certificate — try running Node.js with --use-system-ca
```

Add `trustServerCertificate=true` to the connection URL:

```
# mssql driver URL format
mssql://sa:pass@localhost:1433/MyDb?trustServerCertificate=true

# sqlserver introspection URL format
sqlserver://localhost:1433;database=MyDb;user=sa;password=pass;trustServerCertificate=true
```

<Aside type="caution">
Only use `trustServerCertificate=true` in development. In production, configure a valid certificate.
</Aside>

## Tenant scope

### `TenantScopeError: MISSING_SCOPE`

Your schema has a `tenant-policy.md` file, which means AskDB requires a `tenantScope` on every `ask()` call. Pass one:

```ts
const { sql } = await ask({
  question,
  schema,
  model,
  dialect,
  tenantScope: {
    access: {
      kind: "ids",
      tenantRoot: "table:public.organizations",
      ids: [currentUser.orgId],
    },
  },
});
```

See [Multi-tenancy](/guides/multi-tenancy/) for the full scope shape.

### `TenantScopeError: UNKNOWN_TENANT_ROOT`

The `tenantRoot` in the scope doesn't match any root defined in `tenant-policy.md`. Check the `id:` field of each root in the policy file — the scope must use the same stable table ID (e.g. `table:public.organizations`).

### `TenantScopeError: SUBTREE_NOT_RESOLVABLE`

The scope uses `access.kind: "subtree"`, but `ask()` couldn't expand it. Either no `resolveTenantDescendants` callback was passed, or the callback didn't return IDs per tenant root. The message says which: it returned an array (the flat shape from before per-root IDs), something other than a plain object, a key that isn't a tenant root in the subtree, a value that isn't an array of non-empty string IDs, or no IDs at all. AskDB doesn't query your database to find descendants, and it won't fall back to the seed IDs alone. Return an object keyed by root table ID, with the seeds and same-table descendants under the scope's `tenantRoot` and each descendant root's IDs under that root: `{ "table:public.agencies": ["1"], "table:public.clients": ["5"] }`. Or send a `multi_root` access with each root's IDs already expanded. Calling `resolveTenantSql()`, `buildTenantPromptBlock()` or `bindPreparedQuery()` directly with an unexpanded `subtree` scope throws the same error, because none of them walks the hierarchy: expand it first with `expandTenantScope()`, or rebind through `askdb.bind()`, which does. See [Hierarchical scope](/guides/multi-tenancy/#hierarchical-scope-subtree).

### `TenantScopeError: UNRESOLVED_TENANT_PLACEHOLDER`

The SQL uses a `:tenant_<root>_ids` placeholder that the scope has no IDs for, so AskDB refuses to return it with the placeholder unfilled. Common causes: the scope covers another root than the one the SQL filters on (a template stored under an agency scope, rebound under a client scope); a covered root has `ids: []`; the placeholder is written in another casing (`:TENANT_AGENCY_IDS`) or runs into the next word (`:tenant_agency_idsOR`); or the scope is `global`, which binds no IDs at all, so SQL under it must not use a tenant placeholder. At rebind, a template with a placeholder also throws this when the schema has no tenant policy. Re-ask the question under the right scope.

### `TenantScopeError: UNESCAPABLE_TENANT_ID`

A tenant ID in the scope contains a backslash or a character outside printable ASCII (an accented letter, `¥`, CJK), and AskDB was asked to inline it as a literal: `ask()`, `bindPreparedQuery()` or `askdb.bind()` with `tenantSqlMode: "sql-only"`. Such a literal can read differently on the server: a backslash depends on its string settings, and a non-ASCII character's bytes depend on the connection charset (`¥` is a backslash under `sjis`). So AskDB refuses it on every dialect instead of returning SQL whose tenant filter a server could read differently. Use the default `tenantSqlMode: "sql-params"`, which passes tenant IDs as driver parameters, and run `sql` with `tenantParams` (or `unboundSql` with `params`). A rebind takes the same option.

### `TenantScopeError: TENANT_SQL_MODE_REQUIRED`

`ask()` got a schema with a tenant policy, no `tenantSqlMode`, and a dialect whose markers AskDB doesn't know: a custom `AskDialect`, or a `DialectSpec` whose `id` isn't a built-in dialect. AskDB can't tell which parameter markers a custom dialect's driver takes, so it doesn't guess: the default `$1, $2, …` would be read as money constants on SQL Server and filter to the wrong tenant. Set `tenantSqlMode: "sql-params"` if your driver binds `$1`-style markers, or `tenantSqlMode: "sql-only"` to get the tenant IDs inlined as escaped literals. Built-in dialect ids, and `DialectSpec`s under one (such as `{ ...POSTGRES_DIALECT, backslashEscapes: true }`), don't need it.

The same error comes from a `tenantSqlMode` that is neither `"sql-params"` nor `"sql-only"` (a typo such as `"sql_only"`, or an empty string), on any dialect: AskDB refuses it rather than read it as either mode.

### Driver error: `there is no parameter $1` / `Too few parameter values` after upgrading

`ask()` binds tenant IDs through driver markers by default (releases up to 1.0.0-beta.45 inlined them): with a `tenantScope`, `result.sql` holds `$1`, `?` or `@p0` where the IDs used to be inlined, and the IDs are in `result.tenantParams`. Running `result.sql` without them fails at the driver (on MySQL, as a syntax error); it never returns other tenants' rows. Pass `result.tenantParams` with `result.sql`, or run `result.unboundSql` with `result.params`. To keep inlined IDs, set `tenantSqlMode: "sql-only"`. See [Executing the result](/reference/core-api/#executing-the-result). A rebind does the same since 1.0.0-beta.46: run `bindPreparedQuery()`'s or `askdb.bind()`'s `sql` with its `tenantParams`, or its `unboundSql` with its `params`, or pass `tenantSqlMode: "sql-only"`.

### `SchemaParseError: Invalid tenant policy: roots … both map to the placeholder …`

Two roots in `tenant-policy.md` derive the same placeholder. A placeholder is the label lowercased, with every run of characters other than ASCII letters and digits turned into `_`, so `Agency` and `agency` both give `:tenant_agency_ids`. A label with no ASCII letter or digit (Cyrillic, CJK and so on) uses the root's table name instead: `Клиент` on `table:public.clients` gives `:tenant_clients_ids`. That fallback can still collide, for example when both table names are non-ASCII too, or when it meets another root's label. Each root's IDs are bound through its own placeholder, so a shared one would bind one root's IDs where the other root's column is compared. AskDB rejects the policy when it loads, `ask()` and `resolveTenantSql()` reject a policy built in code the same way, and Studio refuses to save it. Rename one of the two roots named in the message, using a label with ASCII letters or digits if the fallback collides. See the `label` row in the [field reference](/guides/multi-tenancy/#field-reference).

### `SchemaParseError: … the tenant policy doesn't match schema.json, and enforcement is strict`

`tenant-policy.md` has `enforcement: strict`, and it names something `schema.json` doesn't have, or its roots form a cycle. The usual cause is a column renamed in the database and then re-introspected. The other causes are a `hierarchy` or `parent` edge that loops back, or a root in `scopeThrough`, `hierarchy`, `parent` or a polymorphic `mapping` that `roots` doesn't declare. A strict policy that doesn't match its schema fails the load instead of running tenant checks against the wrong columns. The message lists every problem with its IDs. Update `tenant-policy.md` to match `schema.json`. Until you do, the schema doesn't load anywhere, and a freshly started Studio can't open it either. Setting `enforcement: warn` loads it with each problem in `schema.tenantPolicy.warnings`, but `warn` also returns SQL that fails the tenant check instead of throwing, so use it only while you fix the file. `askdb introspect --out` prints the same list after it writes. See [When the policy and the schema disagree](/guides/multi-tenancy/#when-the-policy-and-the-schema-disagree).

### `TenantGuardrailError`

Your tenant policy uses `enforcement: strict`, and the generated SQL is missing a required tenant predicate on a tenant-scoped or root table, names a table the policy leaves unclassified, names a polymorphic table without its type discriminator, uses a Postgres Unicode-escaped name such as `U&"\006Frders"` (`UNICODE_ESCAPED_IDENTIFIER`), which the check can't read, or, under a scope other than `global`, has a statement that doesn't start with `SELECT` or `WITH` (`NOT_SELECT_OR_WITH`: a `DO` block, `CALL`, `EXPLAIN` or `SHOW`, which a custom `AskDialect` can return), or names a function whose reads the check can't see, as a call or as a column, alias or parameter (`UNCHECKABLE_FUNCTION`: `query_to_xml`, `table_to_xml`, `crosstab`, `dblink`, `OPENQUERY`, `set_config` and the like; see [What the tenant check requires](/guides/multi-tenancy/#what-the-tenant-check-requires)), or continues an `E'…'` string on a later line (`STRING_CONTINUATION`), or has a `b'…'` byte string with a backslash or a continuation (`ESCAPED_BYTE_STRING`), either of which could hide a table from the check. AskDB throws instead of returning that SQL. A predicate counts only as the table's tenant column compared with its placeholder (`agency_id = :tenant_agency_ids`, or `IN (…)` / `= ANY(…)`), ANDed into a `WHERE`, inner-join `ON`, or `HAVING` clause. A literal tenant ID, a column that's only selected, or a predicate next to an `OR` doesn't count, and a query on the root table itself needs the predicate too; see [What the tenant check requires](/guides/multi-tenancy/#what-the-tenant-check-requires). Under a `subtree` scope, each covered root the query reads needs its own placeholder: filtering `clients` only through `clients.sub_agency_id` or a joined agency is rejected, and a covered root you returned no IDs for can't be read at all (see [Hierarchical scope](/guides/multi-tenancy/#hierarchical-scope-subtree)). Inspect the `warnings` array on the error to see which table triggered it, then re-ask the question or narrow it. `bindPreparedQuery()` and `askdb.bind()` run the same check on a stored template under the scope you rebind with, and with `enforcement: warn` they refuse a failing template unless you pass `acceptWarnings: ["tenant"]`; the message says so. The check is heuristic: passing it doesn't prove the query is tenant-safe, so keep tenant isolation enforced in the database. See [Run generated SQL safely](/concepts/safety-boundaries/#run-generated-sql-safely).

### `QueryParameterError: DIALECT_SPEC_REQUIRED`

`bindPreparedQuery()` or `askdb.bind()` got a template whose dialect rules it can't recover, and no `dialect` in its guardrails. That's a template `ask()` made under your own `DialectSpec` (`preparedQuery.dialectRules: "host"`), or one stored before 1.0.0-beta.46, which has no `dialectRules`. Pass the spec you gave `ask()` as `dialect`. If `ask()` ran with the built-in rules, the built-in id is enough, such as `dialect: "postgres"`. An app that loads two copies of `@askdb/core`, such as ESM beside CJS, gets `"host"` templates from the built-in constants of the other copy, and the same fix applies. See [`bindPreparedQuery()`](/reference/core-api/#bindpreparedqueryprepared-values-guardrails).

### `QueryParameterError: MISSING_GUARDRAIL_CONTEXT`

`bindPreparedQuery()` was called with two arguments. Since it re-checks the stored template before binding, it needs a third: `{ schema, tenantScope? }`, the same schema and the caller's scope you pass to `ask()`. With `@askdb/client`, call `askdb.bind(prepared, values, { tenantScope })` instead; it supplies the schema. A `:tenant_*` key in the values throws `TENANT_VALUE_SUPPLIED`: tenant IDs now come from `tenantScope`. See [`bindPreparedQuery()`](/reference/core-api/#bindpreparedqueryprepared-values-guardrails).

## RAG / large schemas

### Retriever is supplied but AskDB uses the full DDL anyway

Two reasons this happens:

1. **Below threshold:** `totalSchemaChunkCount` is at or below `retrievalThresholdChunks` (default 30). Pass the actual chunk count from `buildSchemaIndex` result:
   ```ts
   const index = await buildSchemaIndex({ schema, embedder });
   const { sql } = await ask({
     ...
     retriever: index.retriever,
     totalSchemaChunkCount: index.stats.chunksTotal,
   });
   ```

2. **Outdated artifact format:** The retriever is silently skipped for schema artifacts created by very old AskDB versions. Confirm `loadSchema()` returns an object with a `schemaId` field; if it doesn't, re-run `askdb introspect` to regenerate the artifact.

### Retriever returns no chunks

The question didn't match any indexed chunks. This usually means the schema artifact descriptions are too sparse for meaningful embedding similarity. Enrich your schema with richer table and column descriptions, then rebuild the index.
