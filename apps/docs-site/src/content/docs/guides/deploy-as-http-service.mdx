<p class="doc-lede"><code>@askdb/http-api</code> wraps the same <code>ask()</code> pipeline behind a minimal HTTP server. Use it when non-Node clients need to ask questions, or when you want one AskDB service shared across multiple consumers.</p>

## Start the server

The package ships an `askdb-http` binary — for most deployments you don't write any server code:

```bash
npx askdb-http --schema-path ./my-app.schema --port 3000
```

All flags are optional. Each falls back to `askdb.config.ts` (`host.schemaPath`, `httpApi.listen.port`, `httpApi.listen.host`). After that, the port defaults to `3000` and the host to `127.0.0.1`; the schema path falls back to the `ASKDB_SCHEMA_PATH` environment variable and has no default.

To embed the server in your own process instead, use the programmatic API:

```ts
// server.ts
import { createAskDbHttpServer } from "@askdb/http-api";

const server = createAskDbHttpServer({
  port: 3000,
  host: "127.0.0.1",
  maxBodyBytes: 1024 * 1024, // 1 MiB default
});

await server.listen();
```

Either way, the server reads its schema and model settings from your `askdb.config.ts`, the same config file the CLI and Studio use. When you create it, the server loads `.env` and the config from the current working directory, unless your process already called `bootstrapAskDbEnv()`, in which case it uses that config. Set `host.schemaPath` to point at your schema artifact and configure the AI provider as usual — supply the provider key (`OPENAI_API_KEY`, etc.) in your environment the same way you do for the CLI.

## Endpoints

The server exposes two endpoints:

### `GET /health`

```bash
curl http://localhost:3000/health
# {"ok":true}
```

### `POST /ask`

Body:

```json
{
  "question": "Which customers signed up last week?",
  "mode": "schema_only",
  "explain": false
}
```

Response (success):

```json
{
  "ok": true,
  "correlationId": "8f14e45f-ceea-4e7a-9f2b-1c3d5e7a9b0c",
  "sql": "SELECT id, name, created_at FROM customers WHERE created_at >= …",
  "usage": { "promptTokens": 812, "completionTokens": 64, "totalTokens": 876 }
}
```

`usage` is `null` when the model provider reports no token counts. The [HTTP API reference](/reference/http-api/) lists every request and response field.

The response is SQL only — the server does not run it. Your client takes the SQL and decides what to do with it.

## Calling from curl

```bash
curl -X POST http://localhost:3000/ask \
  -H "content-type: application/json" \
  -d '{"question": "How many customers signed up last week?"}'
```

## Calling from Python

```python
import os
import httpx

resp = httpx.post(
    f"{os.environ['SERVER_URL']}/ask",
    json={"question": "How many customers signed up last week?"},
    timeout=30,
)
resp.raise_for_status()
body = resp.json()

if body["ok"]:
    sql = body["sql"]
    correlation_id = body["correlationId"]
    # Run the SQL against your read-only role here.
else:
    raise RuntimeError(body["error"]["code"])
```

## Run it behind a gateway

`@askdb/http-api` is intentionally minimal — there is no built-in auth, rate limiting, or TLS termination. **Don't expose it directly to the public internet.** Put it behind your existing API gateway, ingress, or reverse proxy and apply the same auth you use for the rest of your services.

A typical production shape:

```
client  ──►  your API gateway  ──►  @askdb/http-api  ──►  model + schema
                  │                          │
                  │                          ▼
                  └────────────────►  read-only DB role  ◄─── (execution happens in your gateway service, not here)
```

The server does not connect to your database. It generates SQL and returns it. Execution is your gateway service's job — that's where your auth context lives.

## Schemas with a tenant policy

`@askdb/http-api` can't serve a schema that has a tenant policy (`tenant-policy.md`) yet. A request has no way to carry a tenant scope, and AskDB never makes one up, so it refuses every such request before calling the model. [#343](https://github.com/Ygilany/AskDB/issues/343) plans a server-side scope hook, and [#277](https://github.com/Ygilany/AskDB/issues/277) a scope for the `askdb-http` binary. Until then, serve tenant-scoped schemas from your own Node service with `ask({ tenantScope })`: see [Multi-tenancy](/guides/multi-tenancy/).

## Custom schema per request

The default is to load the schema from `host.schemaPath` once at boot. Per-request schemas are **off by default**: a request that sends `schemaJson` gets `403 schema_override_disabled`. An override puts caller-supplied text into the prompt through your model key, so only enable it for tests or callers you trust. For a multi-product deployment where different consumers send different schemas, turn it on in `askdb.config.ts`:

```ts
httpApi: { allowSchemaOverride: true },
```

Then supply the bundled JSON as `schemaJson` in the request body:

```json
{
  "question": "How many users?",
  "schemaJson": "{\"version\":2,\"schemaId\":\"…\",\"tables\":[…]}"
}
```

Bundle the artifact with `askdb bundle` and ship the resulting JSON as the value.

## Correlation IDs

Every response except `GET /health` includes a `correlationId`: the value of the request's `x-correlation-id` header when the caller sends one, or a new UUID. The server tags its structured log events with the same ID. Send `x-correlation-id` from your gateway to join its logs to the generated SQL and any errors.
