<p class="doc-eyebrow">Scale-up guide</p>

<p class="doc-lede">Big databases need retrieval. <code>@askdb/rag</code> chunks the same schema artifact and indexes it in a vector store. Per question, AskDB retrieves the relevant slice instead of stuffing the whole thing into every prompt.</p>

## When you need it

A rule of thumb: if your schema artifact has more than ~30 tables, or if rendered DDL routinely exceeds 8K tokens, you'll save money and improve generation quality by retrieving instead of stuffing.

The retrieval trigger is configurable. By default `ask()` uses retrieval when a retriever is supplied <em>and</em> the schema's chunk count exceeds 30.

## Set up pgvector

pgvector is the recommended store: it lives in Postgres alongside your other data, you already know how to back it up, and AskDB ships ready-made DDL.

There are three provisioning paths — pick the one that matches your deploy story.

### Path 1: Studio (local development)

Studio auto-provisions the pgvector schema on first use. Configure the store in `askdb.config.ts`:

```ts
export default {
  rag: {
    embedder: "openai",
    store: "pgvector",
    storeConfig: {
      pgvector: {
        databaseUrl: process.env.PGVECTOR_URL,
      },
    },
  },
};
```

Launch Studio (`npx askdb studio --schema ./my-app.schema`) and the first RAG operation creates the table.

### Path 2: `askdb-rag setup-store` (CI / staging)

One idempotent command. All DDL uses `IF NOT EXISTS` so it's safe to re-run on every deploy.

```bash
askdb-rag setup-store \
  --pg-url "$PGVECTOR_URL" \
  --dimensions 1536
```

Pass `--dimensions` (or `--embedder openai`) to match your embedding model. Without either, the command uses the default `mock` embedder's 64 dimensions. If the table already exists with different dimensions, the command fails instead of silently keeping the old size.

Drop it into a deploy step:

```yaml
- name: Provision pgvector schema
  run: askdb-rag setup-store --pg-url "${{ secrets.PGVECTOR_URL }}" --dimensions 1536
```

### Path 3: Explicit migration (production)

For production teams that want all DDL in a versioned migration file:

```ts
import { createPgvectorStore } from "@askdb/rag/stores/pgvector";

const store = createPgvectorStore({
  connectionString: process.env.DATABASE_URL!,
  dimensions: 1536,
});

console.log(store.setupSql());
```

Paste the output (CREATE EXTENSION, CREATE TABLE, CREATE INDEX) into Flyway, Liquibase, Drizzle, or whatever migration runner your team uses.

## Index the schema artifact

After the store is provisioned, index your schema's chunks:

```ts
import {
  buildSchemaIndex,
  createAiSdkEmbedder,
  createPgvectorStore,
  loadChunkerSourcesFromDir,
} from "@askdb/rag";
import { openai } from "@ai-sdk/openai";

const store = createPgvectorStore({
  connectionString: process.env.PGVECTOR_URL!,
  dimensions: 1536,
});

const embedder = createAiSdkEmbedder({
  model: openai.textEmbeddingModel("text-embedding-3-small"),
});

const { retriever, stats } = await buildSchemaIndex({
  schema: loadChunkerSourcesFromDir("./my-app.schema"),
  store,
  embedder,
  embedderId: "openai:text-embedding-3-small", // changes force a full re-embed
  lockFilePath: "./my-app.schema/schema.lock.json", // records embedder, store, dimensions
});
```

`buildSchemaIndex` chunks the artifact and embeds only the chunks the store doesn't already hold with the same content hash. It returns a ready-to-use `retriever` plus indexing stats. The lock file records the embedder id, store, and dimensions. If any of them changed, or the lock is missing, every chunk is re-embedded. Pass `force: true` to re-embed unconditionally.

## Wire retrieval into `ask()`

Pass the retriever to `ask()`. AskDB calls it with the question and substitutes the retrieved chunks for the full DDL in the prompt.

If you just ran `buildSchemaIndex` in the same process, pass its returned `retriever` directly. To retrieve in a separate process (the common production shape), rebuild one from the store:

```ts
import { createAskDb } from "@askdb/client";
import { createRetriever } from "@askdb/rag";

// askdb initialized at startup — see Embed in a Node app.
const retriever = createRetriever({ store, embedder });

const { sql } = await askdb.ask(question, {
  retriever,
  retrievalThresholdChunks: 30, // default
});
```

## Sensitive fields and embeddings

Sensitive content stays out of the index by default. The chunker drops the describable layer (descriptions, aliases, enum values, notes, common query language, example questions, business context, concepts) for sensitive tables and columns. It also drops any of that text that mentions a sensitive column by name (whole word, case-insensitive), so a concept that says "filter by SSN" is not embedded when `ssn` is sensitive. Column identifiers and types stay available to the model through `ask()`'s prompt.

Set `chunkOptions: { includeSensitiveDescribable: true }` only if your trust model allows embedding that content. Chunks kept this way carry `sensitive: true`. See the [schema-v2 contract on GitHub](https://github.com/Ygilany/AskDB/blob/main/docs/contracts/schema-v2.md#sensitive-propagation) for the full rules.

## Custom table or dimensions

Several schemas can share one table: chunk ids are scoped by schema id (`chunk:<schemaId>:…`), and reindexing one schema never removes another schema's chunks. Use a separate table when deployments use different embedding models or dimensions. To isolate multiple AskDB deployments in the same Postgres database, pass a custom table name and a matching embedding dimension:

```bash
askdb-rag setup-store \
  --pg-url "$DATABASE_URL" \
  --pg-table myapp_rag_chunks \
  --dimensions 1536
```

Match the same `table` value in `askdb.config.ts` under `rag.storeConfig.pgvector.table`.
