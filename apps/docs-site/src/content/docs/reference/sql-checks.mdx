AskDB runs up to three checks on the SQL a model returns: the read-only check, the tenant check and the sensitive check. This page says when each runs, how each reads SQL on every engine, and what each rejects. They're heuristics, not a parser: [Safety boundaries](/concepts/safety-boundaries/) explains why your database stays the boundary.

## The two forms of the model's SQL

The model returns its SQL in two forms. In the first, which `ask()` returns as `sql`, the model writes the values it takes from the question, such as a date or a name, into the SQL as literals. In the second, the `sql-unbound` block, it writes the same statement with a `:name` placeholder in place of each of those values. The model writes the second form only when `parameterize` is on, the default.

With a tenant policy, both forms name the caller's tenant IDs by a placeholder, `:tenant_<root>_ids`, never by value: the model never sees the IDs.

AskDB checks both forms with every placeholder still in place. Only then does it *bind* the values. It puts your scope's tenant IDs in place of the tenant placeholders. It turns each `:name` placeholder into a driver marker, and puts its value in `params`. So the SQL the checks read holds no tenant ID, and no value that AskDB binds. [Executing the result](/reference/core-api/ask/#executing-the-result) says which SQL to run with which values, and [Rerun a query with new values](/guides/rerun-a-query-with-new-values/) binds new values into the stored form.

## When each check runs

| Check | Runs when | With a custom `AskDialect` | On a finding |
| --- | --- | --- | --- |
| Read-only | The dialect is a built-in id or a `DialectSpec`. | Doesn't run. Call `validateSelectSql()` in your generator. | Always refuses: `SqlValidationError`. |
| Tenant | The schema has a `tenant-policy.md`, and the scope isn't `global`. | Runs. | `enforcement: strict` refuses with `TenantGuardrailError`; `warn` returns the SQL and reports it. |
| Sensitive | The schema marks a table or column `sensitive`, and `sensitiveGuardrailMode` isn't `"off"`. | Runs. | `"strict"` refuses with `SensitiveReferenceError`; `"warn"`, the default, returns the SQL and reports it. |

`ask()` runs each check on both forms of the model's SQL, before it binds any value. `bindPreparedQuery()` and `askdb.bind()` run all three again on the stored template, under the schema, scope and dialect rules you pass then. `generateSelectSql()` runs the read-only and tenant checks. [Guardrail verdict](/reference/core-api/ask/#guardrail-verdict) says how the findings become an outcome, and which error a refusal throws.

## How the checks read SQL

The checks don't parse SQL. All three split it into tokens with one shared lexer and skip strings, quoted names and comments, so a keyword inside one doesn't count. Each built-in dialect id is read with its engine's column of the table, under the engine's default string settings unless the `DialectSpec` sets `backslashEscapes`. Some SQL has no built-in engine to read it with. That is SQL from a custom `AskDialect`, from a dialect id that is no built-in engine, or passed to a check with no dialect. It is read with every column, and must pass under each reading.

| | `postgres`, `cockroachdb` | `mysql`, `mariadb` | `sqlite` | `sqlserver` |
| --- | --- | --- | --- | --- |
| Strings | `'…'`, `E'…'`, `$tag$…$tag$` | `'…'` and `"…"` | `'…'` | `'…'` |
| A backslash in `'…'` | Plain text. With `backslashEscapes: true`, an escape. | An escape. With `backslashEscapes: false`, plain text. Unset means the server default, an escape. | Plain text | Plain text |
| Quoted names | `"…"` | `` `…` `` | `"…"`, `` `…` ``, `[…]` | `"…"`, `[…]` |
| Comments | `--`, `/* … */` (nested) | `--` followed by a space or a control character, `#`, `/* … */`. | `--`, `/* … */` | `--`, `/* … */` (nested) |
| Where a `--` comment ends | At a line feed or a carriage return on Postgres, at a line feed only on CockroachDB. Both ids are read both ways. | At a line feed | At a line feed | At a line feed or a carriage return |
| `$` | Inside a name, such as `a$$b`, part of the name. Elsewhere, `$$` or `$tag$` starts a dollar-quoted string (`$tag$…$tag$`), read only on these engines. A tag with non-ASCII letters (`$é$ … $é$`) is read as a string, as the engine does. | Inside a name, part of the name | Inside a name, part of the name | Starts a money literal such as `$1.5` |

On SQL Server, a number also ends after `0x` or `1E` with no digits after it. On SQL Server, a name also ends at whitespace such as a non-breaking space (U+00A0), U+200B or U+0085. So a keyword written right after one is read as a keyword, as SQL Server reads it ([#623](https://github.com/Ygilany/AskDB/issues/623)).

### Forms the checks refuse to read

The checks refuse four forms rather than guess where they end or what they name:

| Form | Refused when | Why |
| --- | --- | --- |
| A string, quoted name or block comment that never closes | Always | The checks can't tell where the statement ends. |
| An `E'…'` string continued on a later line (`E'a'`, a newline, then `'b'`) | The SQL may be read as Postgres: `postgres`, `cockroachdb`, a dialect id that is no built-in engine, or no dialect | Postgres reads the continuation with backslash escapes, so the checks can't tell where the string ends. Join the parts with `\|\|`. |
| A `b'…'` byte string (lower-case `b`) with a backslash, or continued on a later line | The same | CockroachDB reads it with backslash escapes. Write the bytes as a hex string cast to `bytea` (`'\x00'::bytea`). |
| A Unicode-escaped name such as `U&"set\005fconfig"` | The same | Its escapes can spell a blocked function, a table or a sensitive column that the checks match by name. Write the name in plain double quotes (`"注文数"`). |

The read-only check refuses each with its own rule, the tenant check reports it as a finding, and the sensitive check fails closed (`passed: false`, with `unresolvedScope`).

### When your server's settings differ

The readings above assume each engine's default string settings. Your server may read backslashes differently, such as MySQL with `NO_BACKSLASH_ESCAPES` or Postgres with `standard_conforming_strings = off`. Then set `backslashEscapes` on a `DialectSpec` to match, or the checks can read a string differently from the server. [Match your server's string settings](/guides/match-server-string-settings/) shows how.

If you upgrade from a beta release, the [upgrade notes](/reference/upgrade-notes/) say what each change to these readings asks of your app.

## The read-only check

`validateSelectSql()` makes sure the SQL is one read-only query. `ask()` runs it for a built-in dialect id or a `DialectSpec`, and a finding always refuses the SQL with `SqlValidationError`, whose `rule` is one of these:

| Rule | The SQL has |
| --- | --- |
| `SQL_EMPTY` | No statement: the model didn't return SQL. |
| `SQL_NOT_SELECT_OR_WITH` | A first keyword, after any opening parentheses, other than `SELECT` or `WITH`. |
| `SQL_MULTI_STATEMENT` | A `;` that separates a second statement. A single trailing `;` is kept, as the model wrote it, and anything after it is refused. If you wrap the SQL, for example in a row-cap subquery, remove the `;` first (see [Row limits](/guides/run-safely-in-prod/#row-limits)). On SQL Server, also a second statement written without a `;`: see [SQL Server statements](#sql-server-statements). |
| `SQL_COMMENT` | A `--` or `/* … */` comment, or `#` on MySQL and MariaDB. |
| `SQL_FORBIDDEN_KEYWORD` | An unquoted keyword from the shared list or the dialect's `extraForbiddenKeywords`: see [Keywords and functions](#keywords-and-functions). Also a `$N` parameter written against a word (`$1INTO`, `$1FOR`), where the SQL may be read as Postgres: a server that ends the parameter at its last digit reads the word as a keyword the check can't see ([#665](https://github.com/Ygilany/AskDB/issues/665)). Put a space after the parameter. |
| `SQL_FORBIDDEN_FUNCTION` | A call to a function in the dialect's `blockedFunctions`, or `NEXT VALUE FOR` on any engine. |
| `SQL_LOCKING_READ` | A locking read: see [Locking reads](#locking-reads). |
| `SQL_UNICODE_ESCAPED_IDENTIFIER` | A Unicode-escaped name, where the SQL may be read as Postgres. |
| `SQL_STRING_CONTINUATION` | An `E'…'` string continued on a later line, where the SQL may be read as Postgres. |
| `SQL_ESCAPED_BYTE_STRING` | A `b'…'` byte string with a backslash or a continuation, where the SQL may be read as Postgres. |
| `SQL_UNTERMINATED` | A string, quoted name, dollar-quoted string or block comment that never closes. |

A `DialectSpec`'s `extraValidate` runs after these, on the SQL without its trailing `;`.

### Keywords and functions

AskDB refuses the SQL if any of these appear as unquoted keywords: `INSERT`, `UPDATE`, `DELETE`, `DROP`, `TRUNCATE`, `ALTER`, `CREATE`, `GRANT`, `REVOKE`, `VACUUM`, `ANALYZE`, `COPY`, `CALL`, `MERGE`, `INTO`. `INTO` covers `SELECT … INTO new_table` and MySQL `INTO OUTFILE`. Each built-in spec adds its own, in its `extraForbiddenKeywords`:

- **MySQL and MariaDB:** `OUTFILE` and `DUMPFILE`.
- **SQLite:** `ATTACH`, `DETACH`, `PRAGMA` and `REINDEX`.
- **SQL Server:** `EXEC`, `EXECUTE`, `OPENROWSET`, `OPENQUERY`, `WAITFOR`, `SHUTDOWN`, `SET`, `USE`, control-flow verbs such as `DECLARE`, `BEGIN`, `IF`, `WHILE` and `RETURN`, and other T-SQL statement verbs. SQL Server refuses them because T-SQL runs a batch without semicolons. `SQLSERVER_DIALECT.extraForbiddenKeywords` lists all 46.

AskDB also refuses calls to known side-effecting functions, from each built-in spec's `blockedFunctions`. For example:

- **Postgres and CockroachDB:** `pg_sleep`, `set_config`, `pg_read_file`, `dblink` and `nextval` (`POSTGRES_DIALECT.blockedFunctions` lists all 84).
- **MySQL and MariaDB:** `SLEEP`, `LOAD_FILE`, and MariaDB's sequence writers `NEXTVAL` and `SETVAL`.
- **SQLite:** `load_extension`.

On every engine, `NEXT VALUE FOR` is refused with the same rule code, because it advances a sequence on MariaDB and SQL Server, outside your transaction's rollback. MariaDB's `PREVIOUS VALUE FOR` and `LASTVAL()` return the value your session last drew, without changing the sequence, and pass. A dialect id that is no built-in engine gets every built-in spec's keywords and functions.

Setting `extraForbiddenKeywords` or `blockedFunctions` on a `DialectSpec` replaces the built-in list, so spread a built-in spec (`{ ...POSTGRES_DIALECT, … }`) to keep it.

### Locking reads

A locking read can hold locks that other sessions wait on until your transaction ends, so it's refused as `SQL_LOCKING_READ`. On every engine that means `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` and `LOCK IN SHARE MODE`, anywhere in the statement, subqueries and CTEs included.

On SQL Server it also means the table hints `UPDLOCK`, `XLOCK`, `HOLDLOCK`, `PAGLOCK`, `TABLOCK`, `TABLOCKX`, `ROWLOCK`, `SERIALIZABLE` and `REPEATABLEREAD`. The check refuses a hint in two forms:

- **Unquoted**, anywhere, inside `WITH (…)` or without it.
- **Quoted**, when one stands alone in parentheses right after a name, at any depth and with trailing spaces (`FROM t ([UPDLOCK])`, `t (("UPDLOCK "))`). SQL Server also reads that as the hint.

`NOLOCK`, `READUNCOMMITTED` and `READPAST` pass.

SQL Server compares hint names loosely (it reads `UPDʟOCK` as `UPDLOCK`). So on SQL Server, two kinds of name must also be printable ASCII: an unquoted name, and a quoted name alone in parentheses right after a name.

A SQL Server name that is a hint word or isn't plain ASCII must be quoted (`[rowlock]`, `[Größe]`). The prompt lists it quoted and tells the model to quote such an alias too. Two cases need more:

- **Only thing inside parentheses:** qualify it too (`COUNT(t.[Größe])`).
- **A one-name column list** (`WITH [集計] ([合計]) AS …`): name the column inside the query instead.

### SQL Server statements

SQL Server doesn't need `;` between statements, so the check also refuses a second statement written without one. It looks for three shapes:

- A `SELECT` that doesn't follow `UNION`, `EXCEPT` or `INTERSECT` and isn't the main query after a leading `WITH`.
- A parenthesized query right after a complete value, such as `SELECT 1 (SELECT 2)`.
- A label, which is any `:` written directly against a name or value (`l:`).

A subquery after a keyword, an operator, a comma or a function name still passes. One inside an ODBC escape such as `{fn UCASE((SELECT …))}` is refused.

Code outside strings and quoted names must also be plain, because SQL Server may split statements anywhere else. The check refuses:

- a character that isn't printable ASCII or a Unicode letter or digit (a non-breaking space, for example)
- a bare `$`
- a `\`
- a number written against a word (`1ESELECT`)
- a `?` written against a name or number

A second statement that starts with `FETCH`, or with `END`, `GET` or `MOVE CONVERSATION`, isn't detected, because those words also appear in ordinary queries (`OFFSET … FETCH`, `CASE … END`) or as column names.

## The tenant check

With a tenant policy, `ask()` refuses to run without a `tenantScope`, and checks the model's SQL before it binds the tenant IDs. The check runs under every dialect, a custom `AskDialect` included. [What the tenant check requires](/reference/tenant-policy/#what-the-tenant-check-requires) lists what passes:

- a query that starts with `SELECT` or `WITH`
- no call it can't read through
- no Postgres planner-statistics relation
- for each tenant-scoped table and each root table the scope covers, its tenant column compared with its placeholder, ANDed into the filter

Each finding has a rule from [`TenantGuardrailError` rules](/reference/core-api/errors/#tenantguardrailerror-rules).

- **Statements.** A statement ends at each `;`, and on SQL Server also at a verb such as `EXEC`. Under `sqlserver`, code that SQL Server may split differently (see [SQL Server statements](#sql-server-statements)) is refused as `NOT_SELECT_OR_WITH` too. So in plain code, where SQL Server's token ends are unambiguous, the tenant check reads the same text the read-only check does ([#623](https://github.com/Ygilany/AskDB/issues/623)).
- **Calls it can't read through.** A function is refused as `UNCHECKABLE_FUNCTION`, wherever the SQL names it, when it does one of these:
  - runs a query or reads a table named in a string (`query_to_xml`, `table_to_xml`, `crosstab`)
  - runs SQL over another connection (`dblink`, `OPENQUERY`)
  - sets a value row-level security may read (`set_config`)
- **Statistics relations.** Five Postgres planner-statistics relations are refused as `UNCHECKABLE_RELATION`, wherever the SQL names one, qualified with `pg_catalog` or not:
  - `pg_stats`
  - `pg_stats_ext`
  - `pg_stats_ext_exprs`
  - `pg_statistic`
  - `pg_statistic_ext_data`

  They hold values sampled from the rows of every table the querying role can read. A column, alias or parameter named like one is refused too, and every other system relation passes.
- **Outcome.** The policy's `enforcement` decides it: `strict` throws `TenantGuardrailError`, and `warn` returns the SQL with the findings in `result.tenantGuardrail.warnings` and `result.verdict`. At rebind, a `warn` finding refuses the template unless you pass `acceptWarnings: ["tenant"]`. AskDB never adds a missing tenant filter.
- **`global` scope.** The tenant check doesn't run, and SQL that still has a tenant placeholder throws `TenantScopeError` (`UNRESOLVED_TENANT_PLACEHOLDER`), since there are no IDs to bind.
- **Tables named like keywords.** An unquoted name the engine reads as a table, such as `user` on MySQL or `lock` on Postgres, is a read and needs its predicate. So is a quoted one, such as `"order"`. `ORDER BY` and `GROUP BY` are read as keywords, not as a table named `order`, `group` or `by`.
- **Each read, in its own `SELECT`.** Every read of a scoped table, and of a root the scope covers, needs its own predicate in the `SELECT` it appears in ([#399](https://github.com/Ygilany/AskDB/issues/399)).
  - A CTE body, a derived table, a subquery and each `UNION` branch are each their own `SELECT`.
  - A qualified predicate (`o.agency_id`) counts only for the read it names. A read has a name only when it is written `table`, `table alias` or `table AS alias`. What follows must end the source (for example a join, `ON`, `WHERE`, `GROUP BY`, a comma or a closing parenthesis). After any other clause, only an unqualified predicate filters it.
  - When a `SELECT` reads a table more than once, each read needs a distinct plain alias (`orders a JOIN orders b`), outside parentheses, and its own predicate qualified with that alias.
  - On MySQL, MariaDB and SQL Server, write an alias the same way each time. A qualifier in another case doesn't count.
  - A read inside a derived table or CTE also passes when every reference to that source is filtered on the tenant column. The source must pass the column through unrenamed (`SELECT *` over one table, or the column itself).
  - The source must also compute nothing across its rows: no aggregate, window, `GROUP BY`, `HAVING`, `QUALIFY`, `LIMIT`, `OFFSET`, `FETCH` or `TOP`.
  - A set operation in the source's body, or a column list on it or on a reference to it, fails closed.
  - So AskDB refuses `WITH t AS (SELECT id FROM orders WHERE agency_id = :tenant_agency_ids) SELECT * FROM orders`, and a root joined for a label from a CTE, derived table or scalar subquery needs its own predicate there.
- **Joins on the declared columns.** A table scoped through a join path, and a root filtered through another table's column, count only when two things hold. First, each join equates the columns the policy declares (`appointments.client_id = clients.id`), as a `col = col` conjunct or `col IN (SELECT col …)` in the same `SELECT`. Second, the last read is filtered with an allowed root's placeholder. A join on any other pair of columns links nothing. In a `SELECT` with an outer join, no `ON` equality counts ([#400](https://github.com/Ygilany/AskDB/issues/400)).
- **Known limit.** It doesn't check that two joined scoped tables share a scope. Only the roots the scope names are checked as root tables. An unqualified predicate in an `ON` can count for a read the join doesn't see. That happens where a name is spelled like a join word (`NATURAL` or `USING` as a SQL Server alias).

## The sensitive check

The sensitive check reports the tables and columns marked `sensitive: true` that the SQL reads:

- sensitive columns named in the SQL
- sensitive tables read in `FROM` or `JOIN`
- sensitive columns reached through `SELECT *`, `t.*` or a whole-row reference such as `row_to_json(t)`

`ask()` attaches the result as `result.sensitiveGuardrail`. [`validateSensitiveReferences()`](/reference/core-api/checks/#validatesensitivereferencessql-schema-options) runs it on SQL you store and replay, and documents how it resolves names and when it fails closed.

It can miss a table in some `FROM` forms, so a wildcard over it goes unreported:

- a parenthesized `FROM` item ([#306](https://github.com/Ygilany/AskDB/issues/306))
- a comma-joined table after a `JOIN`'s `ON` or `USING` ([#307](https://github.com/Ygilany/AskDB/issues/307))
- MySQL `STRAIGHT_JOIN` used as a join ([#308](https://github.com/Ygilany/AskDB/issues/308))
Mark sensitive data in the database too: keep it out of the read-only role's grants (see [Keep sensitive columns out of prompts](/guides/keep-sensitive-columns-out-of-prompts/)).
