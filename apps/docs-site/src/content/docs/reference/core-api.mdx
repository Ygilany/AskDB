<p class="doc-eyebrow">Reference · @askdb/core</p>

<p class="doc-lede"><code>@askdb/core</code> is the NL-to-SQL pipeline. It owns schema loading, prompt construction, the built-in dialects, heuristic SQL checks, and tenant-scope validation and binding. Everything else in the AskDB ecosystem composes it.</p>

## `ask(options)`

The main pipeline function. Accepts a natural-language question and a loaded schema; returns checked SQL.

```ts
import { ask } from "@askdb/core";

const { sql } = await ask({
  question: "How many users signed up last week?",
  schema,       // from loadSchema()
  model,        // AI SDK LanguageModel
  dialect: "postgres",
});
```

### Options

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `question` | `string` | yes | — | The natural-language question. |
| `schema` | `AnyNormalizedSchema` | yes | — | Loaded schema from `loadSchema()` or `loadSchemaFromJson()`. |
| `model` | `AskDbLanguageModel` | yes | — | An AI SDK `LanguageModel` instance (e.g. `openai("gpt-4o-mini")`). |
| `dialect` | `AskDialectInput` | yes | — | A built-in dialect id, a `DialectSpec` under a built-in id, or a custom `AskDialect`. See [Dialects](#dialects). |
| `mode` | `AskDbModeV1` | no | `"schema_only"` | Trust boundary. See [Modes](#modes). |
| `explain` | `boolean` | no | `false` | When `true`, populates `result.explain` with heuristic guardrail metadata. |
| `omitSensitiveIdentifiersFromNlToSqlPrompt` | `boolean` | no | `false` | When `true`, withholds sensitive columns from the NL→SQL prompt, along with any describable text that names one (a description, alias, enum value, common query language, or retrieved chunk text). A sensitive table stays as a one-line placeholder with its name. Default (`false`) includes them with a `(sensitive)` tag so the model can still ground queries. |
| `tenantScope` | `TenantScope` | no | — | Required when the schema has a `tenant-policy.md`. The pipeline fails closed if a policy exists and this is absent. |
| `tenantSqlMode` | `TenantSqlOutputMode` | no | `"sql-params"` | `"sql-params"` replaces the tenant placeholders with the dialect's driver markers (`$N` Postgres/CockroachDB, `?` MySQL/MariaDB/SQLite, `@pN` SQL Server) and returns the IDs as `tenantParams`. `"sql-only"` inlines them in `sql` as escaped literals, for a tool that takes one SQL string, and refuses a tenant ID that isn't printable ASCII or contains a backslash. A custom `AskDialect` has no default: with a tenant scope it must set this (`$N` markers in `"sql-params"`), or `ask()` throws `TenantScopeError` (`TENANT_SQL_MODE_REQUIRED`). With a tenant policy, any value other than these two throws the same error, on every dialect. See [Executing the result](#executing-the-result). |
| `resolveTenantDescendants` | `ResolveTenantDescendants` | for `subtree` scopes | — | `(tenantRoot, seedIds) => TenantIdsByRoot \| Promise<TenantIdsByRoot>`, where `TenantIdsByRoot` is `Record<rootTableId, string[]>`. Returns the subtree's IDs grouped by tenant root: the seeds and same-table descendants under `tenantRoot`, each descendant root's IDs under that root, e.g. `{ "table:public.agencies": ["1"], "table:public.clients": ["5"] }`. `ask()` unions the seeds in and binds each root's IDs to its own placeholder (a `multi_root` scope). Without it, or when it returns a flat array or an invalid result, a `subtree` scope throws `TenantScopeError` (`SUBTREE_NOT_RESOLVABLE`). See [Hierarchical scope](/guides/tenant-hierarchy/). |
| `parameterize` | `boolean` | no | `true` | Ask the model for unbound SQL + a parameter manifest. Still exactly one model call. Set `false` to save output tokens. Inert for custom `AskDialect` implementations. |
| `sensitiveGuardrailMode` | `"warn" \| "strict" \| "off"` | no | `"warn"` | How to treat SQL that references identifiers marked `sensitive`. `"warn"` reports them in `result.verdict` and `result.sensitiveGuardrail` and logs; `"strict"` throws `SensitiveReferenceError`; `"off"` skips the check. Any other value refuses a sensitive reference, as `"strict"` does. See [Guardrail verdict](#guardrail-verdict) and [`validateSensitiveReferences`](#validatesensitivereferencessql-schema-options). |
| `retriever` | `Retriever` | no | — | RAG retriever from `@askdb/rag`. When supplied, retrieval replaces the full DDL in the prompt, unless `totalSchemaChunkCount` is at or below `retrievalThresholdChunks`. |
| `retrievalK` | `number` | no | `8` | Top-k passed to the retriever. |
| `retrievalThresholdChunks` | `number` | no | `30` | Chunk count at or below which the full DDL is used even if a retriever is supplied. Compared with `totalSchemaChunkCount`. |
| `totalSchemaChunkCount` | `number` | no | `Infinity` | Total chunk count from `buildSchemaIndex`. Pass `result.stats.chunksTotal` here for the threshold check to be meaningful; omit to always use the retriever when one is supplied. |
| `logger` | `AskDbLogger` | no | — | Structured logger. Attach one for observability — it emits `AskDbLogEvent` entries at each pipeline stage. |
| `deps` | `AskGenerateDeps` | no | — | `{ generateText?, providerOptions? }`. `generateText` replaces the AI SDK's `generateText`, for unit tests. `providerOptions` is passed to the model call's `providerOptions` as is; core doesn't read or check it. Use it for provider settings such as reasoning effort, for example from an `@askdb/ai` registry's `resolveProviderOptions()` (see [Reasoning/latency effort](/guides/bring-your-own-model/#reasoninglatency-effort)). A custom `AskDialect` receives both in its `generate()` options. |
| `abortSignal` | `AbortSignal` | no | — | Cancels the model call (`generateText({ abortSignal })`). Use `AbortSignal.timeout(ms)` for a per-request timeout. With a built-in dialect or `DialectSpec`, an aborted call rejects with `SqlGenerationError` whose `cause` is the abort reason. A custom `AskDialect` receives it as `options.abortSignal` and maps its own errors. |

### Result — `AskPipelineResult`

| Field | Type | When present |
| --- | --- | --- |
| `sql` | `string` | Always. The model's bound, checked SQL — business values inlined as literals. Keeps the model's trailing `;`, if it wrote one; remove it before wrapping the statement. Its tenant markers start at the first slot (the default `tenantSqlMode: "sql-params"`); run it with `tenantParams`. In `"sql-only"` mode it has the tenant IDs inlined instead. Never overwritten by rebind failures. |
| `unboundSql` | `string \| undefined` | When `parameterize` is on and the model returned a consistent unbound block + manifest. Absent, with `params`, `parameters` and `preparedQuery`, when a form `ask()` renders from that block still holds a placeholder or fails the read-only check, such as a `:tenant_<root>_ids` placeholder under a schema with no tenant policy. Driver markers (`$N` / `?` / `@pN`) for every value; run it with `params`. Keeps the trailing `;` of the model's `sql-unbound` block, if it has one. |
| `params` | `QueryParamSlot[] \| undefined` | Values for `unboundSql`, in marker order. With a tenant scope this already includes the tenant IDs, in either `tenantSqlMode`. |
| `parameters` | `QueryParameterBinding[] \| undefined` | Named bindings for form UIs (includes runtime `value`, `markers`, `indices`). |
| `preparedQuery` | `PreparedQuery \| undefined` | Definitions + named template only (no runtime values). Input to [`bindPreparedQuery()`](#bindpreparedqueryprepared-values-guardrails). |
| `verdict` | `GuardrailVerdict` | Always. Every guardrail finding for the model's SQL and the outcome: `"allow"`, or `"warn"` when a check in `warn` mode found something. A `"deny"` throws instead. See [Guardrail verdict](#guardrail-verdict). |
| `usage` | `AskUsage \| undefined` | When the model provider reports token counts. |
| `explain` | `unknown \| undefined` | When `explain: true`. Heuristic guardrail metadata — which read-only rules fired and why. |
| `sensitiveGuardrail` | `SensitiveGuardrailResult \| undefined` | When the schema declares at least one `sensitive` table/column and `sensitiveGuardrailMode` is not `"off"`. The sensitive identifiers the returned SQL references, derived from `verdict`. |
| `tenantGuardrail` | `TenantGuardrailResult \| undefined` | When a tenant policy is active. `{ passed, warnings }` from the heuristic tenant check, derived from `verdict`, run on the model's SQL (and its `sql-unbound` block) before tenant binding. It requires each tenant-scoped table, and each root table the scope covers, to have a tenant predicate that filters: its tenant column compared with the placeholder, ANDed into a `WHERE`, inner-join `ON` or `HAVING` clause (see [What the tenant check requires](/reference/tenant-policy/#what-the-tenant-check-requires)). Passing it doesn't prove the SQL is scoped. With `enforcement: strict`, a failure throws `TenantGuardrailError` instead. |
| `tenantParams` | `unknown[] \| undefined` | When `tenantSqlMode` is `"sql-params"` (the default) and the SQL has tenant placeholders. The tenant IDs for the markers in `sql`, in marker order. |
| `tenantBindings` | `TenantBinding[] \| undefined` | When a tenant policy is active and `sql` has at least one tenant placeholder to fill. One entry per placeholder, for audit. |

### Executing the result

Each SQL form runs with exactly one params array — never concatenate `params` and `tenantParams`:

| SQL | Run with | Contents |
| --- | --- | --- |
| `sql` | `tenantParams` (or nothing in `"sql-only"` mode) | Business values inlined; tenant IDs as markers numbered from the first slot (`"sql-params"`, the default) or as literals (`"sql-only"`). |
| `unboundSql` | `params` | All values bound, tenant IDs included in either `tenantSqlMode`: after the business values for `$N` / `@pN`, interleaved in source order for `?`. `parameters[].indices` point into `params`. `tenantSqlMode` governs `sql` only. |

```ts
const result = await ask({ ...options, dialect: "mysql", tenantScope });
if (result.unboundSql && result.params) {
  await conn.execute(result.unboundSql, result.params);
} else {
  await conn.execute(result.sql, result.tenantParams ?? []);
}
```

Always pass `params` as returned. Every driver AskDB documents (`pg`, `mysql2`'s `query` and `execute`, `mssql`, `better-sqlite3`) refuses an array shorter than the statement's markers, so `unboundSql` run with the business values alone fails instead of binding one to a tenant marker. `node:sqlite` doesn't check the number of values it binds: it binds the values it gets in order and the rest as `NULL`, so a short array can return another tenant's rows.

Tenant substitution fails closed. It only replaces placeholders in SQL code (never inside string literals or quoted identifiers) and throws `TenantScopeError` when the SQL references a tenant root the scope has no IDs for (`UNRESOLVED_TENANT_PLACEHOLDER`), or when several IDs meet a predicate with no list form such as `<=` (`UNSUPPORTED_TENANT_PREDICATE`). With several IDs, `=` becomes `IN (…)` and `!=` / `<>` become `NOT IN (…)`. In `"sql-only"` mode, tenant IDs are inlined in `sql` with their quotes doubled, and a tenant ID that isn't printable ASCII (U+0020 to U+007E) or that contains a backslash throws `UNESCAPABLE_TENANT_ID` on every dialect, a custom `AskDialect` included. Any other literal can read differently on the server: on Postgres with `standard_conforming_strings = off`, `'x\'' OR 1=1 -- '` ends the literal early and runs the `OR`, and under a MySQL `sjis` connection `¥` is sent as a backslash. The default `"sql-params"` mode passes such IDs as driver parameters. In `"sql-only"` mode `ask()` also re-checks the rendered `sql`, as `bindPreparedQuery()` does, and refuses a statement that reads differently once the IDs are inlined with `SqlValidationError`.

### Guardrail verdict

`ask()` runs up to three checks on the model's SQL, before it renders tenant IDs or binds values: the read-only check (built-in dialects and `DialectSpec`s only), the tenant check (with a tenant policy), and the sensitive-identifier check (unless `sensitiveGuardrailMode` is `"off"`). Each check reads the model's bound `sql` and its `sql-unbound` block, and one decision maps their findings to an outcome:

| Check | `ask()` returns | `bindPreparedQuery()` rebinds |
| --- | --- | --- |
| read-only | Always `deny`. A failing `sql-unbound` block is dropped with the reuse artifacts instead, and `sql` is still returned. | Always `deny`. |
| tenant | Policy `enforcement: strict` → `deny`; `warn` → `warn`. | `strict` → `deny`; `warn` → `deny`, unless `acceptWarnings` includes `"tenant"`. |
| sensitive | `sensitiveGuardrailMode: "strict"` → `deny`; `"warn"` → `warn`. | Same as `ask()`. |

A `deny` throws the typed error of the highest-ranked denying check: `SqlValidationError`, then `TenantGuardrailError`, then `SensitiveReferenceError`. Every check runs first, and the error carries the whole verdict as `error.verdict`.

```ts
type GuardrailVerdict = {
  outcome: "allow" | "warn" | "deny";
  findings: GuardrailFinding[];
};

type GuardrailFinding =
  | { check: "read-only"; form: "sql" | "template"; rule: SqlValidationRuleCode; message: string; hint?: string }
  | { check: "tenant"; form: "sql" | "template" | "generator"; rule: TenantGuardrailRuleCode; message: string; tableId: string }
  | {
      check: "sensitive";
      form: "sql" | "template";
      rule: SensitiveReferenceRuleCode;
      message: string;
      reference?: SensitiveReference;         // SENSITIVE_TABLE_REFERENCED / SENSITIVE_COLUMN_REFERENCED
      unresolvedScope?: SensitiveScopeReport; // UNRESOLVED_TABLE_SCOPE
    };

type GuardrailOutcome = "allow" | "warn" | "deny";
type GuardrailCheckId = "read-only" | "tenant" | "sensitive";
type GuardrailForm = "sql" | "template";
```

`form` says which form the finding is about: `"sql"` is the model's bound SQL, `"template"` is its `sql-unbound` block (`preparedQuery.namedSql`), and `"generator"` is a finding a custom [`AskDialect`](#askdialect) reported. `generateSelectSql()` returns the same `verdict` for its read-only and tenant checks; it runs no sensitive check. The verdict is in-memory API: AskDB doesn't store it, so a host that wants to show "had warnings" later stores `result.verdict` itself. The checks are heuristics: they catch model mistakes early, and the database stays the boundary (see [Safety boundaries](/concepts/safety-boundaries/)).

### `bindPreparedQuery(prepared, values, guardrails)`

Local rebind of a stored `preparedQuery` with new business values, without a model call. Synchronous. It re-runs the guardrails on the template under the schema, tenant scope and modes you pass now, then renders the template. It returns `sql` with the business values inlined (with a tenant scope in the default `tenantSqlMode: "sql-params"`, run it with `tenantParams`; in `"sql-only"` the tenant IDs are inlined too), `unboundSql` + `params` for driver binding, `bindings` for the business parameters, and the `verdict`. `sql` and `unboundSql` keep the trailing `;` of `namedSql`, if it has one; remove it before you wrap the statement (see [Row limits](/guides/run-safely-in-prod/#row-limits)).

```ts
import { bindPreparedQuery } from "@askdb/core";

const rebound = bindPreparedQuery(
  result.preparedQuery!,
  { state_name: "Utah" },
  { schema, tenantScope }, // the same schema and the caller's scope, as for ask()
);
await pool.query(rebound.sql, rebound.tenantParams ?? []);
// or: await pool.query(rebound.unboundSql, rebound.params);
```

The third argument, `BindGuardrails`, is required:

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `schema` | `AnyNormalizedSchema` | yes | — | The schema to check the template under: its tenant policy and its `sensitive` markers. |
| `tenantScope` | `TenantScope` | with a tenant policy | — | The caller's scope, as for `ask()`. Tenant IDs are rendered from it. A `subtree` scope must be expanded first with [`expandTenantScope()`](#expandtenantscopepolicy-scope-resolvetenantdescendants). |
| `sensitiveGuardrailMode` | `"warn" \| "strict" \| "off"` | no | `"warn"` | As for `ask()`: `"warn"` binds and reports sensitive references in `verdict`; `"strict"` refuses them. |
| `acceptWarnings` | `ReadonlyArray<"tenant">` | no | — | With a policy whose `enforcement` is `warn`, a template that fails the tenant check is refused unless this includes `"tenant"`. |
| `tenantSqlMode` | `TenantSqlOutputMode` | no | `"sql-params"` | As for `ask()`: `"sql-params"` puts tenant markers in `sql` and the IDs in `tenantParams`, with the markers of the template's built-in dialect (a rebind always has one, so `ask()`'s custom-dialect rule never applies); `"sql-only"` inlines them as escaped literals and refuses a tenant ID that isn't printable ASCII or contains a backslash. Any other value throws `TenantScopeError` (`TENANT_SQL_MODE_REQUIRED`). |
| `dialect` | `DialectSpec \| BuiltInDialectId` | for a `"host"` template, or one stored without `dialectRules` | the built-in spec | The dialect rules to check and render under: the `DialectSpec` you passed to `ask()`, or a built-in id. Its `id` must be the template's `dialect`. |

**Which dialect rules a rebind uses.** `ask()` records them in `preparedQuery.dialectRules`: `"builtin"` when it ran with a built-in id or the exported constant (`POSTGRES_DIALECT` and the others), `"host"` for any other `DialectSpec` object, such as `{ ...POSTGRES_DIALECT, backslashEscapes: true }`. A `"builtin"` template rebinds under the built-in spec unless you pass `dialect`. A `"host"` template needs the same spec as `dialect`, so your `backslashEscapes`, `blockedFunctions`, `extraForbiddenKeywords` and `extraValidate` apply at rebind too. A template stored without `dialectRules`, before 1.0.0-beta.46, needs `dialect` as well: pass the spec `ask()` ran with, or the built-in id, such as `"postgres"`, if it ran with the built-in rules. If your app loads two copies of `@askdb/core`, such as ESM beside CJS, a constant from the other copy is a different object, so its templates are `"host"`: pass `dialect` ([ADR 0032](https://github.com/Ygilany/AskDB/blob/main/docs/adrs/0032-rebind-checks-under-the-hosts-dialect-spec.md)).

Tenant IDs come from `tenantScope`, never from `values`. Each `:tenant_<root>_ids` placeholder is filled in both forms, as `ask()` fills it. In `sql`, it becomes driver markers numbered from the first slot, with the IDs in `tenantParams` (the default, `"sql-params"`), or escaped literals in `"sql-only"` (`col = :tenant_agency_ids` becomes `col IN ('7', '8')` with several IDs). In `unboundSql`, it becomes driver markers after the business markers, with the IDs in `params` (appended for `$N` / `@pN`, interleaved in source order for `?`, and `bindings[].indices` remapped). Run each form with its own array, never the two concatenated.

Every check uses the bind-time inputs, so a template refused today may have bound yesterday: a tightened policy, or a scope other than the one it was produced under, applies at the next rebind. It throws:

- `QueryParameterError` (`MISSING_GUARDRAIL_CONTEXT`) without the third argument or its `schema`; (`DIALECT_SPEC_REQUIRED`) without `dialect` for a `"host"` template or one stored without `dialectRules`; (`DIALECT_UNSUPPORTED`) for a `dialect` whose `id` isn't the template's; (`TENANT_VALUE_SUPPLIED`) for a `:tenant_*` key in `values`; (`TENANT_PARAM_ALIGNMENT`) when the tenant markers can't be lined up with the business params; (`INVALID_DECLARATION`) for a parameter declaring a `type` or `cardinality` AskDB doesn't support; and the existing reasons for a wrong, missing or misplaced business value.
- `TenantScopeError`: as in `ask()` for a missing or invalid scope; `SUBTREE_NOT_RESOLVABLE` for an unexpanded `subtree`; `UNRESOLVED_TENANT_PLACEHOLDER` for a placeholder the scope has no IDs for. That includes a template scoped through another root, any placeholder under a `global` scope, and any placeholder when the schema has no tenant policy. `UNESCAPABLE_TENANT_ID` in `"sql-only"` mode for a tenant ID that isn't printable ASCII or contains a backslash. `TENANT_SQL_MODE_REQUIRED` for a `tenantSqlMode` that is neither mode.
- `SqlValidationError`, `TenantGuardrailError` or `SensitiveReferenceError` for a `deny` verdict (see [Guardrail verdict](#guardrail-verdict)). A refused tenant warning throws `TenantGuardrailError` with a message naming `acceptWarnings`.

`@askdb/client` users call [`askdb.bind()`](/reference/client-api/#clientbindprepared-values-options), which supplies the client's schema and expands a `subtree` scope.

List parameters are arity-stable in `unboundSql` only on PostgreSQL/CockroachDB (`= ANY($n)`). Elsewhere a changed list length changes the marker count — rebind rather than swapping the array. Map SQL Server values via `parameters[].markers` (`@p0`-based).

### `expandTenantScope(policy, scope, resolveTenantDescendants)`

```ts
import { expandTenantScope } from "@askdb/core";

const expanded = await expandTenantScope(schema.tenantPolicy!, subtreeScope, resolveTenantDescendants);
const rebound = bindPreparedQuery(prepared, values, { schema, tenantScope: expanded });
```

The `subtree` expansion `ask()` runs, as a function: it calls your [`resolveTenantDescendants`](#options) and returns a `multi_root` scope with one entry per root the subtree covers (an `ids` scope when the subtree is one root table), keeping a level with no IDs as `ids: []` so reading it fails closed. Other access kinds pass through. It validates the scope first and throws `TenantScopeError` (`SUBTREE_NOT_RESOLVABLE`) for a missing resolver or a malformed result, as `ask()` does.

### `expandClosure(seedIds, childrenOf)`

```ts
import { expandClosure } from "@askdb/core";

const ids = expandClosure(seedIds, (id) => childrenByAgencyId.get(id) ?? []);
```

Walks a hierarchy you already hold in memory, breadth-first, and returns the seed IDs and every descendant, each once, seeds first. It's cycle-safe: an ID it has already visited isn't visited again. Use it inside `resolveTenantDescendants` for a tree inside one table; see [Scope to a tenant hierarchy](/guides/tenant-hierarchy/#walk-a-hierarchy-you-hold-in-memory).

### `AskUsage`

```ts
type AskUsage = {

```

Populated from the model provider's usage report. Use for cost tracking or quota enforcement. All fields are `null` when the provider does not report that counter.

## Guardrails

### `validateSensitiveReferences(sql, schema, options?)`

Reports the `sensitive` tables and columns a SQL statement references. Pure, synchronous, no model call.

`sensitive: true` otherwise only affects the **prompt** — `formatSchemaForNlToSql` either tags identifiers `(sensitive)` or, with `omitSensitiveIdentifiersFromNlToSqlPrompt`, withholds them. Both act on what the model *sees*. This function is the **enforcement** path: it inspects SQL that is about to execute. Hosts that cache, store, or replay generated SQL should call it on **every execution path**, not just at generation time.

```ts
import { validateSensitiveReferences } from "@askdb/core";

// Cache-replay path — no model in the loop.
const { passed, references } = validateSensitiveReferences(cachedSql, schema);
if (!passed) {
  throw new Error(`refusing to replay: ${references.map((r) => r.column).join(", ")}`);
}
```

`ask()` runs this check on the model's SQL and reports it in `result.verdict` and `result.sensitiveGuardrail`, and `bindPreparedQuery()` runs it again on every rebind. Use the standalone function for statements that don't come through either, such as SQL you store and replay yourself.

#### Result — `SensitiveGuardrailResult`

| Field | Type | Meaning |
| --- | --- | --- |
| `passed` | `boolean` | `true` only when nothing sensitive was referenced **and** table scope was fully resolved. |
| `references` | `SensitiveReference[]` | Every sensitive identifier the statement touches. |
| `unresolvedScope` | `SensitiveScopeReport \| undefined` | Present when the statement's `FROM`/`JOIN` scope could not be resolved with confidence. |

```ts
type SensitiveReference = {
  table: string;            // table name as spelled in the schema artifact
  schema?: string;          // namespace, when the artifact records one
  column: string;           // column name, or "*" when matchKind is "table"
  matchKind: "qualified" | "unqualified" | "table";
};
```

- **`"qualified"`** — `table.column`, or `alias.column` where the alias binds to the owning table. Also `alias.*` and whole-row references such as `row_to_json(alias)` or `to_jsonb(alias)`, which reach every sensitive column of that table.
- **`"unqualified"`** — a bare `column`, counted **only because the owning table is in the statement's scope**. Also a bare `SELECT *`, which reaches every sensitive column of the tables in that `SELECT`'s own `FROM`/`JOIN` (not a subquery's).
- **`"table"`** — the sensitive table itself is a `FROM`/`JOIN` target. Catches `SELECT * FROM secrets`, where no column is named.

#### Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `mode` | `"warn" \| "strict"` | `"warn"` | See [Modes](#modes). |
| `dialect` | `Pick<DialectSpec, "id" \| "backslashEscapes">` | — | A `DialectSpec`, or `{ id }` with an optional `backslashEscapes`. Lex the SQL the way that engine does (MySQL backslash escapes and `#` comments, Postgres `E'…'` and `$tag$…$tag$`, SQL Server `[…]`). Without it, references are collected under every built-in engine's reading, which is conservative and can over-report in rare cases. |

#### Scope resolution

An unqualified name is not a substring search. `FROM`/`JOIN` targets and their aliases are resolved first — including inside CTEs and derived tables — and bare names are matched only against the columns of tables actually in scope.

This matters most with table-level `sensitive`, which promotes *every* column of that table into the match set. A schema with a `sensitive` audit or changelog table that has an `id` column would otherwise flag `SELECT s.id FROM students s`. It does not:

```ts
validateSensitiveReferences(
  "SELECT s.id, s.first_name FROM people.students s",
  schema,
); // → { passed: true, references: [] }

validateSensitiveReferences("SELECT email, password FROM identity.users", schema);
// → references: [{ table: "users", schema: "identity", column: "password", matchKind: "unqualified" }]
```

#### Modes

`{ mode: "warn" }` (default) returns the references without throwing. `{ mode: "strict" }` throws `SensitiveReferenceError extends AskDbError` whenever `passed` is `false`, carrying `.rule` (`"SENSITIVE_TABLE_REFERENCED"` | `"SENSITIVE_COLUMN_REFERENCED"` | `"UNRESOLVED_TABLE_SCOPE"`), `.references`, and `.unresolvedScope`.

#### Conservative failure

When the check can tell it couldn't bind names to tables, it reports that in `unresolvedScope` rather than passing. It can't always tell: a table in a `FROM` form it doesn't recognize is skipped without a report (see [Safety boundaries](/concepts/safety-boundaries/), #306–#309). `unresolvedScope.issues` contains one or more of:

| Issue | Cause | Effect |
| --- | --- | --- |
| `NO_TABLE_SOURCE` | No `FROM`/`JOIN` target resolved, so unqualified names cannot be bound. | Unqualified matching widens to every sensitive column. |
| `UNKNOWN_QUALIFIER` | A `qualifier.column` whose qualifier is not a known table, alias, or CTE. | That column is matched against every sensitive column. |
| `OPAQUE_TABLE_SOURCE` | A table source that is not a relation name (table function, table-valued expression). | Reported only; no widening — such a source exposes no schema columns. |
| `UNTERMINATED_TOKEN` | A string, quoted identifier, or comment never closes. | Reported only; the rest of the statement could not be scanned. |
| `UNICODE_ESCAPED_IDENTIFIER` | A Postgres Unicode-escaped name (`U&"p\0061ssword"`), which Postgres decodes and the check matches as written. Raised when the SQL may be read as Postgres: postgres, cockroachdb, a custom `AskDialect`, or no dialect. | Reported only; the check can't tell which column the name reads. |
| `STRING_CONTINUATION` | An `E'…'` string continued on a later line, which Postgres reads with backslash escapes. Raised when the SQL may be read as Postgres. | Reported only; a column after it may be hidden from the check. |
| `ESCAPED_BYTE_STRING` | A `b'…'` byte string (lower-case `b`) with a backslash, or continued on a later line, which CockroachDB reads with backslash escapes. Raised when the SQL may be read as Postgres. | Reported only; a column after it may be hidden from the check. |

`unresolvedScope.widened` says whether matching was widened, and `.message` explains why. `strict` mode treats unresolved scope as a failure: `passed` is `false`, so it throws `SensitiveReferenceError` (`rule: "UNRESOLVED_TABLE_SCOPE"` when no sensitive reference was found).

The check is heuristic, not a SQL parser — a review and enforcement aid, not a substitute for database-side column privileges.

### `schemaHasSensitiveIdentifiers(schema)`

`true` when the schema marks at least one table or column `sensitive`. Cheap pre-check for hosts that want to skip the guardrail entirely on schemas with no markers — `ask()` uses it for exactly that, which is why `result.sensitiveGuardrail` is absent on unmarked schemas.

### `formatSensitiveReference(ref)`

Renders a `SensitiveReference` as `schema.table.column` (or `table.column` when the artifact has no namespace). `askdb ask` uses it for its `Warning:` line, and `ask()` uses it for the `sensitiveColumns` field of the `askdb.pipeline.sensitive_sql_warning` log event, next to `sensitiveColumnCount`.

## Schema loading

### `loadSchema(path)`

```ts
import { loadSchema } from "@askdb/core";
const schema = loadSchema("./my-app.schema"); // synchronous
```

Autodetects and loads a v2 schema artifact. Accepts:
- A **schema directory** (`<name>.schema/`) — the output of `askdb introspect`
- A **bundled JSON file** (any JSON object with a `bundled` key, whatever the file's name) — the output of `askdb bundle`
- A direct path to a `schema.json` file, matched in any case (`Schema.json` works too). This loads the enclosing directory, so sibling `tables/*.md`, `concepts.md`, and `tenant-policy.md` apply just as they do for the directory path.
- Any other JSON file, loaded as the physical layer only. If its directory also holds `tenant-policy.md`, `tables/`, or `concepts.md`, in any case, `loadSchema()` throws `SchemaParseError` instead, because loading the file alone would ignore them: a copy such as `prod-schema.json` would load without its tenant policy. Pass the directory, or pass the file's content to `loadSchemaFromJson()` to load only the physical layer.

The file names `loadSchema()` looks up in a directory are exact: `schema.json`, `tenant-policy.md`, `concepts.md`, `tables/`, and the `.md` extension in `tables/`. A file whose name matches one only when case is ignored, such as `Tenant-Policy.md` or `tables/orders.MD`, throws `SchemaParseError` on every OS, and the error names each rename. On Linux, where file names are case-sensitive, the file would otherwise be skipped, and a skipped `tenant-policy.md` turns tenant enforcement off.

Returns `NormalizedSchemaV2`. A path that doesn't exist throws Node's file system error (`code: "ENOENT"`), not `SchemaParseError`, and so does a JSON file you can't read (`EACCES`). Other failures throw `SchemaParseError`. The optional files (`tables/*.md`, `concepts.md`, `tenant-policy.md`) may be absent. If one exists but is empty or cannot be read or parsed, for example because of malformed YAML front-matter, loading throws. Bundles follow the same rule: only an absent `tenantPolicy` key means "no policy", and the error names the file and the bundle, for example `tenant-policy.md (in /srv/prod.bundle.json)`. A broken `tenant-policy.md` never silently turns tenant enforcement off.

`loadSchema()` also checks every ID in `tenant-policy.md` against `schema.json`. Under `enforcement: strict`, an orphaned column or foreign key ID, a column that `schema.json` has on another table than the field names (`misplaced_column_id`, with `id`, `tableId` and `context`), a hierarchy cycle, or a root that `roots` doesn't declare throws `SchemaParseError` naming the file and the IDs. Under `warn` these load, listed in `schema.tenantPolicy.warnings`. A table that `schema.json` doesn't have is a warning in both modes. See [When the policy and the schema disagree](/reference/tenant-policy/#when-the-policy-and-the-schema-disagree). `normalizeTenantPolicy(parsed, physicalTableIds, columnOwners)` runs the same check on a policy you parsed with `parseTenantPolicyMarkdown()`: `physicalTableIds` is the set of table IDs in `schema.json`, and `columnOwners` maps each column ID in `schema.json` to its table's ID.

Each table and column in the result has one effective `sensitive` flag. It is `true` when `schema.json` marks it sensitive, when its `tables/*.md` front-matter sets `sensitive: true` (which is what Studio's Sensitivity tab writes), or, for a column, when its table is sensitive. Front-matter is escalate-only: a front-matter `sensitive: false` never un-marks something that is sensitive anyway. It is ignored and reported in `schema.warnings` as `{ kind: "sensitivity_downgrade_ignored", tableFile, id }`. A `columns` entry whose ID belongs to a different table than the file it is in is reported as `{ kind: "misplaced_column_id", tableFile, id, tableId }`. Its `sensitive: true` still applies to the column the ID names, but nothing else in the entry does. A column ID listed more than once in the same file is reported as `{ kind: "duplicate_column_id", tableFile, id }`. Only the first entry's description, aliases, and enum are used, but the column is sensitive if any entry naming it, in any `tables/*.md` file, sets `sensitive: true`. Two `tables/*.md` files with the same front-matter `id` make `loadSchema()` and `loadSchemaFromJson()` throw `SchemaParseError` naming both files. `tableFile` is always the markdown file that was actually read. Prompt formatting, `validateSensitiveReferences`, and `@askdb/rag` chunking all read this effective flag. A column that is sensitive only because its table is also carries `sensitiveFromTable: true`; `@askdb/rag` uses it to count a mention of that column only when written as `table.column`.

`loadSchema` is synchronous — load once at startup and keep the result in memory, not per request.

### `loadSchemaFromJson(raw)`

```ts
import { loadSchemaFromJson } from "@askdb/core";
const schema = loadSchemaFromJson(bundleJsonString);
```

Parses a raw JSON string. Accepts the same formats as `loadSchema` (bundled JSON or bare `schema.json` blob). Useful when the schema is passed as a string over a network boundary (e.g., the HTTP API's `schemaJson` request field).

The bundle's shape is exported as the `BundledSchemaV2` type: `{ bundled: true, physical, tables, concepts?, tenantPolicy? }`, where `physical` is the `schema.json` object, `tables` maps each `tables/` filename to its raw markdown, and `concepts` and `tenantPolicy` hold the raw `concepts.md` and `tenant-policy.md` when those files exist. `tables` is required (`{}` when there are no table files): a bundle without it, or whose `tables` isn't an object of strings, throws `SchemaParseError` naming `tables` and the bundle. `askdb bundle` writes it.

### `readSchemaDirectory(dir)`

```ts
import { readSchemaDirectory } from "@askdb/core";
import { writeFileSync } from "node:fs";

const bundle = readSchemaDirectory("./my-app.schema"); // synchronous
writeFileSync("./my-app.schema.bundle.json", `${JSON.stringify(bundle, null, 2)}\n`);
```

Reads a schema directory into its bundle form, a `BundledSchemaV2`. `loadSchema()` reads every directory through this function, and `askdb bundle` and `@askdb/enrich`'s `bundleSchemaDirectory()` return it, so `loadSchemaFromJson(JSON.stringify(readSchemaDirectory(dir)))` gives the same schema as `loadSchema(dir)`. It follows the directory rules of `loadSchema()`: names must be spelled exactly, an optional file is absent only when the directory doesn't list it, and a listed file that can't be read throws `SchemaParseError`. It validates `schema.json` and returns the markdown files unparsed. `bundleSchemaDirectory()`, and so `askdb bundle`, also checks the bundle with the loader, and refuses one that doesn't load.

### `findMentionedNames(text, names)`, `createMentionMatcher(names)` and `sensitiveMentionNames(schema)`

```ts
import { createMentionMatcher, findMentionedNames, sensitiveMentionNames } from "@askdb/core";
findMentionedNames("Dedupe by EMAIL; see users_email", ["email", "ssn"]); // → ["email"]

const sensitive = createMentionMatcher(["ssn", { table: "users", column: "org_id" }]);
sensitive.mentionsAny('filter by "users"."org_id"'); // → true
sensitive.find("Rows come from users. Org_id is the key"); // → []

// The names the rule checks for a loaded schema: here users.email is marked sensitive,
// and users.org_id is sensitive only because the whole users table is.
const names = sensitiveMentionNames(schema); // → ["email", { table: "users", column: "org_id" }]
createMentionMatcher(names).mentionsAny("Dedupe on email"); // → true
```

The schema contract's "mentions a sensitive column by name" rule, which `@askdb/rag`'s chunker, `@askdb/enrich`'s authoring warning and `ask()`'s prompt (with `omitSensitiveIdentifiersFromNlToSqlPrompt`) all use: whole-word and case-insensitive, with a bare name (a string, matched literally) or a qualified one (`{ table, column }`). The full rule is in the [schema-v2 contract on GitHub](https://github.com/Ygilany/AskDB/blob/main/docs/contracts/schema-v2.md#sensitive-propagation). `findMentionedNames` returns the names `text` mentions, in the order given. It compiles the names on every call, so to check many texts against one list, build a `MentionMatcher` once with `createMentionMatcher` and call `mentionsAny(text)` or `find(text)`. `sensitiveMentionNames(schema)` returns the names that rule checks for a normalized schema, schema-wide: a column marked sensitive itself by its bare name, and a column that is sensitive only because its table is (`sensitiveFromTable`) only as `{ table, column }`. Columns of untracked tables count too.

### `saveSchemaFile(schemaDir, relativePath, content)`

```ts
import { saveSchemaFile, writeConceptsMarkdown } from "@askdb/core";
saveSchemaFile("./my-app.schema", "concepts.md", writeConceptsMarkdown({ concepts }, body));
```

Writes `content` (a string, written as UTF-8, or a `Uint8Array`, written as given) to one file inside a schema directory, so that no link redirects the write out of it. `@askdb/enrich`'s saves, Studio and `@askdb/introspect` all write the directory through it; use it when your own authoring tool writes there. `relativePath` names the file from `schemaDir` with `/` between parts (`schema.json`, `tables/orders.md`).

- It throws, and writes nothing, when the file or a directory between it and `schemaDir` (such as `tables/`) is a symbolic link. `schemaDir` itself can be a symbolic link.
- It throws when `relativePath` has an empty, `.` or `..` part or a NUL byte (on Windows, also a `\`), so an absolute path is refused too. It doesn't create missing directories.
- It writes a temporary file next to the target and renames it over the target. A hard link at the target is replaced, not written through, and a reader sees the old file or the new one, never part of one. The new file keeps the target's permission bits, group and, where the process may set it, owner. It doesn't keep an access control list (ACL) or other extended attributes, so on a file with an ACL a save can widen access.
- A target you can't write throws `EACCES`, as a plain write would. The temporary file needs write access to the target's directory.

A refusal's message reads `Refusing to write <relativePath> outside the schema directory: <why>`. On Windows, the rename fails with `EPERM` while another process holds the target open; writing again usually works.

## Enrichment suggestions

### `suggestEnrichment(target, context, model, deps?)`

```ts
import { loadSchema, suggestEnrichment } from "@askdb/core";
import { buildSuggestionContext, buildSuggestionTarget } from "@askdb/enrich";

const schema = loadSchema("./my-app.schema");
const source = { scope: "table", tableId: "table:public.users", field: "description" } as const;
const candidates = await suggestEnrichment(
  buildSuggestionTarget(schema, source),
  buildSuggestionContext(schema, source.tableId),
  model,
  { omitSensitiveIdentifiersFromPrompt: true }, // your modes.omitSensitiveFromPrompt
);
// → [{ text: "Registered user accounts." }, { text: "People who can place orders." }]
```

Asks the model for up to three candidate values for one describable field, which a person reviews before anything is saved: a table's description, aliases, primary entity or common query language, or a column's description or aliases. Studio's **Suggest** buttons call it. `target` names the field and carries its table; `context` carries the schema id and up to four tables linked to it by foreign key. `@askdb/enrich`'s `buildSuggestionTarget(schema, source)` and `buildSuggestionContext(schema, tableId)` build both from `loadSchema()`'s result. The target table and the neighbors are `NormalizedV2Table`s, the table type in `loadSchema()`'s result, so a table read straight from `schema.json` doesn't typecheck. Load the schema directory or a bundle with `loadSchema()`, so the `sensitive` flags include `tables/*.md` front-matter: `loadSchemaFromJson()` of a bare `schema.json` typechecks too, but has none.

The prompt lists the target table the way `ask()`'s prompt does (`TABLE public.users`, then one line per column), with no descriptions, and tags sensitive columns `(sensitive)`. `deps` takes:

| Field | Default | Description |
| --- | --- | --- |
| `omitSensitiveIdentifiersFromPrompt` | `false` | Leave sensitive columns out of the prompt; a sensitive table keeps only its name. `suggestEnrichment` reads no config, so pass your `modes.omitSensitiveFromPrompt`. A target that is itself a sensitive column throws `SensitiveEnrichmentTargetError` (an `AskDbError`, whose message names no column) before any model call, because the prompt would have to name it. |
| `providerOptions` | — | Forwarded to the AI SDK's `generateText` unchanged. |
| `temperature` | `0.4` | Sampling temperature. |
| `maxCandidates` | `3` | The most candidates returned. |

The option's type is exported as `EnrichmentPromptOptions`. `buildEnrichmentUserPrompt(target, context, options?)` returns the user prompt `suggestEnrichment` sends, with the same `options`, for hosts that call their model themselves; it throws `SensitiveEnrichmentTargetError` in the same case. `ENRICHMENT_SYSTEM_PROMPT` is the system prompt, and `parseCandidates(text, max)` splits a reply into candidates.

## Dialects

The `dialect` option accepts three forms:

### Built-in dialect id

```ts
dialect: "postgres"  // or "mysql" | "sqlite" | "sqlserver" | "cockroachdb" | "mariadb"
```

| Id | Engine |
| --- | --- |
| `"postgres"` | PostgreSQL — `"` quotes, `ILIKE`, `::type` cast, `NOW()`, `\|\|` concat |
| `"cockroachdb"` | CockroachDB — PostgreSQL-wire-compatible; reuses the Postgres spec and prompt. Outside the 1.0 support claim: AskDB's end-to-end tests don't cover it. |
| `"mysql"` | MySQL — `` ` `` quotes, `CONCAT()`, `LIKE`, `CAST()`, `NOW()` |
| `"mariadb"` | MariaDB — MySQL-protocol-compatible; reuses the MySQL prompt |
| `"sqlite"` | SQLite — dynamic typing, `LIKE`, `date('now')`, `\|\|` concat, `LIMIT` |
| `"sqlserver"` | SQL Server (T-SQL) — `[bracket]` or `"` quotes, `GETDATE()`, `+`/`CONCAT()`, `CAST()`/`CONVERT()` |

`@askdb/core` exports the built-in `DialectSpec` of each id: `POSTGRES_DIALECT`, `COCKROACHDB_DIALECT`, `MYSQL_DIALECT`, `MARIADB_DIALECT`, `SQLITE_DIALECT` and `SQLSERVER_DIALECT`. `BUILT_IN_DIALECTS` maps each id to its spec, `SUPPORTED_DIALECT_IDS` lists the ids, `isBuiltInDialectId(id)` checks one, and `getDialectSpec(id)` returns its spec. The engine packages re-export their own engine's constants (`@askdb/postgres`, `@askdb/mysql`, `@askdb/sqlite`, `@askdb/sqlserver`; `COCKROACHDB_DIALECT` comes only from core). Passing the string id to `ask()` is enough: you don't need an engine package for SQL generation.

### `DialectSpec`

Customize how one of the built-in dialects prompts and validates — for example, a PostgreSQL-compatible warehouse that needs extra guidance in the prompt or extra forbidden keywords. `id` must be one of the six built-in ids (the spec describes a variant of that engine family, not a brand-new engine — for that, use [`AskDialect`](#askdialect)). `ask()` throws `UnknownDialectError` for a spec under any other `id`: spread the built-in spec and keep its `id`, as in `{ ...MYSQL_DIALECT, displayName: "TiDB", promptBrief: "…" }`.

```ts
import { type DialectSpec } from "@askdb/core";

const redshiftFlavor: DialectSpec = {
  id: "postgres", // the built-in family this variant belongs to
  displayName: "Amazon Redshift",
  promptBrief: "Amazon Redshift SQL. PostgreSQL syntax with some differences: ...",
  identifierQuote: '"',
  extraForbiddenKeywords: ["COPY", "UNLOAD"],
  extraValidate(sql) {
    // throw SqlValidationError for dialect-specific rules
  },
};
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `DialectId` | yes | One of the six built-in ids — the engine family this spec belongs to. |
| `displayName` | `string` | yes | Human-readable name. |
| `promptBrief` | `string` | yes | One-paragraph guidance for the model about this dialect's syntax. |
| `identifierQuote` | `'"' \| '`'` | yes | Identifier quoting style. The prompt quotes names the way `id`'s engine does, not with this field. |
| `reservedWords` | `readonly string[]` | no | Words the engine reserves, case-insensitive. The prompt lists a schema, table or column with one of these names quoted. The built-in specs set their engine's list; spread one to keep it, since setting the field replaces the list. |
| `unqualifiedNamespace` | `string` | no | A namespace that isn't a schema in this engine. When it is the schema's only namespace, the prompt lists its tables without it and tells the model never to write `<namespace>.<table>`; next to other namespaces (a MySQL database list that includes a database named `public`) it stays qualified. The SQLite, MySQL and MariaDB specs set `SINGLE_NAMESPACE_LABEL` (`"public"`), the namespace their connectors give the database's tables; spread one to keep it. |
| `extraForbiddenKeywords` | `readonly string[]` | no | Keywords to forbid in addition to the shared read-only denylist. |
| `blockedFunctions` | `readonly string[]` | no | Functions `validateSelectSql` rejects when called (`name(`), such as `pg_sleep` or `load_file`. |
| `extraValidate` | `(sql: string) => void` | no | Dialect-specific SQL validator. Throw `SqlValidationError` for failures. |
| `listBinding` | `"array" \| "expand"` | no | How a list value binds in `unboundSql`. `"array"` binds the whole list to one marker (`= ANY($1)`), so the marker count doesn't change with the list length. `"expand"` binds one marker per item (`IN (?, ?, ?)`). Default `"expand"` when unset. `POSTGRES_DIALECT` and `COCKROACHDB_DIALECT` set `"array"`, and the other built-in specs set `"expand"`. |
| `backslashEscapes` | `boolean` | no | Whether a backslash escapes a quote inside `'…'` strings on your server. The built-in specs set the engine default (`true` for MySQL and MariaDB, `false` otherwise). Set `false` for MySQL or MariaDB with `NO_BACKSLASH_ESCAPES`, and `true` for Postgres with `standard_conforming_strings = off`. The checks lex strings this way, and the business values `bindPreparedQuery()` inlines are escaped to match. Tenant IDs are never escaped for the dialect: they are driver parameters by default, and `"sql-only"` refuses an ID that would need escaping. See [Match your server's string settings](/concepts/safety-boundaries/#match-your-servers-string-settings). |

`id` also selects how the validator lexes strings, quoted identifiers, and comments. The built-in specs ship their own `extraForbiddenKeywords` and `blockedFunctions`; spread one (`{ ...POSTGRES_DIALECT, … }`) to keep them, since setting either field replaces the built-in list. These checks are defense in depth — run generated SQL under a read-only database role.

`id` also decides how the prompt quotes names. A schema, table or column whose name is in `reservedWords`, is a word the SQL checks reject unquoted (the shared denylist plus `extraForbiddenKeywords`, such as `copy`, and on `sqlserver` and an id that is no built-in engine the lock hints, such as `rowlock`), isn't a plain identifier (on `sqlserver` and an id that is no built-in engine, anything beyond ASCII letters, digits, `_` and `$`), or (for `postgres` and `cockroachdb`, which fold unquoted names to lowercase) has capitals, is listed quoted (`billing."order"` for `postgres` and `cockroachdb`, ``billing.`order` `` for `mysql` and `mariadb`, `billing.[order]` for `sqlserver`, `"order"` for `sqlite`; a Prisma table `Post` is `public."Post"` on Postgres). When the prompt lists tables with their schema, it also tells the model to quote each part of a qualified name separately. On `sqlserver` and an id that is no built-in engine, it tells the model to quote a non-ASCII alias (`AS [注文数]`) and to qualify a quoted column that is alone in parentheses (`SUM(o.[金額])`), because the SQL checks reject both otherwise. An id that quotes with a backtick (`` identifierQuote: "`" ``) can't use a column named like a denylisted word, a lock hint, or a name that isn't plain ASCII yet: the checks read its SQL under every engine's lexer, SQL Server's included, where a backtick doesn't quote (#672). `promptIdentifierQuoter(dialect)` returns that quoting as a function; pass it as `quoteIdentifier` when you call `formatSchemaV2ForNlToSql` or `synthesizeRetrievedDdl` yourself.

### `AskDialect`

Full escape hatch for custom NL→SQL generators — agentic flows, tool-calling, fine-tuned models, non-SELECT targets. 95 % of consumers should use a built-in id or `DialectSpec` instead.

```ts
import { type AskDialect } from "@askdb/core";

const myDialect: AskDialect = {
  async generate(question, schema, model, options) {
    // call your own generation logic
    return { sql: "SELECT ...", usage: { promptTokens: 100, completionTokens: 20, totalTokens: 120 } };
  },
};
```

The `generate` method receives:
- `question: string`
- `schema: AnyNormalizedSchema`
- `model: AskDbLanguageModel`
- `options?: AskDialectGenerateOptions` — `{ logger, explain, omitSensitiveIdentifiersFromNlToSqlPrompt, generateText, providerOptions, abortSignal, prebuiltDdl, promptTableIds, tenantPolicy, tenantScope }`. Under retrieval, `prebuiltDdl` is the retrieved DDL and `promptTableIds` the ids of the tables it shows; a dialect that builds its prompt with `buildNlToSqlUserPrompt()` passes both, so the prompt's tenant block names no other table. Pass `abortSignal` to your model call so the caller's timeout cancels it; `ask()` doesn't wrap what `generate()` throws, so an abort surfaces as your dialect's own error (typically the AI SDK's `AbortError`) unless you map it. `tenantScope` is the scope after `ask()` expands a `subtree`: a `multi_root` scope with one entry per covered root, where a root the resolver returned no IDs for has `ids: []`. `validateTenantScope()` accepts it.

It must return `AskDialectGenerateResult`:

| Field | Type | Description |
| --- | --- | --- |
| `sql` | `string` | The generated SQL. |
| `explain` | `unknown \| undefined` | Guardrail metadata when `options.explain` is true. |
| `tenantGuardrail` | `TenantGuardrailResult \| undefined` | Optional extra tenant findings from your generator. With a tenant policy, each warning becomes a tenant finding with `form: "generator"` in `ask()`'s verdict, decided under the policy's `enforcement`, and `passed: false` with no warnings becomes one `UNPROVABLE_SCOPE` finding. They add to `ask()`'s own check and can't replace it. Without a tenant policy, it is passed through to `result.tenantGuardrail` unchanged. |
| `usage` | `AskUsage \| undefined` | Token usage, if your generator has access to it. |

A custom `AskDialect` is responsible for its own read-only validation. `ask()` does not run the SELECT-only validator on its output. If your generator should only emit read-only SQL, call `validateSelectSql(spec, sql)` before returning. Tenant enforcement is different: when the schema has a tenant policy, `ask()` runs the tenant guardrail on the returned `sql` (and its `sql-unbound` block), with the `:tenant_<root>_ids` placeholders still in place, and then substitutes them, whatever the dialect. With any scope but `global`, that check also requires every statement to start with `SELECT` or `WITH`, so a `DO` block, `CALL`, `EXPLAIN` or `SHOW` is a tenant finding (`NOT_SELECT_OR_WITH`), even though `ask()` doesn't run the read-only check on your SQL. It also refuses a function whose reads it can't see, wherever the SQL names it, such as `query_to_xml('SELECT …')`, `table_to_xml('orders', …)` or `OPENQUERY` (`UNCHECKABLE_FUNCTION`), because the read-only check that blocks some of them doesn't run on your SQL. With a tenant scope, a custom `AskDialect` must set `tenantSqlMode`, because AskDB can't know its driver's markers (see [`ask()` options](#options)). Under `strict`, SQL that fails the tenant check throws `TenantGuardrailError`; passing it doesn't prove the SQL is scoped. A custom `AskDialect` doesn't tell the guardrail how its engine quotes strings, so the statement must pass under the standard-SQL, Postgres (`E'…'` escape strings), and MySQL (where `"…"` is a string) readings: a tenant column written only as `"agency_id"` doesn't count as a predicate. The sensitive-identifier check runs on a custom dialect's SQL too, unless `sensitiveGuardrailMode` is `"off"`.

Passing an unknown string dialect id, or a `DialectSpec` whose `id` isn't one of the six built-in ids, throws `UnknownDialectError`, which extends `AskDbError`. `ask()` refuses such a spec before any tenant check, retrieval or model call.

## Logging

### `createAskDbLogger(options)`

```ts
import { createAskDbLogger } from "@askdb/core";

const logger = createAskDbLogger({
  correlationId: requestId,
  level: "info",
  logFile: "./logs/askdb.json",
});
```

Returns an `AskDbLogger` that emits structured JSON for each pipeline stage. Pass it to `ask()` via `options.logger`.

| Option | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `correlationId` | `string` | yes | — | Attached to every log line. Pass the request id. |
| `level` | `AskDbLogLevel` | no | `"silent"` | Pino log level. `"silent"` suppresses all output. |
| `logFile` | `string` | no | — | Append JSON logs to this path. Parent directories are created automatically. Loggers with the same path share one open file, which stays open for the life of the process: rotate it with `copytruncate`, or restart the process after a rotate. |
| `logStdout` | `boolean` | no | `false` | Duplicate logs to stdout in addition to stderr/file. |

**`AskDbLogLevel`:** `"fatal"` | `"error"` | `"warn"` | `"info"` | `"debug"` | `"trace"` | `"silent"`

The emitted log events are typed as `AskDbLogEvent` constants (e.g. `PipelineMode`, `PipelineGenerateStart`, `TenantScopeValidated`). Import `AskDbLogEvent` from `@askdb/core` to filter logs by event kind.

To pass your own logger instead, implement `AskDbLogger`: `info(context, message)` and `error(context, message)`, plus optional `debug` and `warn`. `ask()` logs `TenantPolicyWarnings` (`askdb.tenant.policy_warnings`) through `warn`, or through `info` when your logger has no `warn`.

## Tenant types

These types are needed when your schema has a tenant policy. See [Scope queries to a tenant](/guides/multi-tenancy/) for the full workflow.

### `TenantSqlOutputMode`

- `"sql-params"` (the default, exported as `DEFAULT_TENANT_SQL_MODE`) — replaces the tenant placeholders with the dialect's driver markers and returns the IDs as `tenantParams`. See [Executing the result](#executing-the-result).
- `"sql-only"` — inlines the tenant IDs as escaped literals, for a tool that takes one SQL string. A tenant ID that isn't printable ASCII or contains a backslash throws `TenantScopeError` (`UNESCAPABLE_TENANT_ID`).

### `DEFAULT_TENANT_SQL_MODE`

```ts
const DEFAULT_TENANT_SQL_MODE: TenantSqlOutputMode; // "sql-params"
```

The mode `ask()` and `resolveTenantSql()` use when you don't pass one. It doesn't apply to `ask()` with a tenant scope and a custom `AskDialect`: those must set `tenantSqlMode`. A host that reports or forwards the mode, such as a UI that shows which mode a query ran in, imports it rather than hard-coding the string:

```ts
import { DEFAULT_TENANT_SQL_MODE } from "@askdb/core";

const mode = options.tenantSqlMode ?? DEFAULT_TENANT_SQL_MODE;
```

### `TenantBinding`

```ts
type TenantBinding = {
  placeholder: string;  // e.g. ":tenant_org_ids"
  rootLabel: string;    // domain label (e.g. "organization")
  rootId: string;       // tenant root id
  ids: string[];        // resolved id values
};
```

### `placeholderForTenantRoot(root)`

```ts
import { placeholderForTenantRoot } from "@askdb/core";

placeholderForTenantRoot({ id: "table:public.sub_agencies", label: "Sub-Agency" }); // ":tenant_sub_agency_ids"
placeholderForTenantRoot({ id: "table:public.clients", label: "Клиент" });          // ":tenant_clients_ids"
```

Returns the `:tenant_<name>_ids` placeholder for a tenant root: the one the prompt names, `ask()` and `resolveTenantSql()` bind, and the tenant guardrail checks. `<name>` is the label lowercased, with every run of characters other than ASCII letters and digits replaced by `_`. A label with no ASCII letter or digit uses the root's table name instead. Pass a root from `schema.tenantPolicy.roots` (anything with `id` and `label`).

`placeholderForRoot(label)` is deprecated. It takes the label alone, so for a label with no ASCII letter or digit it returns `:tenant___ids`, which core doesn't bind. For every other label the two agree.

### `buildTenantPromptBlock(policy, scope, prompt)`

```ts
import { buildTenantPromptBlock, loadSchema, type TenantScope } from "@askdb/core";

const schema = loadSchema("./my-app.schema");
const scope: TenantScope = { access: { kind: "ids", tenantRoot: "table:public.agencies", ids: ["42"] } };

// The prompt shows the whole schema: the block names its tracked policy tables.
buildTenantPromptBlock(schema.tenantPolicy!, scope, { schema });

// Under retrieval, pass the ids of the tables the retrieved DDL shows.
buildTenantPromptBlock(schema.tenantPolicy!, scope, { schema, tableIds: ["table:public.orders"] });
```

Returns the tenant-policy block `ask()` adds to the NL→SQL prompt: the roots, the tenant-scoped, polymorphic and global tables, the scope's placeholders and the columns each one may be compared with, and the rules. `prompt` is required. It's the prompt's schema and, under retrieval, the ids of the tables the retrieved DDL shows (`synthesizeRetrievedDdl()`'s `tableIds`). The block names only the tables the prompt shows: never a table marked `tracked: false`, and no table retrieval left out, except one on a join path a shown table needs. A root whose table isn't shown appears by its label and placeholder. An unexpanded `subtree` scope throws `TenantScopeError` (`SUBTREE_NOT_RESOLVABLE`); expand it first with `expandTenantScope()`.

### `buildNlToSqlUserPrompt(dialect, question, schema, ambiguityNotes?, logger?, nlToSqlSchemaOptions?, prebuiltDdl?, tenantPolicy?, tenantScope?, parameterize?, promptTableIds?)`

Returns the NL→SQL user prompt `ask()` sends with a built-in dialect: the rules, the schema's DDL (or `prebuiltDdl`), the tenant block when `tenantPolicy` and `tenantScope` are set, and the hints. With a tenant policy, the tenant block follows the tables the prompt shows. Without `prebuiltDdl` those are the schema's tracked tables. With `prebuiltDdl`, pass `promptTableIds`, the ids of the tables it shows; leaving them out throws `AskDbError`. A tenant policy also needs a v2 schema.

### `formatTenantPolicyWarning(warning)`

```ts
import { formatTenantPolicyWarning, loadSchema } from "@askdb/core";

// A policy with `enforcement: warn`: under `strict`, this problem makes loadSchema() throw.
const schema = loadSchema("./my-app.schema");
schema.tenantPolicy?.warnings.map(formatTenantPolicyWarning);
// ["scopeThrough column on table:public.orders: column table:public.orders#agency_ref is not in schema.json"]
```

Returns one line describing a `TenantPolicyWarning`, naming the IDs involved. The `SchemaParseError` for a strict policy, the `askdb.tenant.policy_warnings` log message and `askdb introspect` use the same wording.

### `TenantScope`

Passed as `options.tenantScope` to `ask()`. Carries enforceable access plus optional advisory context.

```ts
// IDs access — user can see records for their specific org ids
const scope: TenantScope = {
  access: {
    kind: "ids",
    tenantRoot: "table:public.organizations", // stable table ID from the policy
    ids: ["org-1", "org-2"],
  },
  context: { role: "regional_manager", label: "Jane Smith" },
};

// Global / super access
const adminScope: TenantScope = {
  access: { kind: "global", reason: "support investigation" },
};
```

`context` goes into the prompt as advisory text, and so does a `global` scope's `reason`; the `access` IDs don't, because the prompt names only their placeholders. Keep personal data you don't want sent to your model provider out of `context` and `reason`: the example's `label` puts a person's name in the prompt.

`access` is a `TenantAccess`, one of four kinds. `tenantRoot` is a root's table ID from the policy's `roots`.

| Kind | Fields | Description |
| --- | --- | --- |
| `"ids"` (`TenantAccessIds`) | `tenantRoot: string`, `ids: string[]` (at least one) | User can access specific root-entity ids. |
| `"subtree"` (`TenantAccessSubtree`) | `tenantRoot: string`, `rootIds: string[]` (at least one), `includeDescendants: true` | User can access a subtree rooted at `rootIds`, including descendant roots. Requires the `resolveTenantDescendants` option on `ask()`, which returns IDs per root; `ask()` expands the scope to `"multi_root"` before generation. |
| `"multi_root"` (`TenantAccessMultiRoot`) | `scopes: { tenantRoot: string; ids: string[] }[]` | User has access across multiple tenant roots, each with their own id set. An entry's `ids` may be empty (a covered root with no IDs, which fails closed if read); at least one entry needs an ID. |
| `"global"` (`TenantAccessGlobal`) | `reason: string` (not blank) | Super / admin access. The `reason` is for audit: a missing or blank one throws `TenantScopeError` (`GLOBAL_WITHOUT_REASON`). Binds no tenant IDs: SQL that still has a `:tenant_*` placeholder throws `TenantScopeError` (`UNRESOLVED_TENANT_PLACEHOLDER`), in `ask()` and at rebind. |

`context` is an optional `TenantScopeContext`: `role`, `label`, `department`, `region` and `description` (each a `string`), and `attributes` (`Record<string, string>`). The prompt lists the fields that are set under "User context (advisory — not enforced)", and no check enforces them. `validateTenantScope()` refuses any other key.

## Errors

`@askdb/core`'s errors are `AskDbError` or one of its subclasses, so `instanceof AskDbError` catches them, except the few plain `Error`s listed after the table. Each class sets `name` to its class name. `@askdb/client` adds four more; see [@askdb/client API → Errors](/reference/client-api/#errors). The [Troubleshooting](/getting-started/troubleshooting/) page has fixes for the common codes.

| Class | Thrown by | Fields |
| --- | --- | --- |
| `AskDbError` | The base class. Thrown as is by `parseAskDbModeV1()` for an unknown mode, and by `ask()` and `generateSelectSql()` with a built-in dialect or `DialectSpec` for an empty question or a schema with no tables. | `message`, `cause?` |
| `SchemaParseError` | `loadSchema()`, `loadSchemaFromJson()`, `readSchemaDirectory()` and the markdown parsers: a file that can't be read or parsed, a name in the wrong case, a standalone JSON file in a schema directory, an invalid tenant policy, or, under `enforcement: strict`, a tenant policy that names IDs `schema.json` doesn't have or a column on another table than its entry's. See [`loadSchema(path)`](#loadschemapath). | `cause?` |
| `UnknownDialectError` | `ask()` with a string `dialect` that isn't a built-in id, or a `DialectSpec` whose `id` isn't one. | `dialectId` |
| `SqlGenerationError` | `ask()` and `generateSelectSql()` with a built-in dialect or `DialectSpec`, when the model call fails or is aborted. Its message is `Model call failed: ` followed by the failure's message. When that message gives no reason, as for a refused connection, AskDB adds the code and address of each error under it, such as `ECONNREFUSED 127.0.0.1:11434`, or the error's name when it has no code. | `cause`: the AI SDK's error or the abort reason. |
| `SqlValidationError` | `validateSelectSql()`, and a `deny` from the read-only check in `ask()`, `generateSelectSql()` and `bindPreparedQuery()`. | `rule`, `hint?`, `verdict?` |
| `TenantScopeError` | `ask()`, `bindPreparedQuery()`, `expandTenantScope()`, `validateTenantScope()`, `resolveTenantSql()` and `buildTenantPromptBlock()`: a missing or invalid scope, or tenant IDs that can't be bound. | `reason` |
| `TenantGuardrailError` | A `deny` from the tenant check in `ask()`, `generateSelectSql()` and `bindPreparedQuery()`, and `validateTenantGuardrails()` under a `strict` policy. | `warnings`, `verdict?` |
| `SensitiveReferenceError` | `validateSensitiveReferences()` in `strict` mode, and a `deny` from the sensitive check in `ask()` and `bindPreparedQuery()`. | `rule`, `references`, `unresolvedScope?`, `verdict?` |
| `QueryParameterError` | `bindPreparedQuery()`: missing guardrail inputs, a template that declares a parameter `type` or `cardinality` AskDB doesn't support, or values that don't fit the template. | `reason` |
| `SensitiveEnrichmentTargetError` | `suggestEnrichment()` and `buildEnrichmentUserPrompt()`, for a sensitive target column while `omitSensitiveIdentifiersFromPrompt` is on. The message names no column. | — |

`verdict` is set when the error comes from `ask()`, `generateSelectSql()` or `bindPreparedQuery()`: every finding of every check, not only the one that denied. See [Guardrail verdict](#guardrail-verdict). A direct `validateSelectSql()` or `validateSensitiveReferences()` call leaves it unset.

Some functions throw a plain `Error` instead: `getDialectSpec()` for an id with no spec, `saveSchemaFile()` for a path it refuses (see [`saveSchemaFile`](#saveschemafileschemadir-relativepath-content)), and `buildEnrichmentUserPrompt()` and `suggestEnrichment()` for a target column the table doesn't have. A custom `AskDialect`'s errors pass through `ask()` unchanged.

### `SqlValidationError` rules

`rule` is a `SqlValidationRuleCode`:

| Rule | The SQL has |
| --- | --- |
| `SQL_EMPTY` | No statement. |
| `SQL_MULTI_STATEMENT` | More than one statement. |
| `SQL_COMMENT` | A `--`, `/* */` or (MySQL) `#` comment. |
| `SQL_NOT_SELECT_OR_WITH` | A first keyword other than `SELECT` or `WITH`. |
| `SQL_FORBIDDEN_KEYWORD` | A keyword from the shared denylist or the dialect's `extraForbiddenKeywords`, outside strings and quoted identifiers. |
| `SQL_FORBIDDEN_FUNCTION` | A call to a function in the dialect's `blockedFunctions`, such as `pg_sleep(` or, on MySQL and MariaDB, `NEXTVAL(`. On every dialect, also `NEXT VALUE FOR`, which advances a sequence on MariaDB and SQL Server. |
| `SQL_UNICODE_ESCAPED_IDENTIFIER` | On Postgres and CockroachDB, a Unicode-escaped identifier such as `U&"set\005fconfig"`, whose escapes could spell a blocked function or a sensitive column. |
| `SQL_UNTERMINATED` | A string, quoted identifier, dollar-quoted string or block comment that never closes. |
| `SQL_STRING_CONTINUATION` | On Postgres, CockroachDB, or a dialect id that is no built-in engine, an `E'…'` string continued on a later line (`E'a'`, a newline, then `'b'`). Postgres reads the continuation with backslash escapes, so the checks can't tell where the string ends. |
| `SQL_ESCAPED_BYTE_STRING` | On Postgres, CockroachDB, or a dialect id that is no built-in engine, a `b'…'` byte string (lower-case `b`) with a backslash, or continued on a later line. CockroachDB reads it with backslash escapes, so the checks can't tell where the string ends. Write the bytes as a hex string cast to `bytea` (`'\x00'::bytea`). |
| `SQL_LOCKING_READ` | A locking read: `FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`, or a T-SQL lock hint such as `UPDLOCK`. On SQL Server, also a name that isn't printable ASCII, unquoted or quoted alone in parentheses after a name, which SQL Server can read as a hint. |

`hint` explains why the rule exists and how to fix the SQL.

### `TenantScopeError` reasons

`reason` is a `TenantScopeRejectionReason`:

| Reason | Cause |
| --- | --- |
| `MISSING_SCOPE` | The schema has a tenant policy and no `tenantScope` was passed. |
| `INVALID_SCOPE_SHAPE` | `tenantScope` doesn't match [`TenantScope`](#tenantscope), for example an `ids` scope with no IDs. |
| `UNKNOWN_TENANT_ROOT` | `tenantRoot` isn't a root in the policy. |
| `GLOBAL_WITHOUT_REASON` | A `global` scope whose `reason` is missing, isn't a string, or is blank. It's checked before the shape, so such a scope never throws `INVALID_SCOPE_SHAPE`. |
| `SUBTREE_NOT_RESOLVABLE` | A `subtree` scope can't be expanded: no `resolveTenantDescendants`, or it returned something other than IDs per root in the subtree. Also an unexpanded `subtree` passed to `bindPreparedQuery()`, `resolveTenantSql()` or `buildTenantPromptBlock()`. |
| `UNRESOLVED_TENANT_PLACEHOLDER` | The SQL has a `:tenant_<root>_ids` placeholder the scope has no IDs for, including any placeholder under a `global` scope. |
| `UNSUPPORTED_TENANT_PREDICATE` | A scope with several IDs meets a tenant predicate with no list form, such as `<=`. |
| `UNESCAPABLE_TENANT_ID` | A tenant ID that isn't printable ASCII (U+0020 to U+007E), or that contains a backslash, would be inlined as a literal: in `"sql-only"` mode, by `ask()`, `resolveTenantSql()` or `bindPreparedQuery()`. |
| `TENANT_SQL_MODE_REQUIRED` | `ask()` has a tenant scope, no `tenantSqlMode`, and a custom `AskDialect`. Also a `tenantSqlMode` other than `"sql-params"` or `"sql-only"`, on every dialect, in `ask()` (with a tenant scope), `bindPreparedQuery()` and `resolveTenantSql()`. |

### `TenantGuardrailError` rules

`warnings` is a `TenantGuardrailWarning[]`, each `{ rule, tableId, message }`. `rule` is a `TenantGuardrailRuleCode`:

| Rule | The SQL |
| --- | --- |
| `MISSING_TENANT_PREDICATE` | Reads a tenant-scoped table, or a root table the scope covers, with no tenant predicate that filters it. See [What the tenant check requires](/reference/tenant-policy/#what-the-tenant-check-requires). |
| `MISSING_TYPE_DISCRIMINATOR` | Reads a polymorphic table without its type column compared with the mapping key of the root whose placeholder filters its ID column, ANDed into the same clause (`owner_type = 'agency' AND owner_id = :tenant_agency_ids`). |
| `UNKNOWN_TABLE_REFERENCED` | Reads a table that `tenant-policy.md` doesn't classify. |
| `UNICODE_ESCAPED_IDENTIFIER` | Uses a Postgres Unicode-escaped name, such as `U&"\006Frders"`, as a table, column or function. Postgres decodes it, so the check can't tell what it reads. Reported with `tableId: ""` when the SQL may be read as Postgres: postgres, cockroachdb, a custom `AskDialect` or no dialect. |
| `UNPROVABLE_SCOPE` | Reported for a custom `AskDialect` whose `tenantGuardrail` has `passed: false` and no warnings. |
| `NOT_SELECT_OR_WITH` | Has a statement that doesn't start with `SELECT` or `WITH` (after any comments and opening parentheses), such as a `DO` block, `CALL`, `EXPLAIN` or `SHOW`, so the check can't read what it touches. Every statement counts: each one after a `;`, and on SQL Server each one a verb such as `EXEC` starts with no `;`. For a custom `AskDialect`, every engine's reading counts. Not checked under a `global` scope. Reported for the whole SQL (`tableId: ""`), under every dialect, a custom `AskDialect` included. |
| `UNCHECKABLE_FUNCTION` | Names a function whose reads the check can't see: one that runs a query passed as a string (`query_to_xml`, `ts_stat`, `crosstab`), reads a table named in a string (`table_to_xml`, `schema_to_xml`, `connectby`), runs SQL over another connection (`dblink`, `OPENQUERY`, `OPENROWSET`), or sets a value row-level security may read (`set_config`). The [tenant policy contract](https://github.com/Ygilany/AskDB/blob/main/docs/contracts/tenant-policy.md#what-the-check-requires) lists the 32 functions, each built into Postgres or SQL Server or from the `tablefunc`, `dblink` or `xml2` extension; a function from any other extension, such as pgRouting's, passes. A listed name counts in any code position, so a column, alias or parameter named like one (`crosstab`, `set_config`) is refused too. Only the first listed name is reported. Not checked under a `global` scope. Reported for the whole SQL (`tableId: ""`), under every dialect, a custom `AskDialect` included. |
| `STRING_CONTINUATION` | Continues an `E'…'` string on a later line, which Postgres reads with backslash escapes and the check doesn't, so a table or call after it could be hidden. Reported with `tableId: ""` when the SQL may be read as Postgres: postgres, cockroachdb, a custom `AskDialect` or no dialect. |
| `ESCAPED_BYTE_STRING` | Has a `b'…'` byte string (lower-case `b`) with a backslash, or continued on a later line, which CockroachDB reads with backslash escapes and the check doesn't, so a table or call after it could be hidden. Reported with `tableId: ""` when the SQL may be read as Postgres: postgres, cockroachdb, a custom `AskDialect` or no dialect. |

The policy's `enforcement` decides the outcome: `strict` throws `TenantGuardrailError`, and `warn` returns the findings in `result.verdict`. At rebind, a `warn` finding throws too, unless `acceptWarnings` includes `"tenant"`.

### `SensitiveReferenceError` rules

`rule` is a `SensitiveReferenceRuleCode`: `SENSITIVE_TABLE_REFERENCED`, `SENSITIVE_COLUMN_REFERENCED`, or `UNRESOLVED_TABLE_SCOPE` when no sensitive reference was found but the table scope couldn't be resolved. `references` lists each [`SensitiveReference`](#result--sensitiveguardrailresult), and `unresolvedScope` is set when scope resolution was incomplete (see [Conservative failure](#conservative-failure)).

### `QueryParameterError` reasons

`reason` is a `QueryParameterRejectionReason`. [`bindPreparedQuery()`](#bindpreparedqueryprepared-values-guardrails) throws every one:

| Reason | Cause |
| --- | --- |
| `INVALID_VALUE` | A value doesn't match its parameter's `type` or `cardinality`: a list for a scalar, a non-finite number, a date that isn't `YYYY-MM-DD`, or `null`. |
| `MISSING_VALUE` | `values` has no entry for a declared parameter. |
| `UNRESOLVED_PLACEHOLDER` | A declared parameter doesn't appear in `namedSql`, a placeholder has no declaration, or a placeholder is left after binding. |
| `INVALID_LIST_CONTEXT` | A list parameter isn't alone inside `IN (…)`, or `= ANY(…)` on a dialect with `listBinding: "array"`. |
| `DIALECT_UNSUPPORTED` | The template's `dialect` isn't a built-in id, or `guardrails.dialect` has a different `id`. |
| `MISSING_GUARDRAIL_CONTEXT` | No third argument, or no `schema` in it. |
| `TENANT_VALUE_SUPPLIED` | `values` has a `:tenant_*` key. Tenant IDs come from `tenantScope` only. |
| `TENANT_PARAM_ALIGNMENT` | The tenant markers in `unboundSql` can't be lined up with the business parameters. |
| `DIALECT_SPEC_REQUIRED` | No `guardrails.dialect` for a template with `dialectRules: "host"`, or one stored without `dialectRules`. |
| `INVALID_DECLARATION` | A parameter in the template declares a `type` other than `string`, `number`, `boolean`, `date` or `datetime`, or a `cardinality` other than `one` or `many`, or the template's `parameters` isn't a list of declarations. Checked before any value; regenerate the template. |
