## 0.0.1-beta.12

### Patch Changes

- eef1321: `askdb init --connection-env <name> --studio-execute` now points Studio execute at the same env var as introspection, as the interactive wizard already did (#777). Before, the non-interactive path wrote `studio.execute.databaseUrl: env("DATABASE_URL")` whatever `--connection-env` named. With `--database prisma`, execute still targets Postgres and reads `DATABASE_URL`.
- 0e5d542: `askdb init` installs with the right package manager, on Windows too:
  
  - **A new pnpm project installs with pnpm** (#750). With no lockfile, `init` fell back to npm, which refuses a project that `pnpm init` started (`EBADDEVENGINES`). It now reads `package.json`'s `packageManager` or `devEngines.packageManager` field, then the tool that ran it (`pnpm dlx`, `yarn dlx`, `npx`, `bunx`), before falling back to npm. An existing lockfile still wins.
  - **The install runs on Windows** (#668). `init` spawned `pnpm.CMD`, `yarn.cmd` or `npm.cmd` without a shell, which Node refuses since its CVE-2024-27980 fix, so the install always failed. It now spawns the package manager as Studio does: allowlisted arguments, the bare command name, and a shell on Windows.
  - **The command `init` prints when it doesn't install names the package manager it picked**, with the `@prisma/engines` build approval on pnpm 10.4 or later. At a workspace root, or with no `package.json`, it printed `npm install --save …`.
- 2cd28cb: `askdb init` writes its files from the scaffold planner in `@askdb/config/scaffold`, which Studio's guided setup shares (#711). `askdb.config.ts` doesn't change. `init` now rejects some flag values it accepted, so this is a minor:
  
  - **An invalid env var name fails.** `--connection-env`, `--ai-key-env`, `--ai-model-env` and `--pgvector-env` take a name of uppercase letters, digits and underscores that doesn't start with a digit (`DATABASE_URL`, `_PRIVATE_URL`). Anything else, such as `my-url` or `database_url`, used to land in the config as `env("my-url")` and now fails.
  - **A path with a control character fails.** `--sqlite-file`, `--prisma-schema` and `--schema-out` reject a newline, a tab, NUL, DEL, U+2028 or U+2029. (`--sqlite-file` still reads a value that isn't an env var name as a path, as before.)
  - Either way, `init` exits 1 before it writes anything, with an error that names the flag, such as `--connection-env must be an environment variable name like DATABASE_URL: …`.
  
  Other changes:
  
  - **`.env.example` leaves every value empty.** Each variable is an empty `NAME=` line under a `# purpose` comment, database variables first. A connection URL's format moves from its value (`DATABASE_URL=postgresql://<USERNAME>:…`) into that comment, and a variable that introspection and Studio execute share says so.
  - **`--database prisma` also installs `ai` and `zod`** (#760): `ai` at the newest major `@askdb/core` accepts, and `zod` at core's range. Under Yarn Plug'n'Play, `askdb introspect --engine prisma` failed without them (`@askdb/core tried to access ai`).
  - **`init` installs a package other than AskDB's own only when `package.json` doesn't list it yet.** A project on `ai@^6` keeps it, and a driver you already list isn't re-added at its latest version.
- b030324: Every `askdb` command parses, documents and checks its flags the same way (#711). Each command's flags live in one table that both the parser and its `--help` read, so the help can't leave out a flag the command takes. `askdb` no longer depends on `commander`. Visible changes:
  
  - **`askdb help <command>` prints exactly what `askdb <command> --help` prints.** `askdb init --help` now lists `--interactive`, `-f` and `-y`, which it accepted but didn't document.
  - **Every command but `studio` and `enrich` takes `--flag=value`**, `askdb init` and `askdb bundle` included. Short flags combine as `askdb ask` took them under `commander` (`-qtext`, `-vq text`), now in every command (`askdb init -fy`).
  - **`askdb init` errors stop repeating values that could be secrets.** An unknown option, a stray argument or an invalid value is repeated only when it looks like a name or a number, as in the other commands.
  - **`askdb ask`'s usage errors read like the other commands'**: `Unknown option: --x` instead of `error: unknown option '--x'`, and `Missing --question <text>.` for a missing question. The exit code is still `1`.
  - **`askdb --help`, `askdb ask --help` and `askdb rag --help` use the shared layout**, with every flag listed under `Options:`.
  - **`askdb rag` with flags but no command says `Missing command (expected 'index', 'query', or 'setup-store')`** instead of `Unknown command: --flag`. `askdb rag` with no arguments still prints its help.
  - **`askdb introspect templates` works wherever the flags put `templates`**, such as `askdb introspect --engine postgres templates`.
  - **`askdb bundle --help` prints its help on stdout and exits `0`.** Without both `<schema-dir>` and `--out`, `bundle` still prints its usage line on stderr and exits `1`, and its flags may now come in any order.
  - **A failed connection prints why** (#749). When a driver gives up on several addresses, such as `localhost` refusing on both `::1` and `127.0.0.1`, `askdb introspect` printed an empty line. It now prints each address's error on its own line.
  - **`--log-stdout` into a reader that stops early no longer hangs.** `askdb rag index --log-stdout | head` waited forever on the unwritten log lines; `askdb` now exits once its output settles.
- ca816cc: The checks refuse a `b'…'` byte string (lower-case `b`) that holds a backslash or is continued on a later line (#730, ADR 0012). CockroachDB reads `b'…'` with backslash escapes, and the checks read it without them, so under the `cockroachdb` dialect `SELECT b'\'' AS x, o.* FROM orders o --'` passed all three checks while CockroachDB ran an unscoped read of `orders`. The read-only check refuses it on Postgres, CockroachDB and a dialect id that is no built-in engine, as `SQL_ESCAPED_BYTE_STRING`. The tenant check (`ESCAPED_BYTE_STRING`, `tableId: ""`) and the sensitive check (the `SensitiveScopeIssue` `ESCAPED_BYTE_STRING`) also cover a custom `AskDialect`, which skips the read-only check, and a call with no dialect. The lexer also reads `:b'…'` (an array slice's `:`) as `:` and a byte string.
  
  **Upgrade notes:** a `switch` over `SqlValidationRuleCode`, `TenantGuardrailRuleCode` or `SensitiveScopeIssue` needs a case for the new member. Write bytes with escapes as a hex string cast to `bytea` (`'\x00'::bytea`), which Postgres and CockroachDB both read as bytes; a `b'…'` string with no backslash, and a `B'…'` bit string, still pass.
  
  The docs add the codes to the `core-api` error tables, Safety boundaries, Troubleshooting, the multi-tenancy guide, the upgrade guide, SECURITY.md and the tenant and sensitive-fields contracts.

- 8410840: **Fix a cross-tenant leak in `subtree` scopes (#338): `resolveTenantDescendants` now returns IDs per tenant root.** The resolver returned one flat list, and `ask()` bound every ID to the scope root's placeholder. In a multi-table hierarchy (agencies → sub-agencies → clients), a sub-agency or client ID that equalled another agency's ID matched that agency's rows. The resolver now returns `TenantIdsByRoot` (`Record<rootTableId, string[]>`), and `ask()` expands the subtree into a `multi_root` scope, so each root's IDs bind only to that root's own placeholder. A resolver that still returns an array throws `TenantScopeError` (`SUBTREE_NOT_RESOLVABLE`) with a message showing the per-root shape to return. So does a key that isn't a tenant root in the subtree. Migrate a same-table resolver by returning `{ [tenantRoot]: ids }`. The decision and the options are in `docs/adrs/0014-subtree-scope-expands-per-root.md`.

  The resolver's result is read once: each entry is snapshotted before validation, and the scope is built from that snapshot. A getter can't return different IDs to validation and binding, and a non-enumerable property is never read.

  **A policy whose roots derive the same placeholder is now rejected.** `Agency` and `agency` both give `:tenant_agency_ids`, as do `Sub-Agency` and `Sub Agency` with `:tenant_sub_agency_ids`. Substitution then bound one root's IDs where the other root's column is compared. Loading such a policy throws `SchemaParseError` naming both roots. `validateTenantScope()` (and so `ask()`) and `resolveTenantSql()` also throw it for a policy built in code. This applies to every scope kind.

  **Labels without ASCII letters or digits now get a usable placeholder.** The placeholder keeps only ASCII letters and digits from the label, so every root labelled in Cyrillic, CJK or another non-Latin script derived `:tenant___ids`, and a policy with two such roots could never bind the right IDs. For such a label, the placeholder now comes from the root's table name (`Клиент` on `table:public.clients` → `:tenant_clients_ids`). Labels with an ASCII letter or digit keep their placeholder. Two setups that work today change, and both fail closed with an error:
  - A lone root labelled without ASCII letters or digits gets a new placeholder name. SQL or code that still uses `:tenant___ids` (stored SQL, SQL passed to `resolveTenantSql()`, or a lookup by `tenantBindings[].placeholder` or a prepared-query parameter name) throws `UNRESOLVED_TENANT_PLACEHOLDER`.
  - A non-ASCII label whose table name matches another root's label (`Агентство` on `table:public.agency` next to a root labelled `agency`) now fails at load with `SchemaParseError`.

  To migrate, switch to the new name (`placeholderForTenantRoot(root)` returns it; see "Tenant types" in the core API reference), or give the root an ASCII label. For a load failure, rename one of the two labels.

  **New export `placeholderForTenantRoot(root)`**, which takes the root object and returns the placeholder core prompts for and binds. `placeholderForRoot(label)` keeps its signature and its output, and is now `@deprecated`: for a label with no ASCII letter or digit it still returns `:tenant___ids`, which core no longer binds.

  **The tenant prompt now pairs each placeholder with its columns when the policy has more than one root.** Under each `:tenant_<label>_ids` line of a `multi_root` or `ids` scope, it lists the columns that hold that root's IDs (its own ID column, child roots' foreign keys to it, scoped tables' direct columns, and polymorphic ID columns with their discriminator value). It then tells the model never to compare one root's placeholder with another root's column. This changes the prompt bytes for every `multi_root` scope, and for `ids` scopes on multi-root policies. A single-root policy's `ids` prompt is unchanged. For `multi_root`, the prompt leaves a child root's foreign key out of its parent's list when that child is in the scope, marks a root with no IDs, and says that every listed root table the query reads must be filtered with its own placeholder. An expanded subtree is a `multi_root` scope, so the strict tenant guardrail from #315's fix checks it like any other: each tenant column must be compared with its own root's placeholder, and every root the expanded scope covers is checked as a root table. A query that reads a covered child root (`clients`) and filters it only through its parent's foreign key (`clients.sub_agency_id`) or a joined ancestor is rejected.

  **A covered level with no IDs stays in the expanded scope.** When the resolver returns no IDs for a level, that root stays in the `multi_root` scope with an empty ID list, instead of being dropped. Reading it then needs its own placeholder, which binds nothing and throws `UNRESOLVED_TENANT_PLACEHOLDER`. Dropped, it was checked less strictly than a level with IDs. A `multi_root` entry may now have an empty `ids` list (the scope schema and `validateTenantScope()` accept it, and at least one entry must still have an ID), so a custom `AskDialect` that validates its scope accepts the expansion, and a host expanding by hand can express an empty level. Reads through a parent's key or an ancestor are rejected under `enforcement: strict`; under `warn` they come back with a warning.

  **`buildTenantPromptBlock()` rejects an unexpanded `subtree` scope** with `SUBTREE_NOT_RESOLVABLE`, like `resolveTenantSql()`, instead of rendering only the root's placeholder.

Before, Studio wrote the file, returned 500, and then failed every request until the file was fixed by hand.
